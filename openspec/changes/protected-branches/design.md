## Goals / Non-Goals

**Goals:**

- Every write botswain makes to `main` or a series branch lands through a pull request gated by the same required checks as a person's, merges unattended when they pass, and leaves every tag pointing at a commit the planners' first-parent walk contains.
- The protection is declared, planned, and applied from `tooling/infra/`, so what the repository enforces is readable in the tree and `tofu plan` shows any drift.
- `cartograph` carries the app's version, prerelease included, written in the same commit as the app manifest, and a pull request that lets them differ fails.

**Non-Goals (design-level, beyond the proposal's):**

- No change to how a pull request's _branch_ commits are written; only the merge message is checked, and that check is `release-groups-guards`'.
- No second phase triggered by a merge event in this change. The planner job waits for its own pull request (D1); whether `library-minting`'s cut moves tagging into a merge-triggered handler is that change's decision.
- No OpenTofu for the App's installation, the environments, or the Actions secrets. One resource per thing this change needs, nothing speculative.
- No new dependency in `xtask`: the client it has is the client it uses.

## Decisions

### D1 (2026-10-17, revised 2026-10-29 — AUDIT): Every botswain write lands through the pull-request action already in the tree, auto-merges through the client `xtask` already has, and is tagged once the merge commit exists

Monolith D13, whose "why not a Rust client" rationale is moot: `xtask` has had one since `707f3a36`.

- **Why:** the cut's writes go through pull requests because `main` is protected. The release index is a second direct write to `main` — the index entry, through the same `github::update_file` — whose own comment leaves the protected-branch case to whoever protects the branch. Protecting `main` without routing that write would break every nightly's index entry.
- **The pull request is still opened by the action,** because `sign-commits` is what makes a bot commit verified: this repository requires every commit signed and a runner holds no signing key, so the commit must be created through the API, and `steps::create_pull_request` already does exactly that — commits whatever the preceding steps left in the working tree restricted to `add-paths`, reuses one branch per purpose so a stalled write is refreshed rather than stacked, and signs through the API. Reimplementing that in `octocrab` would be a Git Data API sequence to maintain beside a pinned action that already does it. A bot write therefore becomes: `xtask` edits files on disk; the action commits them and opens the pull request; and a second `cargo xtask` step, given the action's `pull-request-number` output, enables auto-merge and, for a transition, waits and tags. `github::update_file` and the `github::file` read inside `write_version` lose their last callers and go. Tags stay with `github::create_tag`.
- **Auto-merge is enabled through `octocrab`, not `gh`.** The REST API has no auto-merge endpoint; it is the GraphQL `enablePullRequestAutoMerge` mutation with `mergeMethod: MERGE`, sent through the client's `graphql` call under the same App token that opened the pull request. GitHub refuses the mutation for a pull request that is already mergeable — every required check reported before the step ran — so in that case the same step merges it directly through the client's merge call with the merge method; either way the landing is GitHub's, not a push.
- **The tag goes on the merge commit, and the job waits for it.** `main`'s first-parent history contains the merge commit, not the pull-request branch's commit, so a tag made before the merge would name a commit the planners never walk. The transition step polls the pull request through the client until `merged_at` is set, fails if it closes unmerged, reads `merge_commit_sha`, and creates the tag there with the App token, which is what makes the tag's push observable. One job, no new trigger, no state carried in a message; the cost is a runner idling for the length of the checks, on a dispatch-only workflow. A merge-triggered second phase was the alternative; it needs an identity check and the tag name parsed back out of the landed message, which `library-minting`'s cut may want anyway. Recorded as an open question there, not here.
- **Merging is unattended, with no waiting period** (decided 2026-10-19). A bot pull request merges as soon as its required checks pass; the checks are the whole gate. GitHub has no time-delay rule, so a cooling-off window would be a scheduled merger of our own — machinery for a veto nobody asked to use. With zero required approvals the check set is the only thing between a bot pull request and `main`, which is what makes `version-integrity` a required check rather than an advisory one.
- **Prerequisite:** the repository has `allow_auto_merge` off, so the mutation fails today. D2 turns it on.
- **One branch per purpose and per target.** The action refreshes its branch in place, so two writes sharing a branch would overwrite each other while the first is still waiting on its checks. The index uses `botswain/release-index/<channel>` — one per channel, which is what keeps the published _Per-channel index files_ requirement's concurrent-channel guarantee true across the pull-request hop — and the planner uses `botswain/release-plan/<target branch>`, since a cut opens one pull request against the series and one against `main` in one run.
- **The job is on the branch being written.** The action, by its own documentation, commits against the checked-out base unless `base` is supplied, and with `base` it _rebases_ the working-tree changes onto that branch — a whole-file index write would conflict with every nightly's earlier write. So the job checks out the target: `cut`'s first write already is on `main`; `advance`, `promote`, and `patch` need the series branch, which the planner only knows once it has computed the version, so it fetches and checks that branch out itself before the action runs; `release-index` is triggered by a tag but writes `main`, so its job checks out `main` with tags fetched and resolves the tag's rev with `git rev-parse`. The entry still lands after its tag and never in the tagged commit, as the published index requirement demands. This settles the monolith's open wrinkle: check the branch out, do not hand the action a `base`.
- **A cut writes twice.** The series branch is created at `main`'s `HEAD` as today; the planner checks it out, writes the app version, opens the series' pull request, checks `main` out again, writes the bump, and opens `main`'s. Both auto-merge; the job waits for the series' one and tags its merge commit. The App token gains `pull-requests: write`.
- **Rejected:** a ruleset bypass actor for the App on a branch ruleset; a hand-rolled Git Data API sequence in `octocrab`; `gh pr merge --auto` in a `run:` step (a second client for one call the typed one can make); a scheduled cooling-off merger; `base` on the action.
- **Gate:** `release-index --dry-run` prints the entry and names the branch and title it would open; the first nightly after landing records its entry through a pull request that merged itself, and the quiet-repository skip still holds the next day; a scratch-repository transition shows the tag on the merge commit.

### D2 (2026-10-19, revised 2026-10-29 — AUDIT): Three rulesets and two repository settings, declared in OpenTofu, with bypass scoped to tag minting

Monolith D17, which treated this as an audited manual step and listed rulesets-as-code as a follow-up. Reversed: `tooling/infra/github.tf` declares them, and "apply" is `just apply` of a specific `.tf` change.

| Resource                                       | Targets                                         | Rules                                                                                                                                                                                                                                                                                           | Bypass                  |
| ---------------------------------------------- | ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| `github_repository_ruleset.protected-main`     | `~DEFAULT_BRANCH`                               | `pull_request` with `required_approving_review_count = 0` and `allowed_merge_methods = ["merge"]`; `required_status_checks` naming `Test Linux`, `Audit the workflows`, and the `version-integrity` job, with `do_not_enforce_on_create`; `deletion`; `non_fast_forward`; `required_signatures` | none                    |
| `github_repository_ruleset.protected-versions` | `refs/heads/v*.x`                               | the same                                                                                                                                                                                                                                                                                        | none                    |
| `github_repository_ruleset.protected-releases` | `refs/tags/v*`, `refs/tags/*-v*` (target `tag`) | `creation`, `update`, `non_fast_forward` — **not** `deletion`                                                                                                                                                                                                                                   | App `4740347`, `exempt` |
| `github_repository.waypoints`                  | —                                               | `merge_commit_title = "PR_TITLE"`, `merge_commit_message = "PR_BODY"`, `allow_auto_merge = true`                                                                                                                                                                                                | —                       |

- **Zero approvals is what makes it unattended.** The rule requires a _pull request_, not a reviewer, so botswain's writes are gated by checks and merged by GitHub rather than by a person (D1).
- **One pattern replaces three.** `v?.?.x`, `v?.??.x`, `v?.???.x` each pin the major to a single character, so `v10.1.x` matches none of them — confirmed against `GET /rules/branches/v10.1.x`, which returned no rules while that ruleset existed. `refs/heads/v*.x` covers every major and minor; `v[0-9]*.[0-9]*.x` is the tighter form if the extra specificity is wanted, since character classes are supported and `?` is undocumented. Nothing is repointed: that ruleset is gone, and the resource creates `protected-versions` afresh.
- **Required checks name jobs.** A status-check context is the check run's name, which for Actions is the job's `name` — `Test Linux` and `Audit the workflows`, not `Tests` — plus whatever `release-groups-guards`' generated workflow names its job. `integration_id` may pin each to the GitHub Actions App so a same-named check from elsewhere cannot satisfy it.
- **Bypass is scoped to the one thing the rules would otherwise forbid.** Botswain needs no bypass to open a pull request, and none for not deleting a branch — so the `exempt` entry the old `protected-versions` carried was wider than its job, and on a ruleset that requires checks a bypass would skip the gate that is doing all the work. It is exempt only on the tag ruleset, because restricting tag _creation_ is what stops a person hand-minting a `v*` tag that the index and release pipelines would then act on, and the planner must still mint them.
- **The planners only ever create tags.** `cut`, `advance`, `promote`, and `patch` each end in one `create_tag`, and the nightly planner in one too. Nothing in either planner updates, moves, or force-pushes a tag, so `update` and `non_fast_forward` are free safety rather than constraints the pipeline has to satisfy.
- **`deletion` is left unrestricted, revising the monolith.** The monolith counted `deletion` as free safety too; it is not. The published _A shortfall withdraws what the run created_ requires the nightly run to delete a tag it minted when it falls short, and `steps::delete_minted_tag` does that with `gh api -X DELETE` under `GITHUB_TOKEN`, which cannot be a bypass actor. Restricting deletion would turn every nightly shortfall into a tag left pointing at an unpublished build. Handing the withdraw job an App token instead would need the `App Release` service account to read the botswain vault item, which is a secret-provisioning change, not this one. A deleted tag is recoverable from the index entry's `rev` and leaves the Nix overlay unaffected, so the loss is small; recreating one by hand is still refused.
- **`--verify-tag` is what keeps the release workflows compatible.** `steps::create_release` runs `gh release view … || gh release create … --verify-tag` under `GITHUB_TOKEN`, which is _not_ the bypass actor. The flag makes `gh` abort rather than create a missing tag, so that path never attempts a ref creation the ruleset would refuse. The generator asserts the flag stays.
- **The tag patterns cover the group tags too.** `refs/tags/v*` does not match `bedrock-v0.4.0`; `refs/tags/*-v*` closes that, ahead of `library-minting`. The repository's one non-release tag, `conventional-commits`, matches neither and stays unprotected, which is right.
- **The branch, not the tag, is the risk in a cut.** `cut` creates `v{minor}.x` with `create_branch`, and `protected-versions` deliberately carries no `creation` rule. `do_not_enforce_on_create` on the status-checks rule (verified in the provider docs: "allow repositories and branches to be created if a check would otherwise prohibit it") covers the checks half. Whether the pull-request rule itself also refuses the _initial creation_ of a matching branch is not settled by the documentation. Verify when enabling (task 4.2); if creation is refused, the fallback is a bypass actor on `protected-versions`, which costs the enforcement guarantee, not the behaviour, and is recorded here.
- **Two repository settings, neither of them a ruleset rule:** `merge_commit_message` moves from `BLANK` to `PR_BODY`, without which every summary body and `Covenant: break` trailer is dropped at merge; and `allow_auto_merge` turns on, without which the auto-merge mutation fails (D1). They live on `github_repository`, which must be _imported_, never created: a `github_repository` the provider creates is a new repository, and one it destroys is a deleted one, so the resource carries `lifecycle { prevent_destroy = true }` and declares every setting the provider would otherwise default — `visibility`, `has_issues`, `has_discussions`, `has_projects`, `has_wiki`, the three `allow_*_merge`, `delete_branch_on_merge`, `squash_merge_commit_*` — at their current values, so the first plan shows exactly two attributes changing.
- **Ordering.** The tag ruleset and both settings are safe to apply at any time. The two branch rulesets are applied only together with the write path (tasks group 3), in one sentence: the planners' direct Contents-API writes fail the moment protection is on. The empirical gate stays: `GET /rules/branches/<name>` after every apply.
- **Rejected:** one ruleset covering `main` and the series branches together; a `required_deployments` rule, which `default` carries today and nothing in this pipeline deploys; keeping botswain exempt everywhere, which would silently defeat every required check; restricting tag deletion (above); `tofu import` of the disabled `default` ruleset (it is replaced, and deleting it by hand is one click with nothing depending on it).
- **Gate:** `tofu plan` is clean after apply; `GET /rules/branches/<name>` lists the expected rules for `main`, `v0.1.x`, and `v10.10.x`; a pull request with a free-form title cannot merge and a conventional one can; a hand-pushed `v*` tag is refused while botswain's is accepted and a `GITHUB_TOKEN` deletion of a tag still succeeds; a test pull request's merge commit carries its description verbatim.

### D3 (2026-10-29, decided — AUDIT): The provider authenticates as the wp-botswain App through `app_auth`, and `owner` names wherever the repository lives

- **What was verified** (OpenTofu registry, provider `v6.13.0`; `docs/index.md` of the provider repository at `main`):
  - `github_repository_ruleset` takes `name`, `repository`, `target` (`branch` | `tag` | `push`), `enforcement`, a `conditions { ref_name { include, exclude } }` block accepting `~DEFAULT_BRANCH`, a `rules` block with `creation`, `update`, `deletion`, `non_fast_forward`, `required_signatures`, `required_linear_history`, `pull_request { required_approving_review_count, allowed_merge_methods, … }`, and `required_status_checks { required_check { context, integration_id }, strict_required_status_checks_policy, do_not_enforce_on_create }`; and `bypass_actors { actor_id, actor_type, bypass_mode }` where `actor_type = "Integration"` names a GitHub App by App id and `bypass_mode` is `always` | `pull_request` | `exempt`. Import is `<repository>:<ruleset id>`.
  - `github_repository` exposes `merge_commit_title` (`PR_TITLE` | `MERGE_MESSAGE`), `merge_commit_message` (`PR_BODY` | `PR_TITLE` | `BLANK`), and `allow_auto_merge`, with the note that under App authentication even reads need `contents: write` or the merge-settings arguments are silently ignored. Import is by repository name.
  - App authentication is the provider's highest-priority mode: an `app_auth { id, installation_id, pem_file }` block, all three required, where `pem_file` is the PEM _contents_ (newlines may be written as `\n`), not a path; the environment equivalents are `GITHUB_APP_ID`, `GITHUB_APP_INSTALLATION_ID`, `GITHUB_APP_PEM_FILE`; `auth_mode = "app"` pins the mode; and `owner` is required — "GitHub organization or user account to manage". A `token` is the alternative mode.
  - The App today (`gh api apps/wp-botswain`): owned by `waypoints-hq`, `administration: read`, `contents: write`, `pull_requests: write`, `metadata: read`. Rulesets and the repository settings D2 writes are governed by the repository **Administration** permission, so the grant must become `administration: write` and the installation on `jmuchovej/waypoints` must accept it. `contents: write`, which the `github_repository` note requires for reads under App auth, is already granted.
- **Why the App, not a token.** The repository is to move to a GitHub organization, and the App installation is what carries over: the `owner` argument changes from `jmuchovej` to the organization and nothing else in `github.tf` does. A fine-grained personal access token is bound to one account and one owner and would be re-minted at the move. The App is also already the identity every other automated write to this repository carries.
- **Credentials.** The App id and private key already exist in the `botswain` vault item behind `WP_BOTSWAIN_APP_ID` and `WP_BOTSWAIN_PRIVATE_KEY`; they are mapped into the `waypoints` 1Password environment under the same names and read as `data.onepassword_environment.waypoints.variables[...]`, the pattern `main.tf` uses for Cloudflare. The installation id is new: it is not secret, is read from the App's installation page or `GET /app/installations` under an App JWT, and joins the environment as `WP_BOTSWAIN_INSTALLATION_ID`. Nothing is a literal in the tree.
- **What `administration: write` costs.** Every CI job that mints an App token could then request it. It is bounded by `app_token` narrowing each token to the permissions it names — `release-plan`, `prepare`, `release-index`, and `devenv-update` never name `administration` — and a generator test asserts no workflow does.
- **Rejected:** a fine-grained PAT (the org move); the `gh auth token` fallback (legacy client only, removed in a future major); `GITHUB_TOKEN` (cannot administer).
- **Gate:** `gh api apps/wp-botswain --jq .permissions.administration` reports `write`; `tofu plan` with the provider configured and no GitHub resources shows no diff; a plan with only `github_repository.waypoints` imported shows the two settings and nothing else; the generator test over every `app_token` call is green.

### D4 (2026-10-11): `cartograph` is lockstep with `src-tauri`, written by every transition in one commit

The lockstep half of monolith D9; the bot-only write and the reserved subject are `release-groups-guards`'.

- **Why:** if people or agents edit versions, the planner's output stops being the record; a member that drifts from its anchor is a version nobody minted.
- **Shape:** `crates/cartograph` follows `src-tauri`, so every app transition writes both manifests with `set_package_version`, and the pull-request step commits them together. On `main` that means `cartograph` carries the same `-nightly` prerelease the app manifest does; cargo accepts a prerelease in a path dependency and nothing consumes `cartograph` by version. `store` drops its `version`, as `xtask`'s already has; `src-tauri` gains `publish.workspace = true` so `publish = false` holds workspace-wide.
- **The check:** `cargo xtask version-integrity` (from `release-groups-guards`) gains the comparison: every versioned member equals its anchor, naming both manifests on drift. It lands here, not with the first guards, because until the planner writes both manifests the next transition drifts `cartograph` and a tree-comparing check fails every pull request on that branch.
- **A mirrored version is not a channel declaration.** D5 amends the published requirement so the contradiction is not left implicit.
- **Gate:** `cargo metadata --no-deps` resolves; `the_app_declares_its_own_version` passes; the lockstep test fails on a hand-drifted `cartograph` and passes on the tree.

### D5 (2026-10-19, proposed — AUDIT): Two published requirements are modified rather than worked around

Monolith D16. Protecting the branches contradicts two requirements `nix-release-index` published, so this change amends them instead of bending around them.

- **_A series branch carries only cherry-picks of `main`_** admits "the planner's version commits and cherry-picks of commits already on `main`", and nothing else. Landing a version commit through a pull request adds a merge commit, a third kind. The requirement is modified to allow the planner's version commit to arrive as the merge commit of a bot pull request, which is what protection forces; its purpose — that no change originates on a series branch, so a tagged tree is self-sufficient — is unchanged and restated.
- **_The manifest version names the channel_** ends `No other file SHALL declare a channel`, which a lockstep `cartograph` version carrying `-nightly` would appear to violate (D4). The requirement is modified to say that a versioned group member mirrors its anchor and is never read as a version or channel source, so the app manifest remains the only one consulted.
- **Rejected:** keeping lockstep to the base version only, which would make "every member equals its anchor" untrue the moment a prerelease exists; and exempting series branches from protection, which the decision does not allow.
- **Gate:** `openspec validate protected-branches --strict` passes with both requirements quoted in full under `## MODIFIED Requirements`, and the archive diff shows only the stated edits.

## Risks / Trade-offs

- [Enabling branch protection before the write path lands] → the nightly index write starts failing that same day. Tasks group 4 applies the branch rulesets only with group 3; the tag ruleset and the settings are the only pieces applied early (D2).
- [`main` and series branches are protected] → every transition becomes two-phase (open PR → merge → tag), and the index write follows (D1). John's local `merge: … into main` commits can no longer be pushed; a feature branch lands by pull request with a conventional title.
- [Unattended merges make the check set the only gate] → with zero required approvals and auto-merge, nothing but the required checks stands between a bot pull request and `main`. Accepted deliberately (D1), which is why `version-integrity` is required rather than advisory, and why a check that cannot report must never be required.
- [A required check that is path-filtered never reports] → `check-generated` is path-filtered and would leave a pull request waiting forever if required. Only the `Tests` jobs and `version-integrity` are required.
- [A required check is renamed] → the ruleset names job display names; a rename in the generator strands every pull request. The generator test that reads the rendered job names is the place to pin them against `github.tf`'s list.
- [The planner job idles while the checks run] → tens of minutes on a dispatch-only workflow, once per transition. Accepted (D1); the six-hour job limit is far away.
- [A release tag can still be deleted by anyone with write] → accepted (D2): the withdraw needs it, the index entry's `rev` survives it, and creation stays restricted so a deleted tag cannot be replaced by hand.
- [`tofu destroy` or a wrong edit of `github_repository`] → `prevent_destroy`, every current setting declared explicitly, and the rule that the first plan after import must show exactly two attributes (D2, D3).
- [The App holds `administration: write`, and CI mints App tokens] → every minted token is narrowed to the permissions its step names, none names `administration`, and a generator test keeps it so (D3).
- [A third-party action sits in the release path] → `create-pull-request` is pinned by SHA, already carries `devenv-update`'s weekly write, and is audited by zizmor like every other action. Every bot write goes through one generator helper, so replacing it later is one function.
- [A planner now needs the branch it writes checked out] → one fetch and checkout per transition, which the planner does itself (D1).
- [Lockstep `cartograph` carries a prerelease version on `main`] → cargo accepts a prerelease in a path dependency; nothing consumes `cartograph` by version, and D5 settles the spec-level reading.
- [A series branch is created under a pull-request rule and refused] → verified empirically before relying on it (task 4.2); the fallback is a bypass actor on `protected-versions`, recorded in D2.

## Migration Plan

1. **Lockstep manifests and the check** (D4, tasks group 1), after `release-groups-guards` has landed its `version-integrity` task and workflow. Landable alone: no planner changes yet, and the tree already agrees.
2. **The safe infrastructure** (D2, D3, tasks group 2): the App's `administration: write`, the provider, the imported `github_repository` with its two settings, and the `protected-releases` tag ruleset. Applied from a branch before the write path, since they break nothing.
3. **The write path and the branch rulesets together** (D1, D2; tasks groups 3 and 4): route every bot write through the pull-request step, regenerate the workflows, land them, then apply the two branch rulesets in the same sitting and run the empirical gate.
4. **The first nightly** records its entry through a pull request that merged itself; the first dispatched transition is a cut that creates a series branch under `protected-versions`.

Rollback: step 1 is additive. Step 2 reverts by `tofu` setting the two attributes back, which is a two-line diff. Step 3 reverts by setting the two branch rulesets' `enforcement` to `disabled` in `github.tf` and applying, then restoring `update_file`'s callers; tags already minted stay valid.

## Follow-ups

- When the repository moves to the organization: `owner` in `github.tf` changes to the organization, the App's installation is confirmed there, and `tofu plan` must be clean before the first apply (D3).
- Restricting tag deletion once the withdraw job can hold an App token — a secret-provisioning change giving the `App Release` service account the botswain item (D2).
- `BotswainGitIdentity` has no callers and this change adds none, since commits are created through the API rather than by a local `git commit`. Either something will want it or it should go; listed here rather than removed.
- Deleting the disabled `default` ruleset by hand once `protected-main` is active; nothing depends on it.
- The releases that still point at removed tags (`v0.1.0`, `v0.1.0-pre.2`, and older nightlies); not this change's concern, but the tag ruleset will refuse recreating those tags by hand.

## Open Questions

- How "the tag and the build succeeded" gates an index entry. A required status check cannot see it: the build ran on the tag, in another workflow, not on the index pull request's own commits. The cleaner reading is to gate upstream — the index workflow waits for the release run to conclude before opening its pull request. Affects `release-index`'s job wiring, not the specs.
- Whether `library-minting`'s cut keeps D1's wait-in-job tagging or moves to a merge-triggered second phase that reads the landed summary body. Either tags the merge commit; the specs do not change.
