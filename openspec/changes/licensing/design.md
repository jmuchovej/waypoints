# Design

## Context

See proposal.md — Why. What shapes the approach, as of 2026-11-04:

- The workspace has fourteen members — `bedrock`, `bedrock-core`, `bedrock-derive`, `cartograph`, `domain`, `outpost`, `outpost-fabric`, `outpost-hold`, `outpost-protocol`, `store`, `transload`, `src-tauri` (the package `Waypoints`), `tooling/gh-workflow`, `tooling/xtask` — all inheriting `license = "Apache-2.0"` and `publish = false` from `[workspace.package]`, none overriding. One of them, `gh-workflow`, is vendored third-party code (D5). No source file carries an SPDX header.
- The frontend is the Nuxt 4 app under `src/`, built by `just app::generate` into `src/.output/public`, which `Tauri.toml` bundles; pnpm with catalogs manages `src`, `website`, `crates/domain` and `crates/cartograph`; Vite options live inline in `src/nuxt.config.ts`. `website/` is a separately deployed Cloudflare worker.
- `docs/` is the source of pages the website publishes — the license page now, later a `docs/legal/` tree — so `docs/licensing/` is authored to render as Markdown. No license text, additional permission or contributor agreement exists anywhere in the tree. Two one-line README stubs exist, `README.md` at the root and `.github/README.md`, the latter named by the workspace `readme` field; GitHub surfaces a README from the root, `docs/` or `.github/`.
- Enforcement shapes already exist and are reused rather than paralleled: Rust-native checks live in `tooling/xtask`; GitHub workflows are generated by `cargo xtask workflows`; local gates are `hk` pre-push steps in `.config/hk.pkl`; generated files are kept honest by `just check-generated`; `.config/deny.toml` is a tuned cargo-deny config with the AGPL-compatible allowlist already in place (D4, D7). `tooling/infra/` is an OpenTofu root module with the 1Password and Cloudflare providers and encrypted Postgres state; it has no GitHub provider yet.
- The copyright holder is John Muchovej, an individual; the Steward of the contributor agreement is the same person, and the agreement's governing law is Connecticut for now. CLA assistant (`cla-assistant.io`) is already configured for the repository against the secret Gist `f2903ad9aa3c2eb374faa28ebadab7f6`, which today holds a one-line placeholder `CLA.md` and a five-field `metadata` schema (D9).

## Goals / Non-Goals

**Goals:**

- Land the licensing posture as declared files, headers and checks that fail a pull request, so the policy cannot drift unobserved.
- Make the change self-contained: a reader with this change and the tree needs nothing else to know what the license is, why, and how it is enforced.
- Reuse the repository's existing enforcement shapes — `xtask` tasks, generated workflows, `hk` steps, the generated-file lockstep check — rather than adding a parallel mechanism.

**Non-Goals:**

- Resolving any legal question. Counsel flags are carried as `[⚖ …]` in this record and left open.
- Choosing the Steward's remaining blanks or the content-and-brand carve-out (D6, Open Questions).
- Reimplementing dependency allowlisting; `cargo-deny` owns it.
- Publishing `docs/` to the website; this change only authors `docs/licensing/` so that it renders.

## Decisions

### D1 — A new `licensing` spec domain

None of the registered domains fits. `toolchain` is forbidden from citing product domains and from constraining app behaviour, yet the license choice rests on what the sync Station is and the notices file ships inside the app. `distribution` is about built artifacts. `app-shell` is the command surface. The config says to mint a domain only when none fits and to say so — this is that case. `licensing` is a tree with four areas: `project-license`, `source-notices`, `third-party-code`, `contribution`.

Rejected: folding everything under `toolchain/licensing` (violates its own charter), or scattering across `toolchain` (checks), `distribution` (notices), and a docs-only change (CLA) — the invariants reference each other and belong in one place.

### D2 — The validator is `cargo xtask license`, on the `spdx` crate

The repository's rule is that Rust-native work lives in `xtask` and shell scripts orchestrate command-line tools. Checking SPDX expressions, walking `cargo metadata`, and judging dependency kinds are all Rust-native. The `spdx` crate (0.13.6, Apache-2.0, the same one `cargo-deny` uses; verified 2026-11-02 on crates.io and docs.rs) gives `Expression::{parse, canonicalize, evaluate, requirements}` and `LicenseId::{is_deprecated, is_copyleft}` — expression parsing, canonicalisation, deprecation and the copyleft flag for free. `cargo_metadata` 0.23.1 is already a workspace dependency; `spdx` and `ignore` (for the gitignore-aware walk) are new.

The task has three subcommands. `check` (the default) runs six checks, reading the third-party registry `.config/third-party.toml` (D5) for the paths and crates that are not ours:

1. **Manifests.** For each workspace package: the `license` field parses, no identifier in it is deprecated, and — for a first-party crate — the policy `AGPL-3.0-or-later` satisfies the expression; for a crate the registry marks third-party, the expression is satisfied by some identifier on the allowlist; for a crate declared as a permissive tier (none today), the expression equals `MIT OR Apache-2.0` and the crate directory holds both license texts.
2. **Headers.** Walk the tree honouring `.gitignore`, skipping the registry's paths and `src-tauri/gen/`; for every file whose extension is header-bearing (or which is an extensionless file under `tooling/bin/`), read the initial comment block after any shebang or `#:tombi` directive and require at least one `SPDX-FileCopyrightText` line carrying a single four-digit year and no bracketed placeholder, exactly one `SPDX-License-Identifier` line, and canonical equality of that expression with the owning crate's (longest crate directory prefix wins; the policy for files outside any crate). The year is never compared with the calendar.
3. **Layering.** For each non-copyleft workspace crate, depth-first over the resolve graph's normal-kind edges; fail on reaching a copyleft workspace crate. Copyleft is "every satisfying path requires a copyleft identifier", so `MIT OR GPL-3.0-or-later` is not copyleft. Vacuous today and run anyway.
4. **Allowlist equality.** The identifier list in `src/nuxt.config.ts`'s plugin options equals `.config/deny.toml`'s `[licenses].allow`. The TOML side is parsed; the TypeScript side is read as a named constant in a known file, and the check names the file and line when the shapes differ.
5. **License texts and the registry.** The root `LICENSE` and `docs/licensing/LICENSE.md` are regular files whose SHA-256 digests equal the FSF's plain-text edition (`0d96a4ff68ad6d4b6f1f30f713b18d5184912ba8dd389f86aa7710db079abcb0`, 34,523 bytes) and Markdown edition (`00352ab19865e23bb0ab7e0f45332206aba6a66d75b3f3cc962fdd6508d63ea4`, 34,260 bytes) respectively, both fetched from `https://www.gnu.org/licenses/agpl-3.0.{txt,md}` on 2026-11-03; no other `LICENSE*` or `COPYING*` regular file sits at the root; and every registry entry names a license some allowlisted identifier satisfies and only text files that exist.
6. **Published agreement.** The Gist that CLA assistant displays (D9) is fetched unauthenticated and compared with `docs/licensing/CLA.md` and `docs/licensing/cla-metadata.json`: identical passes; a differing `CLA.md` whose version line also differs is a pending publication — it passes on a pull request and fails on a push to `main`, so the Gist is updated right after the merge that bumped it; a differing `CLA.md` with the same version line fails; a differing `metadata` fails. A network failure is reported as one, not as a mismatch.

`notices` regenerates `src-tauri/resources/THIRD-PARTY-NOTICES.md` (D4). `publish` runs item 6 and, when the repository carries a newer version, writes `docs/licensing/CLA.md` and `docs/licensing/cla-metadata.json` into the Gist with `octocrab`'s `gists().update(id).file(name).with_content(..)` on a client authenticated by the device flow as the `wp-botswain` App — not the installation token `tools/github.rs` builds, which cannot reach a user's Gists; it refuses a text with the same version line and a text containing a bracketed blank (D9).

Rejected: a shell script over `git ls-files` and `grep` — adequate for headers alone, but the manifest and layering checks need the metadata graph, and one tool that reports every failure in one run beats three. Rejected: REUSE's `reuse lint` — it checks header presence and license-file presence, not header-to-manifest agreement or layering, and adopting it is a non-goal.

### D3 — Header scope: source by type, exemptions by path, tags in the initial comment block, the year fixed at first authorship

Header-bearing extensions are `rs`, `ts`, `vue`, `js`, `mjs`, `css`, `toml`, `nix`, `typ`, `nu`, `sh`, plus extensionless files under `tooling/bin/` (nine bash and nushell scripts, each starting with a shebang). Everything else — `yaml` (fifty-two tracked files, nearly all generated workflows), `json`, `xml`, `md`, `kt`, `swift`, `tf`, `pkl`, images, fonts, lockfiles, `.d.ts` — is not. The dividing line is "code the application or its tooling is built from" against "data, configuration and documents"; a header in a workflow YAML would also trip zizmor's and the renderer's expectations for nothing. The tracked source census the scope covers: 337 `.rs`, 99 `.ts`, 93 `.vue`, 53 `.toml`, 15 `.typ`, 12 `.nix`, 4 `.css`, 2 `.nu`, plus the website's own `.vue` and `.ts` (D6).

The walk honours `.gitignore`, so build output and dependency trees (`target`, `node_modules`, `.output`, `.nuxt`) never enter it. Exemptions are tracked paths and come from two places: the third-party registry (D5), whose `crate` and `files` entries name code that carries its upstream's license and so must not carry ours — `tooling/gh-workflow/` and `tooling/patches/` today — and one constant, `src-tauri/gen/`, for the platform projects that mix Tauri scaffolding with hand-maintained `project.yml` and Gradle files. The check reads the initial comment block after any shebang or the `#:tombi toml-version` directive every TOML file begins with, so neither displaces the tags. The formatters in play — `rustfmt`, `oxfmt` for TS/Vue/JS/CSS/Markdown, `tombi`, `nixfmt`, `typos` — do not rewrite leading comments.

What the block must contain is deliberately minimal: at least one `SPDX-FileCopyrightText: <year> <holder>` line and exactly one `SPDX-License-Identifier: AGPL-3.0-or-later` line. The holder is John Muchovej. The year is the year the file was first authored and never changes — the one-off header write takes it from the commit that first added each file, the generator keeps the year an existing output file carries and uses the current year for a new one, and the check requires a single four-digit year without comparing it to the calendar. A contributor who holds copyright in a file — or a registered ported portion's upstream holder — gets their own `SPDX-FileCopyrightText` line beside the Steward's; the check requires at least one, not exactly one. A pointer line to `docs/licensing/COPYING.exceptions` may follow and is not required: the permission is a term of the license named by the identifier, and the full notice at the entry points spells it out.

Generated TypeScript (`crates/domain/typescript/{types.g,schema.g}.ts`, `crates/cartograph/typescript/types.g.ts`) is written by `cargo xtask typegen`, whose first line is already a generated-file marker (`typegen.rs:27`); the generator emits the tags after it.

The full notice goes on crate roots (`crates/*/src/lib.rs`, `src-tauri/src/lib.rs`, `tooling/xtask/src/lib.rs`), the four flavour binaries under `src-tauri/src/bin/`, `src/app/app.vue`, and `docs/README.md`. Everything else takes the two tags. The one-off header write is a script run once and discarded; headers are then maintained by hand under the check.

Rejected: headers in YAML and JSON — JSON cannot carry one, and REUSE-style `.license` sidecars are what REUSE adoption would bring, later. Rejected: a fixed three-line header within the first five lines — brittle against directives and multi-holder files for no gain over "the tags are present and agree". Rejected: a current-year or year-range convention — it churns every file annually for no legal benefit, since the year records first publication, and a range misstates it.

### D4 — Dependency gates reuse `cargo-deny` and a Vite plugin; notices are generated from the registry and the lockfiles, and committed

`.config/deny.toml` is the canonical cargo-deny configuration (`.cargo/deny.toml` is a symlink to it, and a devenv task syncs its `graph.targets` from `rust-toolchain.toml`). Its `[licenses].allow` is already the sixteen-identifier AGPL-compatible set the third-party-code spec names, with `confidence-threshold = 0.8`, `private.ignore = true` for the unpublished workspace crates, and one `[[licenses.clarify]]` for `cfg_block`. `cargo deny check licenses` passes today (2026-11-02): the dependencies relying on MPL-2.0 alone — `attohttpc`, `colored`, `cssparser`, `cssparser-macros`, `dtoa-short`, `option-ext`, `selectors` — are unmodified registry crates, so the weak copyleft imposes nothing on us; `detect-coding-agent` offers `EUPL-1.2` and `fastdivide` offers `zlib-acknowledgement` only as alternatives in `OR` expressions, never relied on. Nothing in the allowlist changes; what changes is that the check runs in CI (D7) instead of only before a push, and that the same list governs in-tree third-party code through the registry (D5).

The frontend **gate** is `rollup-license-plugin` (3.2.1, MIT; options verified 2026-11-02 against its README) in `src/nuxt.config.ts`'s `vite.plugins`: `unacceptableLicenseTest` returning true for any identifier outside a named allowlist constant, `licenseOverrides` (keyed `name@version`) for bad metadata, `outputFilename: false`. It operates on what actually ships and fails the build; the validator (D2 item 4) keeps its constant equal to `deny.toml`'s list.

**Notices.** `cargo xtask license notices` has three inputs. First the registry: every `.config/third-party.toml` entry — vendored crates, copied files and ported portions alike — is rendered into a hand-authored "In-tree third-party code" section, which is what closes the gap a lockfile-only generator would leave for ported code that no manifest names. Then `cargo about generate -c .config/about.toml .config/about.hbs` (`cargo-about` 0.9.3, packaged in nixpkgs, added to `devenv.nix`; `cargo about init` writes both files) for the Rust dependencies, and `pnpm licenses list --prod --json` filtered to the `src` package's closure for the frontend's. The three are merged into `src-tauri/resources/THIRD-PARTY-NOTICES.md`, and that file is committed. `check-generated` gains `Cargo.lock`, `pnpm-lock.yaml` and the registry as sources and the notices file as an output, so the existing lockstep machinery fails a pull request that changes any of them without regenerating. The file ships as a Tauri `bundle.resources` entry rendered from a Settings page, and in every release archive beside the license texts.

Rejected: generating the notices from the plugin's bill of materials at build time. It is exact to the bundled byte, but it needs a full Nuxt build inside the lockstep check and a `cargo about` run inside the Nix derivation, where vendored registry sources are not laid out as `cargo-about` expects. A lockfile-derived list over-includes a tree-shaken package, which costs nothing; it never omits one, which is what matters. Rejected: `license-checker`-style tools — one more tool for a job `pnpm` already does. Rejected: lockfile-only gating for the frontend — the gate should see what ships.

### D5 — Third-party code in the tree declares its own license, and one registry records it

`tooling/gh-workflow` is a vendored copy of `tailcallhq/gh-workflow` (upstream base `3793c17`, with a documented local delta) that `just gh-workflow-sync` overwrites from upstream. Upstream is Apache-2.0 — its `LICENSE` reads "Copyright 2023 Tailcall", and the companion `gh-workflow-macros` 0.9.0 on crates.io declares `Apache-2.0` (verified 2026-11-02) — but the vendored manifest says `license.workspace = true` and the directory holds no license or notice file. After the flip that would label Tailcall's code `AGPL-3.0-or-later`, which is false and, since Apache-2.0 requires preserving its notices, a compliance gap on our side. So the manifest declares `license = "Apache-2.0"`, the directory gains upstream's `LICENSE` and `NOTICE`, the sync recipe is amended to keep the three files (it already keeps the README), and the README's provenance table records them.

The two `[patch.crates-io]` forks, `tooling/patches/specta-macros` (2.0.0-rc.25) and `tooling/patches/specta-serde` (0.0.12), declare `MIT` in their cargo-normalised manifests but carry no license text; each gains `LICENSE-MIT` from upstream specta. They are not workspace members, so cargo-deny already judges them as ordinary dependencies. There is no `vendor/` directory, and no first-party source carries a foreign license header or a "ported from" attribution to another project.

**The registry.** Three things need the same facts about code we did not write — which paths the header check must skip, which crates the manifest check must judge by their own license, and what the notices must attribute — and a lockfile-driven notices generator can never see a routine ported into a first-party file. One file, `.config/third-party.toml`, feeds all three, and the Steward edits data rather than the validator:

```toml
[[entry]]
path    = "tooling/gh-workflow"
kind    = "crate"                    # crate | files | portion
project = "tailcallhq/gh-workflow"
holder  = "Tailcall"
license = "Apache-2.0"
texts   = ["LICENSE", "NOTICE"]
```

`crate` and `files` entries are whole units carrying their own license texts; they are exempt from the header check and, for workspace members, judged against their own declared license. `portion` entries are routines or snippets inside first-party files: the file keeps the project license and its identifier, the portion is bracketed by a comment naming its origin, holder and license, the file gains the holder's `SPDX-FileCopyrightText` line, and the registry entry carries the attribution into the notices. Every entry's license must be on the allowlist — one list, the same one `cargo-deny` and the Vite gate use — and every text file it names must exist; the validator checks both (D2 item 5). The rules a contributor follows to add such material are the "Contributions containing material you do not own" section of the licensing overview (Appendix C), which the agreement's non-owner pointer resolves to.

Rejected: re-vendoring with our headers — upstream has none, and adding ours to their files would be the same mislabel. Rejected: a central `docs/licensing/LICENSE.APACHE` — attribution belongs beside the code it covers, and a directory of every third-party license text is what REUSE's `LICENSES/` is for, which is deferred. Rejected: keeping the exempt paths and third-party crates as constants in the validator — two lists to keep in step by hand, and no path from a ported snippet to the notices.

### D6 — `website/` code is first-party under the project license; content and brand are the open question

`website/` is a Nuxt site deployed on its own as a Cloudflare worker, with its own `package.json`. Its code is ours and served by us, and nothing distinguishes it from the app's frontend for licensing purposes: it carries the project license like everything else first-party, and its `.vue` and `.ts` files are header-bearing like the rest. "Licensing the website" is not a separate question.

What the root license does not fit is the non-code material in the tree: the website's copy, the Waypoints name and logo, the app icons and marketing renders under `src-tauri/res/`. Copyright in all of it already exists; the question is what the license _grants_, and under AGPL anyone may copy and adapt that material — trademark stops passing-off, not copying. The carve-out is a Steward decision listed in Open Questions: a trademark notice, an explicit exclusion of brand assets from the license grant, and which of the agreement's Creative Commons options documentation and website copy take. Until it is made, the material sits under the root license by default; none of it is header-bearing, so the header check is unaffected either way.

Rejected: a separate code license for `website/` — nothing third parties must link, so a permissive site would be a birth-policy exception for no interoperability reason. Rejected: exempting `website/` from the header check pending a decision — the decision is about content, not code.

### D7 — CI: one job in the Tests workflow, one `hk` step, three lockstep additions

CI is GitHub Actions generated by `cargo xtask workflows` from `tooling/xtask/src/workflows/`. The Tests workflow (`pull_request.rs`) runs `test-linux` on a mise-based setup and `zizmor`; `check-generated` installs Nix, cachix and devenv and runs `devenv shell -- just check-generated`. Locally, `.config/hk.pkl` runs `clippy`, `nextest`, `deny` (via `just deny`), `check-generated`, `typecheck`, `typos` and a broken-symlink check before every push. cargo-deny runs in that hook and in no workflow today — a merged pull request is unchecked.

One entry point, `just license`, runs `cargo xtask license check` and `cargo deny check licenses`; the hook and CI both call it, beside the existing `just deny`. The Tests workflow gains a `license` job built from the devenv step shape `check-generated` uses — checkout, install Nix, the devenv cachix cache, `nix profile install` of devenv and just, then `devenv shell -- just license` — not the mise setup `test-linux` uses: devenv is the toolchain everywhere it can be, and mise is reserved for the release builds that must link against system libraries Nix does not ship. The job runs on every pull request and push to `main` like its siblings, and will be a required check once the branch rulesets exist. `check-generated` gains the two lockfiles, the registry and the notices file. `hk.pkl` gains a `license` step globbed on `**/*.{rs,ts,vue,js,mjs,css,toml,nix,typ,nu}`, `**/Cargo.toml`, `Cargo.lock`, `pnpm-lock.yaml`, `.config/deny.toml`, `.config/third-party.toml`, `src/nuxt.config.ts`, `LICENSE`, `docs/licensing/**` running `just license`. `cargo-about` enters `devenv.nix`'s tool set so both `just license` and `just check-generated` find it under devenv, locally and in CI.

Rejected: a separate `license` workflow — one more file for a job that belongs with the others and shares their triggers. Rejected: reusing the test job's mise steps — faster to copy, but a second toolchain for a job that needs nothing mise provides.

### D8 — The flip is the merge; the branch is ordered so every commit is green

The change lands on one branch and reaches `main` as one merge commit. `main` has two states — the Apache-2.0 field with no text, and the whole structure — and no intermediate one in which the manifest, a header, a Nix `meta.license` or `CONTRIBUTING.md` disagree. No contribution is ever accepted under the agreement against a Project License reading Apache-2.0.

Branch order, every commit green under the existing hooks:

1. Texts and documents: `LICENSE`, `docs/licensing/{LICENSE.md,COPYING.exceptions,CLA.md,STEWARD.md,cla-metadata.json}`; the README move and the manifest `readme` pointer.
2. Manifests and metadata: the workspace `license` field, `Tauri.toml` `copyright`, Nix `meta.license`, the `gh-workflow` relabel with upstream's texts, the patch crates' `LICENSE-MIT`, the registry.
3. Headers in one mechanical commit, with the generator emitting them; the overview, the `CONTRIBUTING.md` section, the `AGENTS.md` line, the README paragraph.
4. The validator, `just license`, the hook step, the CI job.
5. cargo-about, notices generation, the committed notices file and its lockstep wiring, the Vite gate, the bundled resource, release-archive inclusion.
6. The merge. Then the agreement's first publication (D9), once its two blanks are filled.

Rules:

- The tree conforms before anything enforces conformance; the validator has no advisory mode.
- Steps 4 and 5 are holder-independent, may be developed in parallel, and are ordered after step 3 when the branch is assembled.
- The agreement's bracketed blanks gate publication, not the merge: the publication check reports an unpublished newer version as pending on pull requests, and `publish` refuses a bracket.
- Until branch rulesets exist, the merge is a local merge the Steward pushes; afterwards, a pull request merging on green. The Tests workflow validates the branch head once a pull request is open.
- No history rewrite. The merge message states that the Apache-2.0 field never reflected the project's license, that no root `LICENSE` existed before this merge (`git log --all` finds none), and that no release was conveyed under the old field.

Rejected: landing the holder-independent work on `main` first and flipping last — it needs an advisory mode, holds back every task that asserts the license, and puts the agreement on `main` before the license it names.

### D9 — Assent is CLA assistant; the Gist is a checked copy of the repository's agreement, written only by `publish`

CLA assistant (`cla-assistant.io`) is configured against the secret Gist `f2903ad9aa3c2eb374faa28ebadab7f6`. It posts a status check and a comment per pull request, keys signatures to GitHub logins per Gist revision, and re-asks signers when the Gist changes — the spec's version-bump re-prompt, delivered by the service.

The repository is the source of truth. The Gist is a copy of `docs/licensing/CLA.md` (as `CLA.md`) and `docs/licensing/cla-metadata.json` (as `metadata`), kept by two halves of one subcommand:

- **Check** (D2 item 6; unauthenticated; every pull request). Identical passes. A newer version not yet published passes on a pull request and fails on `main`. A text change without a version bump fails. A Gist edited anywhere but the repository fails.
- **Write** (`cargo xtask license publish`; the Steward's machine). The same comparison, then both files written with `octocrab`'s gist update builder. Refuses the check's two failing cases and any text containing a bracketed blank.
- **Credential.** None stored. Gists is a GitHub App account permission reachable only with a user access token, so `publish` runs the device flow as the `wp-botswain` App (public client id `Iv23liNfm1Q9EIKSExlK`) and uses the resulting eight-hour token. One-time App setup: Gists account permission at read and write, device flow enabled, the Steward's authorization on first use.
- **Fields** (Appendix F). Full name and email prefilled from GitHub, an "at least eighteen" checkbox, the agreement checkbox; all required. The present age-in-years and employer fields go: one collects more than §3(c) needs, the other promises what the individual agreement cannot deliver.
- **Flags.** The `[⚖ …]` annotations live in Appendix B, never in `CLA.md`, because the Gist is the signable text.

Rejected:

- A workflow running `publish` on `main` pushes — only a user access token reaches Gists, so CI would hold the App's refresh token and rewrite it on every run, for a step taken every few years that the `main` failure already prompts.
- A fine-grained personal token through `secretspec` — works, but is minted, rotated and stored by hand; the device flow stores nothing.
- Pasting by hand with only the check — the write is a dozen lines on the check, and a paste is the one path for a stray edit or a bracketed draft to reach signers.
- The Gist in OpenTofu — no provider resource exists; a provisioner is imperative, blind to drift, and needs the same token.
- A `CLA-Version:` commit trailer — offline-verifiable, but per-commit noise and an untested theory of recorded assent.
- A committed signatures file — service-free, but a first pull request must carry the signature edit, and the configured service does the job.
- The Gist as the only copy — the agreement would be absent from the tree the website renders, and the pledge would quote an external document.

### D10 — The CLA and the permission are repository files; the Steward is a public record

`docs/licensing/CLA.md` and `docs/licensing/COPYING.exceptions` are committed as the texts in Appendices A and B — the agreement without the counsel flags, which stay here (D9), and with its two remaining blanks bracketed until filled — and the CLA's version line is `1.0-draft` until counsel reviews. The long-form prose — the bundle explained, the enforcement-intent statement, the pledge quoting §2.3 of Appendix B verbatim, the header rule, the section on material a contributor does not own (Appendix C), the plugin-boundary note, how assent works — lives in `docs/licensing/README.md`, which renders on the website with the rest of the directory. `CONTRIBUTING.md` carries one or two paragraphs and links to the texts and the overview; licensing prose is written once, where the website publishes it, and the contributor guide defers to it.

The agreement's non-owner pointer resolves to a section of that overview, pinned by the Submission Date, because the instructions reference repository machinery — the registry, the allowlist — that will evolve, and git plus the date fix the version a contributor accepted. `docs/licensing/STEWARD.md` is the public record §7.3 of the agreement calls for: the current Steward, the governing law, and whether a succession designation is in effect and since when — its existence and date, never its private terms. The entity (corporate) agreement is a follow-up. The rollout decision that the agreement needs no "each tier is a separate project" sentence holds while the tree is uniform; that sentence returns with the first permissive crate.

## Risks / Trade-offs

- **The one-off header write assigns a wrong first-authorship year.** → Each file's year comes from the commit that first added it (`git log --diff-filter=A --follow`), so a renamed file keeps its original year; the commit is reviewed as a diff of leading comment lines only, and a sanity pass asserts no year is later than the file's first-commit year.
- **A placeholder holder in headers could be committed by accident.** → The header check fails on `[` in the copyright line.
- **Third-party code lands unregistered.** → A copied file without our tags fails the header check; a vendored crate declaring another license fails the manifest check naming registration as one of the two remedies; a ported portion inside a first-party file is the one case nothing mechanical catches, which is why the overview's non-owner section asks for it in the pull request description and review looks for it.
- **The registry drifts from the tree.** → The validator fails on a registered license off the allowlist or a named text file that does not exist, and the lockstep check fails when the registry changes without the notices being regenerated.
- **`cargo-about` cannot find a license text for some crate and the notices command fails.** → That is the intended failure; a `[[licenses.clarify]]` entry in `deny.toml` (mirrored in `about.toml`) supplies the text. Expected for a handful of crates at first run.
- **The frontend allowlist and `deny.toml` drift.** → The validator's equality check (D2 item 4) fails the pull request.
- **`pnpm licenses list` output shape changes across pnpm versions.** → The notices command parses a narrow subset (name, version, license, path) and fails loudly on a shape change; pnpm is pinned by mise and bumps are reviewed.
- **The one-time header write touches every source file in one commit, colliding with every open workspace.** → Land it when the open stacks are few; rebase conflicts are mechanical (the header is at the top of the file).
- **`tombi` or `oxfmt` reflows a leading comment.** → Neither does today; the header check would catch it, and the format step runs before the check in `hk`.
- **Adding a required check before the branch rulesets exist means nothing enforces it on `main`.** → The `hk` pre-push step enforces it locally meanwhile, as every other check is enforced today.
- **The `license` job needs Rust compiled.** → It shares the build cache the other devenv-based xtask jobs use; `cargo xtask` is already built on that runner.
- **Downstream removes the store permission from forks they publish.** → Permitted by section 7; it only re-creates the conflict for them.
- **Two editions of the license text could drift apart.** → Neither is editable: each is hash-checked against the FSF's published file by the validator (D2 item 5), and `oxfmt` formats Markdown, so the `hk` `license` step runs on `docs/licensing/**` to catch a formatter touching `LICENSE.md` before it is pushed. If the formatter ever does, the file is excluded from formatting, not re-hashed.
- **Publication is forgotten after a version bump, or the Gist is edited by hand, or a trivial edit to `CLA.md` would re-ask every signer.** → The publication check fails on `main` while a bumped version is unpublished, fails on drift, and fails on a text change without a version bump; the remedy in every case is `cargo xtask license publish`, which refuses the unbumped case itself. A whitespace-only edit to the agreement is therefore a deliberate version bump or nothing.
- **`publish` depends on the App's settings and a browser.** → The device flow needs the Gists account permission and the device flow enabled on `wp-botswain` once, and a browser approval per run; a missing permission fails the write with a 403 naming the resource, and there is no stored credential to lapse or leak. The validator's check stays unauthenticated, so CI needs none of this.
- **The publication check needs the network on every pull request.** → It fetches two small files from one Gist; a network failure is reported as such, not as a mismatch, and the hook step runs the same check locally.
- **The Steward is unreachable and no designation exists.** → The agreement's ordered succession chain runs, and if nobody accepts the dual-licensing permissions lapse while every downstream license survives, because each recipient holds it from the original licensors under AGPL section 10. The legal clause is not enough on its own: a successor also needs the accounts, which the Workflow follow-up lists.

## Migration Plan

1. One branch, in the order D8 gives: texts and documents; manifests, metadata and the registry; headers and documentation; the validator and its gates; dependency gates and notices. Each commit green under the existing hooks; the Tests workflow validates the branch head.
2. One merge into `main`, with the message D8 describes.
3. The agreement's first publication to CLA assistant: fill `[SUCCESSION_WINDOW]` and `[FALLBACK_ORGANIZATION]` or drop tier (ii), bump the version, merge, run `cargo xtask license publish`, and sign a test pull request.

Rollback: before the merge, nothing has reached `main` and the branch is simply not merged. After it, a rollback is a revert of the merge commit, never a rewrite; since no release was ever conveyed under either field, nothing downstream depends on the sequence. The Gist keeps its placeholder until the first `publish`, which refuses a bracketed text, so CLA assistant asks nobody to sign a draft.

## Spec decisions

The dated policy decisions behind each new capability, in the form the `storage` main spec carries under its own `## Decisions`. A delta spec's extra sections are not carried into the main spec at archive, so they live here until then; at archive each group is copied into its capability's main spec as a `## Decisions` section.

### `licensing/project-license`

#### 2026-08-28 — AGPL-3.0-or-later for the whole tree

**Decision.** One license, `AGPL-3.0-or-later`, set once in the workspace manifest and inherited by every first-party crate and by the in-repo frontend.

**Rationale.** The sync Station is an accept-only, content-blind network service. Anyone hosting a modified Station has users interacting with it over a network, which is the trigger of AGPLv3 section 13, so the copyleft lands on the one component whose hosted modification is the competitive risk. Static linking makes copyleft whole-binary anyway, so a per-crate split buys nothing. "Or later" gives downstream the same migration option the Steward keeps through the contributor agreement. The frontend is one work with the binary — intimate IPC, single distribution — and licensing it separately would invite ambiguity at the webview boundary.

**Rejected alternatives.**

- _SSPL, BUSL, FSL for the core._ Not open source; forecloses the fork guarantee the project has made in public.
- _LGPL, MPL-2.0 for the core, plain GPL-3.0._ No network clause; a hosted modified Station would owe nothing.
- _`AGPL-3.0-only`._ Denies downstream the later-version option while the Steward keeps a relicensing path.

#### 2026-08-28 — The sync crates are never permissive

**Decision.** `outpost-protocol`, `outpost-fabric`, `outpost-hold` and `outpost` stay under the project license whatever interoperability argument is made.

**Rationale.** The protocol crate is not thin wire types: it is the access-control fold, the key schedule, validation and reconciliation and the full cryptographic suite. Because the Station is content-blind, that crate is the hard majority of a clean-room Station, and a permissive copy would arm a hosted competitor against section 13. Third-party clients remain possible as AGPL clients.

**Rejected alternatives.**

- _A permissive protocol crate for third-party clients._ If proprietary third-party clients ever matter, the surgical answer is a new thin crate holding framing and message types only, never loosening the existing stack.

#### 2026-08-28 — Permissive is a birth policy, never a migration; the layering check lands now

**Decision.** A crate may be born `MIT OR Apache-2.0` only if third parties must link it to interoperate. No existing crate qualifies, so no crate is permissive. The layering check (no copyleft workspace crate in a permissive crate's normal dependency graph) runs from day one and passes vacuously.

**Rationale.** Reversibility. While copyright is consolidated, AGPL to permissive is a free later flip; permissive to AGPL cannot recall shipped versions. The layering check costs nothing while vacuous and is already live when the first permissive crate appears, so that crate cannot be born wrong. The `bedrock` family has no standalone-crate ambition and stays internal.

**Rejected alternatives.**

- _`MIT` alone for a permissive crate._ No patent grant.
- _`Apache-2.0` alone._ GPLv2-incompatible; the dual is the Rust convention.
- _Marking candidate crates permissive now "to be ready"._ Nothing qualifies, and the flip is free later.

#### 2026-08-31 — A true section 7 additional permission for application stores

**Decision.** `COPYING.exceptions` is a genuine AGPLv3 section 7 additional permission, granted to every recipient, forks included, conditioned on a restriction-free source channel for the same version.

**Rationale.** Three genres exist. A non-objection waiver (the `mosh` `COPYING.iOS` lineage, used by Nextcloud iOS) is a personal covenant: it neither travels with the code nor binds a successor cleanly, and the contributor agreement's Project License mechanism needs the permission to be an actual license term so that contributed code can never lose store distributability. An alternative-license conveyance (WireGuard iOS, conveying under MPL-2.0 through the store) splits license identity and fits poorly beside the AGPL server story. The section 7 permission (the Feeel and wger genre) travels with the code, binds successors through the agreement, and costs section 13 nothing — it addresses conveyance-through-stores frictions only. The universal grant is legally cleanest and pledge-consistent; trademark handles store-listing confusion. "Operated by a third party not under your control" plus "terms you cannot individually negotiate" forecloses a construct-your-own-store reading. Crate metadata carries the plain SPDX identifier because no registered SPDX exception exists for store permissions; the permission is strictly broadening, so metadata understates nothing a recipient must know.

**Rejected alternatives.** The waiver and the alternative-license genres, above.

#### 2026-11-03 — Two FSF editions: the plain text at the root, the Markdown under `docs/licensing/`

**Decision.** The root `LICENSE` is the FSF's plain-text edition of AGPLv3, verbatim, the only license file at the root. `docs/licensing/LICENSE.md` is the FSF's Markdown edition of the same text, verbatim. `docs/licensing/` is the browsable home of the licensing material — `LICENSE.md`, `COPYING.exceptions`, `CLA.md`, `cla-metadata.json`, `STEWARD.md`, the `README.md` overview — and is authored to render as pages, because `docs/` is the source of what the website publishes. Both editions are hash-checked against the FSF's published files; neither is a symlink.

**Rationale.** GitHub detects a repository's license with `licensee`, which scores files in the repository root only; its git-backed project keeps symlink entries as blobs and reads the blob at the entry's object id — for a symlink, the target path — so a symlinked root license file is not detected (licensee issues #155 and #227, both closed without a fix; the documented workaround is a real copy), and a project with two root files matching known licenses gets no license at all. So the detected file has to be a regular file at the root, alone. Run locally on 2026-11-03 (`licensee` 9.18.0), the plain-text edition matches AGPL-3.0 at 100% through the exact matcher, while the Markdown edition matches at 99.17% through the similarity matcher against a 98% threshold — detected, but by a margin that depends on the detector's stripping of `#` headings, list markers and emphasis, which regressed once (its issue #435, 2020) before being fixed. The root therefore carries the plain text and keeps the exact match. The website wants the license as a rendered page, and the FSF publishes its own Markdown edition at `https://www.gnu.org/licenses/agpl-3.0.md` (alongside `txt`, `html`, `texi`, `tex`, `rtf` and `dbk`; each is the FSF's own verbatim document), so the rendered copy is also verbatim rather than a conversion; a `.md` file renders where a `.md` symlink to plain text would reflow it. Two copies of one document cost 34 KB and a hash check each, and cannot drift because neither may be edited. The GPL-family convention is `COPYING`; detection accepts either name, and `LICENSE` was preferred for readers who do not know the convention. The section 7 permission works wherever it lives as long as the notices name the path, so it sits with the rest under `docs/licensing/`.

**Rejected alternatives.**

- _One file: the FSF Markdown edition at the root, with `docs/licensing/LICENSE.md` a symlink to it._ Sound: one verbatim document, detected at 99.17%. Rejected only for the margin — the plain text's exact match does not depend on normalisation behaviour.
- _A root `COPYING` or `LICENSE` symlink into `docs/licensing/`._ Not detected; the repository would show no license.
- _Every license file at the root._ Three root files for a flat-root repository, and a second-match risk if `COPYING.exceptions` is ever scored as a license text.
- _`COPYING` as the root name._ Equivalent for detection; `LICENSE` reads better to non-GNU audiences, and `COPYING.exceptions` keeps its name because it names what it is.
- _A third-party Markdown conversion of the text._ Not needed: the FSF's own Markdown edition exists and is verbatim by definition.

#### 2026-11-02 — First-party developer tooling stays under the policy

**Decision.** First-party code under `tooling/` — `xtask`, the `bin/` scripts, `infra/` — carries the project license like every other first-party workspace member. Decided by the Steward on being asked; it is not a default left unexamined.

**Rationale.** Tooling is never conveyed except as part of the source tree, which is under the project license as a whole, so the copyleft on it constrains nobody who builds or runs the application; its only effect is on someone lifting the tooling's code into another project. A permissive tooling tier would also need the layering rule narrowed: `xtask` links `cartograph` and `domain` for typegen, the dev server and the demo territory, so a permissive `xtask` has copyleft workspace crates in its normal dependency graph. Narrowing that rule to crates third parties link is coherent but adds a third classification to the validator for no present need, and the flip from the project license to permissive stays free while copyright is consolidated.

**Rejected alternatives.**

- _A permissive tooling tier (`MIT OR Apache-2.0` for first-party `tooling/`)._ Liftable tooling, at the cost of a third validator classification, per-crate license texts under `tooling/`, and a layering rule scoped to the SDK tier. Available later as a free flip if the tooling is ever worth publishing on its own.
- _Leaving `tooling/` without headers, as a pending surface._ It is not pending; nothing about it awaits a decision now that one has been made.

#### 2026-11-04 — Bundled media defaults to the project license; a short menu for everything else

**Decision.** Any non-code asset bundled into the application binary carries the project license. The contributor agreement lets the Steward place contributed Media under the Project License, `CC-BY-4.0`, `CC-BY-SA-4.0`, `CC0-1.0`, or, for fonts only, the SIL Open Font License 1.1; the Creative Commons options are for documentation and the website.

**Rationale.** An asset compiled into the binary is part of the one work the license covers, and giving it a different license would reintroduce the per-component ambiguity the uniform policy exists to avoid. Documentation and website copy are read, not linked, and the Creative Commons family is what readers and republishers expect there; a font license exists because fonts are the one asset class whose own community licenses expect to be used as-is.

**Rejected alternatives.**

- _Creative Commons for bundled assets._ Splits the binary's license by file type for no one's benefit.
- _No Media list, Project License only._ Leaves documentation under a software license its readers do not recognise.

### `licensing/source-notices`

#### 2026-11-02 — SPDX headers everywhere now; REUSE deferred

**Decision.** Every first-party source file carries an SPDX header; the project does not adopt the REUSE specification (no `LICENSES/` directory, no `REUSE.toml`), and a first-party check stands in for `reuse lint`.

**Rationale.** REUSE's value is machine-checking a mixed-license map. At a uniform policy that value is nil, and SPDX headers alone give scanners what they need. The headers are already REUSE-formatted, so adopting it later is additive — a `LICENSES/` directory and a root `REUSE.toml`, both spec-mandated locations — not a rewrite. The first-party check also verifies something `reuse lint` does not: that each header agrees with its owning manifest and that manifests agree with the policy.

**Rejected alternatives.**

- _Full REUSE now._ Two more root entries for a check that passes vacuously on a uniform tree.
- _REUSE with `.license` sidecars for header-less files._ The same root cost without the config file; only worth it once a second tier exists.

#### 2026-11-02 — The "or later" election lives in the notices

**Decision.** The license texts in the tree are the version 3 text; the grant of "version 3 or (at your option) any later version" is made by the per-file notices and the `-or-later` SPDX identifier.

**Rationale.** The FSF permits verbatim copying of the license text only. Applying it means vendoring the text, writing notices that invoke it, and writing the additional permission as its own file that the notices reference; the license of the Program is the union of the text and the permission, assembled by the notices.

#### 2026-11-02 — Header scope by file type; exemption by path

**Decision.** Header-bearing types are `rs`, `ts`, `vue`, `js`, `mjs`, `css`, `toml`, `nix`, `typ`, `nu`, `sh` and the extensionless scripts under `tooling/bin/`. Data, configuration and document formats (`yaml`, `json`, `xml`, `md`, Kotlin and Swift under the platform projects, OpenTofu, images, fonts, lockfiles, `.d.ts`) carry none. Registered third-party code and platform scaffolding are exempt by path.

**Rationale.** The line is "code the application or its tooling is built from" against "data and configuration". JSON cannot carry a comment; the fifty-odd YAML files are nearly all generated workflows whose first line is already a generator marker and whose linters expect a known shape. A header asserts terms: where the terms are not ours (third-party code) the file carries none, and the check exempts it rather than failing on it. Generators emit the header so regeneration never strips it.

**Rejected alternatives.**

- _Headers in YAML and JSON via REUSE sidecars._ That is REUSE adoption, deferred above.
- _Failing on exempt directories until they are "fixed"._ Third-party code will never be fixed in that sense; the exemption is the correct steady state.

#### 2026-11-04 — Two tags in the initial comment block; the year is first authorship and never changes

**Decision.** A header-bearing file's initial comment block carries at least one `SPDX-FileCopyrightText: <year> <holder>` line and exactly one `SPDX-License-Identifier: AGPL-3.0-or-later` line, after any shebang or tool directive the first line requires. The year is the single year the file was first authored and is never updated; the check requires a four-digit year and does not compare it with the calendar. The holder is John Muchovej; contributors who hold copyright, and the upstream holders of registered ported portions, get their own line. A pointer to the additional permission may follow and is not required.

**Rationale.** "The tags are present and agree" is the whole invariant; a fixed three-line form within a fixed window adds brittleness against directives and multi-holder files without adding meaning. The copyright year records first publication, so updating it yearly is both churn and a misstatement, and a range misstates it twice. The additional permission is a term of the license the identifier names and is spelled out in the full notice at every entry point, so repeating the pointer in every file buys nothing.

**Rejected alternatives.**

- _A mandatory three-line header within the first five lines._ Brittle, and wrong for a file with two holders.
- _Updating the year on edit, or a `first-last` range._ Annual churn across the tree for no legal gain.
- _Requiring the Steward as the only holder._ Contradicts the agreement, under which contributors retain copyright.

### `licensing/third-party-code`

#### 2026-08-28 — Division of labour: cargo-deny, a bundle plugin, cargo-about, and one first-party validator

**Decision.** Dependency allowlisting for Rust is `cargo-deny`'s; for the frontend bundle it is a Vite-side license plugin with the same allowlist; notice generation is `cargo-about` plus the package manager's license listing; the first-party validator checks only what none of those do — manifests against policy, headers against manifests, layering, the license texts against the FSF's, the registry's consistency, the published agreement against the repository's, and that the two allowlists are one.

**Rationale.** Nothing should reimplement `cargo-deny`: it already has expression evaluation, text detection and the clarification machinery, and the tree already carries a tuned configuration. The frontend gate operates on the actual bundle, the legally relevant set, and is package-manager-agnostic. The validator fills the gaps and reports every failure in one run.

**Rejected alternatives.**

- _One tool for everything._ Would reimplement allowlisting badly.
- _Lockfile-only gating for the frontend._ The gate should see what ships; the bundle plugin does, at build time.

#### 2026-11-02 — In-tree third-party code declares its own license

**Decision.** The vendored workflow generator declares `Apache-2.0` itself and carries upstream's `LICENSE` and `NOTICE`; the two patched registry crates carry `LICENSE-MIT`; the validator learns which workspace crates are third-party from the registry.

**Rationale.** The vendored crate inherits the workspace license field today. After the flip that would label another party's Apache-2.0 code as AGPL — false, and a gap against Apache-2.0's notice-preservation condition. Third-party code is not ours to relabel; the compatible-license condition is what lets it be combined with ours, and that is what the check verifies for those crates.

**Rejected alternatives.**

- _Re-vendor with our headers._ Upstream has none, and adding ours would be the same mislabel.
- _Treat the vendored crate as first-party because of the local delta._ The delta is a modification of their work under their license, not a new work.
- _A central `docs/licensing/LICENSE.APACHE` for the vendored crate's license._ Attribution belongs beside the code it covers, and a directory of every third-party license text is what REUSE's `LICENSES/` is for, which is deferred.

#### 2026-11-02 — Notices are generated from the lockfiles and committed

**Decision.** `THIRD-PARTY-NOTICES.md` is generated by one command from the third-party registry, `Cargo.lock` (via `cargo-about`) and `pnpm-lock.yaml` (via the package manager's production license listing), committed, and covered by the generated-file lockstep check.

**Rationale.** Committing generated output and lockstep-checking it is how every other generated file in the repository is kept honest, and it makes a dependency change visible as a notice change in review. A lockfile-derived list may include a package the bundler tree-shook, which costs nothing; it never omits one, which is what the MIT, ISC and BSD notice-preservation conditions care about. The registry supplies what no lockfile can: attribution for code ported into first-party files.

**Rejected alternatives.**

- _Build-time generation from the bundle plugin's bill of materials._ Exact to the shipped byte, but it needs a full frontend build inside the lockstep check and a `cargo-about` run inside the Nix derivation, where registry sources are not laid out as the tool expects.
- _A separate notices file per ecosystem._ Two files to ship and surface for no gain.

#### 2026-11-04 — One registry of in-tree third-party code

**Decision.** `.config/third-party.toml` records every vendored crate, copied file and ported portion with its path, origin, holder, license and license-text files. The header check's exemptions, the manifest check's third-party set and the notices all derive from it; every registered license must be on the allowlist and every named text must exist.

**Rationale.** Three consumers want the same facts, and a lockfile-driven notices generator can never see a routine ported into a first-party file. One data file the Steward edits replaces two constants in the validator and closes the notices gap, and "one list" — the allowlist cargo-deny and the Vite gate already share — extends to in-tree code by construction.

**Rejected alternatives.**

- _Constants in the validator for exempt paths and third-party crates._ Two lists kept in step by hand, and no path from a ported snippet to the notices.
- _REUSE `.license` sidecars as the record._ They mark files, not portions, and REUSE is deferred.

### `licensing/contribution`

#### 2026-08-28 — A contributor license agreement, not a Developer Certificate of Origin

**Decision.** Contributions are accepted under a CLA derived from the Harmony Individual Contributor License Agreement (HA-CLA-I) version 1.0, with its outbound clause rewritten.

**Rationale.** Dual licensing — selling commercial exceptions while the Material stays open — requires relicensing rights that a DCO cannot give: a DCO certifies provenance under the inbound license and grants nothing further. Harmony is a well-understood base with a CC-BY-3.0 text that may be adapted.

**Rejected alternatives.**

- _DCO only._ No relicensing right; forecloses commercial exceptions and any future move to a later or different open license.
- _Copyright assignment._ Takes more from contributors than the project needs and is unenforceable in some jurisdictions.

#### 2026-08-31 — An asymmetric outbound clause, with the grants conditioned on it

**Decision.** Harmony's five mutually exclusive outbound options are replaced by an obligation plus two bounded permissions: perpetual availability under the Project License (a), relicensing only to OSI-approved terms (b), commercial exceptions subordinate to (a) (c), and an express condition (d) that the copyright and patent grants depend on compliance with all three. A contributor may terminate for breach; downstream licenses survive; remedies are cumulative.

**Rationale.** CLA plus AGPL is the power structure that lets a steward sell exceptions, and also the one that let other projects flip to source-available terms. Making the pledge a _condition_ of the grant rather than a covenant means a flip outside (a)–(c) is infringement, not mere breach — the strongest guarantee a solo steward can offer without giving up dual licensing. The Project License is defined to include additional permissions so that contributed code can never lose application-store distributability even if a future Steward stops offering the permission on new code. The Steward's own future code is not bound; the pledge and the enforcement-intent statement speak for that in the Steward's voice.

**Rejected alternatives.**

- _Harmony's option "any license approved by OSI" alone._ Permits dropping the Project License entirely.
- _A covenant not to relicense restrictively._ Breach sounds in contract only; the remedy is damages, not the grant falling away.
- _Promising the pledge beside the agreement rather than quoting it._ Two texts drift; one is the operative one.

#### 2026-11-04 — Assent is recorded by CLA assistant against the repository's agreement

**Decision.** The Steward's CLA-assistant configuration records assent: a status check and comment on each pull request, signatures held per revision of the Gist the service displays, re-signing when the Gist changes. The Gist is a copy of `docs/licensing/CLA.md` and `docs/licensing/cla-metadata.json`, written from the repository by `cargo xtask license publish` on each version bump and never edited independently; the command runs on the Steward's machine, authenticating as the `wp-botswain` App through the device flow with no stored credential, never in CI, and refuses a text with a bracketed blank. The validator compares the Gist with the repository on every pull request, failing on drift, on a text change without a version bump, and on `main` while a bumped version is still unpublished. Signers give full name and email, confirm they are at least eighteen, and confirm agreement; nothing else, and no employer option until the entity agreement exists.

**Rationale.** The service is already configured, is what contributors recognise, and delivers the version-bump re-prompt the spec requires without a line of our code. Keeping the repository as the source of truth turns the Gist into a copy the repository already knows how to keep honest: a check on every pull request, and a write that is the same check plus one builder chain from a client xtask already has. The write stays off CI because Gists is a user-scoped App permission: the installation token the pipeline runs on cannot reach it, only a user access token obtained with the Steward in a browser can, and a step taken once every few years, which the `main` failure reminds the Steward of, needs no stored secret and no automation beyond a command. Refusing an unbumped text change protects signers from being re-asked for an edit nobody can name. The fields follow §3 of the agreement and nothing more; an age in years is more personal data than "at least eighteen" needs, and offering to sign for an employer under an individual agreement would record a signature that binds no employer.

**Rejected alternatives.**

- _A workflow publishing the Gist on pushes to `main`._ Self-maintaining, but only a user access token reaches Gists, so CI would hold a refresh token that rotates on every run, for a copy made every few years.
- _A fine-grained personal token from 1Password._ Works, but is minted and rotated by hand and stored, where the device flow stores nothing.
- _Declaring the Gist in OpenTofu._ No provider resource exists; a provisioner would be imperative and blind to drift.
- _A signed commit trailer naming the agreement version._ Offline-verifiable, but per-commit noise and an untested theory of recorded assent.
- _A committed signatures file with a custom check._ Auditable and service-free, but a first pull request must carry the signature edit, and the configured service already does the job.
- _The Gist as the only copy._ The agreement would be absent from the tree the website renders from, and the overview's pledge would quote a document outside the repository.

#### 2026-11-04 — Licensing prose lives in the overview; the contributor guide defers to it

**Decision.** The long-form licensing prose — the bundle, the enforcement-intent statement, the pledge quoting the agreement, the header rule, the non-owner section, the plugin-boundary note, how assent works — lives in `docs/licensing/README.md`. `CONTRIBUTING.md` carries one or two paragraphs and links to the license texts, the permission, the agreement, the Steward record and the overview.

**Rationale.** `docs/` is what the website publishes, so the overview is written once where it is read most. A contributor guide that restates licensing drifts from the texts it paraphrases; a guide that links cannot.

**Rejected alternatives.**

- _`CONTRIBUTING.md` absorbs everything, for a flat root._ The guide becomes a second licensing document to keep in step with the first.

#### 2026-11-04 — Succession is an ordered chain that ends in lapse, and the Steward is a public record

**Decision.** The agreement's §7.3 is restructured: assignment with written acceptance (a); designation of a successor by written declaration, effective now or on a stated condition such as death, Incapacity or the formation of a named entity, revocable until it takes effect (b); for an individual Steward who dies or suffers Incapacity without an effective designation, an ordered chain — a successor named by the estate, then a named fallback organisation, then any free-software stewardship entity the estate names — each accepting in writing within a window, with a dissolution mirror for a Legal Entity Steward (c); lapse of the relicensing and commercial permissions if nobody accepts, every downstream license surviving (d); and continuity without re-assent (e). `docs/licensing/STEWARD.md` records the current Steward and the existence and date of any designation.

**Rationale.** The chain is a residuary clause in the shape of a will: each tier is tried in order and only the first acceptor takes. The lapse is safe for everyone because of how the AGPL is built — under its section 10 each recipient of the Material is licensed directly by the original licensors, every contributor and the Steward, not by "Us" as an intermediary — so when the Steward disappears without a successor, nobody's existing freedom to use, modify or redistribute depends on a licensor who no longer exists; what disappears is only the dual-licensing optionality in §2.3(b)–(c), the power the agreement was careful to bound. The Legal-Entity mirror is the FLA 2.0 idea and lets the clause survive the Steward's own incorporation without a rewrite. Conditional-effect designation is the operational point: a one-page declaration naming a person "upon my death or Incapacity" can be signed now, and a later one naming "Waypoints, Inc. upon its formation" is the whole legal half of incorporating. The public record lets contributors see that a line of succession exists without publishing its terms.

**Rejected alternatives.**

- _A single blank for "the mechanism"._ Load-bearing for a solo steward and unfillable without a structure to fill it into.
- _Passing the Steward's rights to the estate indefinitely._ An estate is not a steward; the chain gives it a window to name one and then closes the dual-licensing door rather than leaving it ajar.
- _Naming only a generic fallback._ A specific organisation is better insurance if it will accept and worthless if it will not; the clause names one as a bracketed blank until it has been asked.

#### 2026-11-04 — Material the contributor does not own is registered or refused; undirected generation is not a Contribution

**Decision.** A contribution may carry material the contributor does not own only if each portion is identified in the pull request and at its site, is under a license on the compatible allowlist, keeps its own notice, and is recorded in the third-party registry. Code the employer owns needs the entity agreement or a written waiver. Material with no stated license is refused however small. Output an AI system produced without the contributor's creative direction, review and editing is not something the contributor can warrant owning and is not a Contribution; assisted work under direction and review is, and on doubt the contributor describes the process and the Steward decides. The agreement's non-owner pointer resolves to this section of the licensing overview, as in force on the Submission Date.

**Rationale.** The agreement asks contributors to own what they submit; real contributions sometimes carry a ported routine or a specification fixture, and the honest answer is a path for it rather than a prohibition nobody follows. Every rule maps to an invariant the tree already holds: one allowlist, attribution beside the code, the registry feeding the notices, the file's own identifier unchanged. The authorship rule follows from copyright protecting human authorship: the contributor can warrant only what they hold, and the line between assisted and generated is fuzzy enough that a disclosure-on-doubt rule with the Steward deciding is the only version that can be applied consistently; a disclosure gate on every pull request would be unenforceable. The pointer rather than inline text because the instructions name repository machinery that will evolve, and git plus the Submission Date pin what a contributor accepted.

**Rejected alternatives.**

- _Forbidding third-party material in contributions._ Unrealistic, and it would push the material in undeclared.
- _Inlining the instructions in the agreement._ Freezes repository mechanics into a legal text that should change rarely.
- _A mandatory AI-use disclosure gate._ Modelled on a registration requirement, not a merge condition; unenforceable at the fuzzy boundary.

## Appendix C — "Contributions containing material you do not own", for `docs/licensing/README.md`

The section the agreement's non-owner pointer resolves to. The register shifts here — this is the Steward speaking to a contributor — but every rule maps to an invariant the validator or `cargo-deny` already holds.

```markdown
### Contributions containing material you do not own

The contributor agreement asks that you own the copyright in what you submit (CLA §3(b)). Sometimes a contribution has to carry something you do not own: a routine ported from another project, a fixture copied from a specification, a glyph from a licensed icon set, a snippet your employer owns. That is allowed when every such piece can be identified, is under terms this tree already accepts, and keeps its own notice. Concretely:

1. **Say so, in the pull request and at the site.** The pull request description lists each third-party portion: what it is, where it came from (URL and commit or version), who holds the copyright, and its license. In the file, the portion is bracketed by a comment saying the same — `Portions derived from <project> (<URL>, <commit>), Copyright (c) <year> <holder>, licensed <SPDX-ID>` — and the file gains an `SPDX-FileCopyrightText` line for that holder beneath the Steward's.

2. **The license must already be on the allowlist.** The identifiers `.config/deny.toml` accepts for dependencies are the identifiers accepted for in-tree third-party code. There is one list. Anything else — including "no license stated", which is the common case for snippets found in the wild — is not acceptable, however small the portion. If you are unsure, ask in an issue before writing the code.

3. **The notice travels with the code.** For MIT, BSD, ISC and other short licenses, the full license text goes in the comment block beside the portion. For longer texts (Apache-2.0 with its NOTICE, MPL-2.0), the text goes in a `LICENSE-<name>` file in the owning crate or package directory, the way `tooling/patches/` carries `LICENSE-MIT`. Either way, record the portion in `.config/third-party.toml` so that it appears in `THIRD-PARTY-NOTICES.md` and the license check knows about it.

4. **The file's license does not change.** A file combining a compatible third-party portion with first-party code stays under the project license and its `SPDX-License-Identifier` is unchanged; the portion remains under its own terms, which the notice preserves. A file copied wholesale from elsewhere is different: it keeps its own identifier, is listed as third-party code in `.config/third-party.toml`, and is exempt from the header check for that reason — the `tooling/gh-workflow` pattern.

5. **Modified weak-copyleft files stay under their license.** A file under MPL-2.0 or another file-scoped copyleft that you modify stays under that license, keeps its original header, and notes the modification. The license requires this; we only enforce it.

6. **Code your employer owns** needs either the Entity version of the agreement signed by your employer (a known follow-up — until it exists, ask) or a written waiver from your employer attached to the pull request.

7. **Material with no human author is not yours to contribute.** You grant rights only in what you hold copyright in, and copyright protects human authorship. Output an AI system produced without your creative direction, review and editing is not something you own, so it is not something CLA §3(b) lets you warrant. Using coding assistants under your direction, with your review and your edits, is fine — it is how the Steward works. Wholesale generation submitted unread is not. If you are unsure whether what you did meets the bar, describe your process in the pull request and the Steward will decide.

8. **If none of the above fits, it is not a Contribution.** Say "Not a Contribution" in the pull request (CLA §1) and it will not be merged.
```
