## Goals / Non-Goals

**Goals:**

- One declarative file names every workspace crate; one planner mints every group's version at the app's cut; every version claim is checked before it reaches history.
- The bump for every group is `max(declared, evidence)`, and the tests that prove it simulate a `1.x` base so pre-1.0 right-shifting cannot hide a severity bug.
- Every write botswain makes to `main` or a series branch lands through a pull request gated by the same required checks as a person's, merges unattended when they pass, and leaves every tag pointing at a commit the planners' first-parent walk contains.
- Everything is derivable: the schema from the parser, the workflows from `xtask`, the bill of materials from tags, the group of a path from the group file.

**Non-Goals (design-level, beyond the proposal's):**

- No change to how a pull request's _branch_ commits are written; only the merge message is checked.
- No second source of versions: no ledger file, no version field in the group file, no version in any Tauri config.
- No new checker for behaviour. API breaks come from `cargo semver-checks`; data breaks come from fixtures; everything else is a declaration.
- No new conventional-commit type where an established one serves. The bookkeeping marker stays `chore(release):` (D3).
- No new GitHub transport. Every API call `xtask` makes goes through `tools::github` and the `octocrab` client it already carries; generated steps stay one-line `cargo xtask` dispatches (D13).
- No cooling-off window before a bot pull request merges. The required checks are the gate (D13).
- No private crate registry. Channels pin libraries by git tag; Kellnr, or a static sparse registry on R2, is a later change that publishes from the same tags (D18).
- No library prereleases, and so no library `promote`. A group is cut to a plain version or not at all (D3).
- No pushing of Nix outputs to a binary cache. That is its own follow-up, and D18 records only what it would cache.

## Decisions

D1–D12 were settled on 2026-10-11. D13–D17 answer what the tree showed when this change was planned, and D18 (2026-10-26) settles how channels consume the libraries; each of D13–D18 needs sign-off (**AUDIT**).

### D1 (2026-10-11): One declarative file names every crate; versions live only in manifests

- **Why:** release-please's useful idea is a declarative group table. Keeping versions out of it means the file never takes bookkeeping commits, and the manifest stays the sole version source, as `distribution/release-planning` requires.
- **Location:** `tooling/release-groups.toml`; shape in the Appendix. Its parser is a library module beside the version reading, `releases/groups.rs`, since the group file is what the release tasks key on.
- **Groups:** `bedrock`, `outpost`, `domain`, and `waypoints`. `domain` is its own group because its data structures are the core of the data covenant.
- **The app:** `src-tauri` and `cartograph` are versioned members, since `cartograph` is the API surface. `store` and `importer` are unversioned internals: their `version` fields go, as `xtask`'s already has. Transload will eventually replace `importer`, and `store` may fold into `cartograph`; both are out of scope.
- **Exhaustive, by one rule** (revised 2026-10-24): a workspace member is in the file's scope if and only if its manifest is not under `tooling/`. Every in-scope member is named as a versioned member or an internal of exactly one group; an out-of-scope member is never named, and naming one is an error, so the file cannot drift into listing what it does not govern. There is no `ungrouped` list: `tooling/xtask` and `tooling/gh-workflow` are excluded by where they live, not by an entry. The working copy's `crates/importer-sdk` and three `plugins/importer-*` crates are in scope the day they are committed and must be placed in a group then — which group is that commit's decision, not this one's — or every planner run refuses. That refusal is the point: `crates/transload` cannot arrive unnamed either.
- **Rejected:** a version ledger like `.release-please-manifest.json` (a second source of truth); groups hard-coded in Rust (drifts silently from workspace members).
- **Gate:** an unnamed or doubly named crate makes the planner refuse; the file validates against its schema (D11).

### D2 (2026-10-11): Extend xtask; adopt neither release-please nor release-plz

- **Why:** release-please releases by merging a PR on one target branch. It does not model cut → `-pre.N` → promote across `v{minor}.x`, and its Rust strategy [fails on virtual workspaces](https://github.com/Gitlawb/node/issues/130). release-plz ([config](https://release-plz.dev/docs/config)) is closer and uses the same `next_version` crate, but its `version_group` bumps only members that changed or depend on a change, and `bedrock-derive` depends on no workspace crate, so it would drift.
- **Borrowed, not adopted:** release-please's release PR (D3) and its multiple-changes-per-commit bodies (D5) are kept as conventions inside `xtask`.
- **Consequence:** `.config/release-plz.toml`, which nothing references, goes with this decision.
- **Rejected:** release-please for all groups; release-plz for libraries only.
- **Gate:** none; this is a scoping decision.

### D3 (2026-10-11, revised 2026-10-19): Library versions are minted by the cut, in one summary commit through a pull request

- **Why:** with `publish = false` and no channels, a library release between app cuts has no reader. Minting at cut gives each app release a coherent bill of materials and keeps library bookkeeping inside a transition the planners already handle.
- **Sequence:** (1) `release-plan cut` computes each library group's next version; (2) botswain opens a pull request to `main` with one summary commit carrying every `main`-side write of the cut — each changed group's manifests and `main`'s provisional `{next minor}-nightly` bump — and enables auto-merge; (3) the required checks run and it lands as a merge commit; (4) the pull request's merge event triggers the second phase, which reads the landed summary's per-group headers, tags each named group at the merge commit, and cuts `v{minor}.x` from it; (5) the app version is written on the series branch the same way: a botswain pull request to the branch, gated by the same checks, landed as a merge commit, then tagged. Advance, promote, and patch follow (5).
- **Tags go on the merge commit.** `main`'s first-parent history contains the merge commit, not the PR branch's commit, so a tag made before the merge would name a commit the planners never walk.
- **The commit:** subject `summary: cut 0.3.0-pre.1`; body one `chore(release): <group> <version>` header per changed group, plus one for `main`'s own bump. One commit over every changed manifest, which the Contents API `update_file` cannot make — it writes one file per commit — so the write goes through the call D13 names. The body is what phase two reads, so the commit describes its own consequences.
- **The bookkeeping marker is `chore(release):`, not a new type** (revised 2026-10-19). An earlier draft of this decision reserved a `release` _type_; the tree settled the question first. Every planner message is `chore(release): …` after the first cut minted its tag and then failed to draft release notes under `require_conventional`, `.config/cliff.toml` already skips `^chore\(release\):`, CONTRIBUTING already documents `release` as a special scope, and a test holds the planner to the prefix. Reusing it means no new type in CONTRIBUTING, no new cliff skip for the headers, and a bookkeeping filter that matches the commits already in history.
- **Tokens:** every pull request botswain opens, and the merge that lands it, uses the App token, as `devenv-update` already does — a pull request opened with `GITHUB_TOKEN` raises no `pull_request` event, so its required checks would never run and it could never merge. The same token mints the tags and branches, which is what the published requirement _Release refs are minted so their pushes are observable_ demands. `release-plan`'s token gains `pull-requests: write`.
- **A group can be cut on its own** (added 2026-10-26). `release-plan cut --group <name>` runs the same first phase for one group — one summary commit, one `chore(release): <group> <version>` header — and phase two tags it at the merge commit. It creates no branch, moves no other version, and raises no release workflow, because only bare `v…` tags trigger anything. Groups follow semantic versioning as Cargo reads it: `0.x` right-shifts, and from `1.0` the bump is major, minor, or patch straight from the commits and the evidence; `--bump major|minor|patch` is a floor that can only raise it, mirroring the app's `--major`. There is no library `promote`: libraries carry no `-pre.N` — they have no installed population to stage a candidate for, nightly is already their integration channel, and `cargo semver-checks` and the right-shift both assume plain versions. The tag template leaves the door open if that ever changes. A group cut with nothing counted refuses.
- **Backports never re-mint.** Builds describe library versions from tags (D12), so a backport reports `bedrock-v0.4.0-2-g…`.
- **Rejected:** a ruleset bypass pushing straight to `main` (`main` is protected); releasing libraries on merge (bookkeeping at random times wakes nightlies); minting at promote (libraries live on `main`); tagging from the first phase (names a commit outside first-parent history).
- **Gate:** `release-plan cut --dry-run` prints every group's current and next version and the pull request it would open; a scratch-repository run shows one landed summary merge, its tags, and the branch cut from it.

### D4 (2026-10-11): Groups own disjoint paths; the app counts what it ships

- **Why:** paths cannot misreport, while scopes are optional and unchecked.
- **Ownership:** each library group owns its members' directories. `waypoints` owns everything else except `tooling/` and bookkeeping: `src-tauri`, `cartograph`, its internals, and the frontend. The mapping reuses the longest-prefix rule `planners::test::owning_package` already applies, extended from crates to groups.
- **Counting:** a library counts commits touching its own paths. The app counts its own paths plus every group's, because the binary ships them; a `fix(bedrock)` is a user-facing fix.
- **Walk:** first-parent, with each merge diffed against its first parent, so a pull request is one commit with the merge message. `releases::index::product_commits` is the one walk both planners read, so the nightly planner becomes first-parent too; its decision — did anything land — is unchanged, since a landed pull request is still one commit.
- **History the walk needs:** full, as the planner jobs already check out. Attributing by path makes that requirement sharper rather than new — a shallow tip is a root commit diffed against the empty tree, so every path would look changed — and `planners_check_out_the_history_they_walk` keeps covering it.
- **Bookkeeping:** `nix/releases/`, commits listed in `.git-blame-ignore-revs`, and botswain's `chore(release):` commits count toward no group. The index exclusion is the `PRODUCT_PATHSPEC` already in place; the other two extend it, and the third already matches every planner message in history (D3).
- **Rejected:** scope-based attribution.
- **Gate:** tests on the existing `index::fixture::Repo`, grown to make merges and body-carrying commits: a `bedrock-core`-only commit counts for `bedrock` and `waypoints` only; a tooling-only, ignored-rev, or `chore(release):` commit counts for none; a three-commit pull request counts once.

### D5 (2026-10-11, revised 2026-10-19): A commit touching more than one group is a summary

- **Why:** one header, many groups. Rather than parse multi-scope subjects, a multi-group commit's subject summarizes, and its body carries one header per touched group. This is the convention release-please uses for [multiple changes in one commit](https://github.com/googleapis/release-please#what-if-my-pr-contains-multiple-fixes-or-features).
- **Format:** subject type `summary` (reserved for this). Body headers are scoped by group name, such as `feat(bedrock)!: rename Filter::eq` and `refactor(outpost): follow the rename`. Within a summary a library header declares its break with `!`; a `BREAKING CHANGE:` footer belongs to a single-group commit, where the subject is the only header.
- **Where it lives:** the merge commit. The repository setting makes its message the PR title and description, so the title is the subject and the description carries the per-group headers and any `Covenant: break` trailer. Branch commits underneath are never read by a planner or checked by the gate; `--first-parent` skips them, and the PR's diff is the merge commit's diff against its first parent. They stay conventional all the same, for the reason D15 gives.
- **That setting is not a ruleset rule, and it is wrong today** (added 2026-10-19). `merge_commit_message` is `BLANK`, so a merge commit currently carries a title and no body — under which every per-group header and every `Covenant: break` trailer would vanish at the moment of landing, and attribution and severity would read an empty body. This change sets it to the pull request's body; nothing in a ruleset would have caught it (D17).
- **Single-group commits** keep free-form scopes; the path decides the group. CONTRIBUTING's comma-joined regions stay legal only while every region falls in one group — `refactor(app,store): …` is one `waypoints` commit; `refactor(domain,cartograph): …` must be a summary.
- **Severity:** each group reads its own header; the subject counts for no group. A `!` in a library's header breaks that library; `!` never breaks the app (D6). The app's declared type is the highest among the commit's headers.
- **Library rules:** Cargo's 0.x right-shift (feat → patch, break → minor), which `next_version`'s defaults and cargo-semver-checks both assume.
- **Rejected:** multi-scope subjects such as `feat(bedrock,outpost)!:`; an unscoped `!` applying to every touched group.
- **Gate:** tests for a two-header summary, a summary missing a touched group (refused at PR), a summary naming an untouched group (refused at PR), and a single-group commit with a free-form scope; and a landed pull request whose merge commit carries its description verbatim.

### D6 (2026-10-11): The app's only breaking signal is a `Covenant: break` trailer

- **Why:** the app's contract is the data covenant (continuity, egress, interop), not Rust APIs. A wire-protocol break is an interop break, so it needs the trailer even though the code lives in `outpost`.
- **Reading it:** the walk reads trailers (`%(trailers:key=Covenant,valueonly)`), not only `%s`. The trailer applies to the whole commit, summaries included.
- **Severity:** feat → minor even in 0.x, unchanged. Before 1.0 a trailer still yields a minor, but it is recorded, and each one is an entry in the covenant exemption log that `git log --grep` can answer.
- **App majors are human-triggered.** A major for `waypoints` is a product decision, which no commit can prove. The cut targets a major for the app only when a person passes `release-plan cut --major` — a flag beside `--dry-run` on the CLI's `Options`. The trailer is the floor, not the trigger: a `Covenant: break` since the last stable makes a cut without `--major` refuse, naming the commits, rather than cut a silent minor or an unreviewed major. `--major` without a trailer is allowed. Library majors stay automatic, since their contract is a Rust API the checkers can see.
- **`cartograph` API breaks never floor the app.** cargo-semver-checks on `cartograph` runs against the last `v*` tag as PR information only; its sole consumers are `src-tauri` and the frontend, in lockstep, so an API break there is internal.
- **The `!` already in history stays meaningful to its own group.** `feat(outpost)!: deployable Station` and its siblings break `outpost` under D5 while leaving the app's version to the trailer, which is exactly the split this decision wants.
- **Rejected:** honouring `!` or `BREAKING CHANGE:` for the app.
- **Gate:** tests on a simulated `1.2.0` base: `feat!:` without the trailer targets `1.3.0`; a commit with the trailer makes `cut` refuse and `cut --major` target `2.0.0`; `cut --major` with no trailer also targets `2.0.0`.

### D7 (2026-10-11): Severity is the greater of declared and detected

- **Why:** a floor stops a mislabeled commit from producing a wrong version; the PR check stops it from reaching history.
- **API floor:** `cargo semver-checks --baseline-rev <group tag>` for each library-target member of `bedrock`, `outpost`, and `domain`. The proc-macro `bedrock-derive` is declared-only. The tool joins the toolchain through `devenv.nix` like every other tool, projected to the `xtask` mise lane.
- **Fixture floor:** a modified, deleted, or renamed file under `covenant/fixtures/<group>/` since the last stable tag is breaking for that group and for the app (D8).
- **PR asymmetry:** an undeclared break fails; an over-declared break passes, since behaviour changes and macro output escape the checkers.
- **Rejected:** evidence alone (misses semantic breaks); messages alone.
- **Gate:** fixture-repository tests where evidence exceeds the declaration, at PR time and at cut.

### D8 (2026-10-11): Covenant fixtures are append-only and owned by a group

- **Layout:** `covenant/fixtures/<group>/`: `domain` (data structures), `outpost` (envelope and ACL records), `bedrock` (storage format), `waypoints` (migrations). A change under a group's directory floors that group and the app.
- **Why append-only:** modifying, deleting, or renaming a fixture changes what old data means. A path rule cannot be defeated by a message-format change, the same reasoning that put the index exclusion in the planners' walk.
- **Fixtures are data, not tests.** `covenant/fixtures/` is a repo-root corpus of frozen inputs; the tests that read them are ordinary `cargo test` cases in the owning crate. What a test cannot do is notice its own fixture being rewritten; the path rule covers that, at PR time (append-only unless `Covenant: break`) and at cut (the fixture floor).
- **Formatting never stands alone.** A formatter's changes amend the commit they belong to, with botswain as co-author. Treewide passes are listed in `.git-blame-ignore-revs` and excluded from planning. Fixtures are excluded from treefmt, since an amended reformat would trip the append-only check.
- **Scope here:** the directories, the rule, the trailer, and the floors. Coverage is a follow-up change.
- **Gate:** PR-check tests for add (pass), modify without trailer (fail), and modify with trailer (pass); treefmt leaves a fixture untouched.

### D9 (2026-10-11): Only botswain writes versions, and group members are lockstep

- **Why:** if people or agents edit versions, the planner's output stops being the record.
- **Checks:** a diff to any versioned member's `[package].version` by an author other than `wp-botswain[bot]` fails; every member must equal its anchor.
- **App lockstep:** `cartograph` follows `src-tauri`, so every app transition writes both in one commit, with the same mechanism as D3. On `main` that means `cartograph` carries the same `-nightly` prerelease the app manifest does.
- **A mirrored version is not a channel declaration.** The published requirement _The manifest version names the channel_ ends `No other file SHALL declare a channel`, which a lockstep `cartograph` would read as violating. It does not: the app manifest stays the only version anything consults, and a group member mirrors its anchor without being read. D16 modifies the requirement to say so rather than leaving the contradiction implicit.
- **Gate:** PR-check tests for both; the app-version test in `workspace.rs` stays.

### D10 (2026-10-11, reversed 2026-10-27): A channel's build may differ at compile time, because every channel's release is a fresh build tested under its own flavor

- **The original rule, and why it was wrong.** As first decided, flavor features were to carry identity only, because `promote` rebuilds the release with `--features stable` in place of `--features preview`, and anything `cfg`-gated on a flavor would ship in a combination no preview user had run. That concern was real but answered the wrong way: three channels are three builds, and a promotion is a fresh build with a fresh release-suite run exactly as an advance or a patch is. The shipped combination is untested only if the suite runs under a flavor other than the build's — which is a gap in the pipeline, not a reason to forbid the difference.
- **Why the difference is wanted.** Some of what distinguishes a channel must be built in rather than toggled. The canonical case is telemetry: once Sentry is integrated, nightly should emit the most, preview less, stable the most privacy-preserving — fidelity inversely related to stability, because the less stable the build, the more data isolating a failure takes. A runtime toggle is by definition disableable, and so unreliable exactly where the data matters most; a compile-time gate is the honest expression of "this channel always does this."
- **What makes it safe:** (1) the release test suite runs under the flavor the builds enable, on every crate that declares one, so a flavor-gated path is exercised by the gate that ships it (task 7.3); (2) flavors are mutually exclusive by meaning but Cargo features are additive, and feature unification can quietly enable two on a shared crate — so every crate that declares a shipped flavor declares all three and carries a `compile_error!` on any two together, and a release build enables exactly one; `development` is not among them — it is the additive test-time flavor the dev-dependencies already unify into every test build, allowed beside a channel flavor and forbidden from overriding one (D14); (3) the flavor set is closed to what `Flavor` in `channel.rs` names, and `src-tauri` forwards each flavor to every crate that declares it (D14).
- **Identity is still the Tauri config's.** Bundle id, updater endpoint, data directory, icon, and product name come from `configs/flavors/<flavor>.toml`, `WAYPOINTS_FLAVOR`, `VITE_WAYPOINTS_FLAVOR`, and the Gradle resources, and nothing here moves them into Rust. `BuildInfo.channel` stays the runtime reading for anything that only needs to _know_ the channel.
- **State of the tree (2026-10-23):** no Rust code reads a flavor yet. The forwarded `store` features are empty, `domain`'s are declared and unforwarded, and `development → store/development → store/mock` is the one chain with content, which never ships. So this change lands the rules and the guard, not a migration.
- **Rejected:** runtime-only branching on `BuildInfo.channel`, which cannot express a non-disableable difference; the flat ban, which would have made the telemetry case a redesign later.
- **Gate:** the release suite runs with the flavor; `cargo check` with two flavors fails naming the conflict; the D14 lint passes on the tree.

### D11 (2026-10-11): The group file's schema is generated from the parser and committed

- **Why:** tombi lints TOML against JSON Schema, bound by an in-file `#:schema` directive or a `[[schemas]]` entry ([tombi docs](https://tombi-toml.github.io/tombi/docs/json-schema/)). Generating the schema from the parser's types means the two cannot drift.
- **Shape:** the config types in `releases/groups.rs` derive `schemars::JsonSchema`; `cargo xtask release-groups schema` writes `tooling/schemas/release-groups.schema.json`. Doc comments become hover text, and enums (severity, minting) become closed sets.
- **Binding:** an in-file directive, `#:schema ./schemas/release-groups.schema.json`, the Tauri-config precedent. Tombi resolves a relative path against the TOML file's own directory, so the path is stable wherever the lint runs from. The file is hand-maintained, so the binding belongs with it rather than in `.config/tombi.toml`, which binds schemas only to hand-edited mise configs.
- **Split of duties:** the schema checks shape; `xtask` checks semantics (every crate named, paths disjoint, paths exist).
- **Gate:** a test regenerates the schema and compares it with the committed file; `tombi lint` fails on a misspelled key.

### D12 (2026-10-11): Builds embed every group's version alongside `BuildInfo`

- **Why:** a bug report should name the `bedrock`, `outpost`, `domain`, and app versions it ran, not only the app's.
- **Shape:** a structure carried alongside `BuildInfo`, baked by `src-tauri/build.rs`: each group's name and `git describe --tags --match '<group tag prefix>*'`. Workspace groups only; third-party dependencies are out. It is registered with typegen like `BuildInfo`, so the bindings stay generated, and `--version` prints it.
- **Without tags:** shallow CI checkouts and Nix sources carry no tags, so `build.rs` takes injected values first, as it already does for `GITHUB_SHA`. When neither is available — a shallow local clone — it reports the anchor manifest's declared version, so a development build never fails to compile for want of a tag and never claims more than the manifest says.
- **Nix:** the overlay builds a fetched tag carrying no git metadata, so it injects each group's version read from the tree's anchor manifests with `builtins.fromTOML`, as `nix/channel.nix` already reads the app's. That reader takes strict TOML 1.0 and only `src-tauri/Cargo.toml` pins that dialect today, so each library anchor gains the same `#:tombi toml-version = "v1.0.0"` directive before the overlay can read it.
- **Gate:** a build at `bedrock-v0.4.0` reports it; a backport reports `bedrock-v0.4.0-N-g<sha>`; a Nix build reports injected values.

### D13 (2026-10-17, revised 2026-10-23 — AUDIT): Every botswain write to a protected branch is one signed commit, a pull request, and auto-merge, all made through `tools::github`

- **Why:** D3 routes the cut's writes through pull requests because `main` is protected. The release index is a second direct write to `main`, through the same `update_file`, whose own `TODO` leaves the protected-branch case to whoever protects the branch. Protecting `main` without routing that write would break every nightly's index entry.
- **Shape:** `tools/github.rs` is already the one module that talks to GitHub, through `octocrab`, and its doc states the rule this change follows — a typed request and a typed answer, no `gh` argument formatting. It gains three calls, and `update_file` loses its last planner caller: `commit_files(branch, files, message)`, one commit over several files through the GraphQL `createCommitOnBranch` mutation, which GitHub signs — the same call `create-pull-request`'s `sign-commits` makes, and the reason it arrives verified where a REST Git Data commit would not; `open_pull_request(head, base, title, body)`; and `enable_auto_merge(number)`, the `enablePullRequestAutoMerge` mutation. A bot write is then: the planner computes the files, commits them on a `botswain/<purpose>` branch, opens the pull request, enables auto-merge, and GitHub lands it when the checks pass. Tags stay with `create_tag`. Every generated step stays a one-line `cargo xtask` dispatch, as the workflow tests already hold the store-touching steps to.
- **Why not the `create-pull-request` action, which an earlier draft of this decision chose.** That draft rested on `xtask` having no GitHub client, so that any Rust path meant a new dependency reimplementing a pinned action's main feature. The tree settled it the other way: `octocrab` is in, the Contents and Refs calls already go through it, and `releases/store.rs` states the house rule — shell out only where no Rust API exists, and keep every workflow step a bare `xtask` dispatch. Under that rule the action is the exception, kept for `devenv-update` because its write is a tree diff left by `devenv update` rather than a value the planner computed. The planners' writes _are_ computed values, so routing them through the working tree, an action, and a `gh` call would split one write across three mechanisms to avoid one GraphQL call in a module built for exactly that.
- **Merging is unattended, with no waiting period** (decided 2026-10-19). A bot pull request merges as soon as its required checks pass; the checks are the whole gate, and nobody watches for a release index entry to land. GitHub has no time-delay rule of any kind, so a cooling-off window would have to be a scheduled merger of our own — machinery that buys a veto window nobody asked to use. The consequence is accepted and stated plainly: with zero required approvals, the check set is the only thing between a bot pull request and `main`, which is what makes `version-integrity` a required check rather than an advisory one.
- **Prerequisite:** the repository has `allow_auto_merge` off, so the mutation fails today. D17 turns it on.
- **Branches, not checkouts:** `createCommitOnBranch` takes the branch and its expected head oid, so the planner needs no checkout of the branch it writes — `advance`, `promote`, and `patch` write the series branch from `main`'s checkout exactly as `write_version` does today, and `release-index` writes `main` from the tag's. The earlier draft's wrinkle about checking the target branch out dissolves.
- **Cost:** one pull request per nightly for the index, merged on green after a test run that `test-plan` scopes to nothing (an index-only diff touches no crate).
- **Rejected:** a ruleset bypass actor for the App — rejected for the cut in D3 on the same grounds, and a bypass cannot be scoped to `nix/releases/`, so granting it for the index grants it for everything. A REST Git Data API sequence (blobs → tree → commit → ref): four calls to one, and unsigned without a hand-rolled signature. The `create-pull-request` action, per above. A scheduled cooling-off merger, per above.
- **Gate:** `release-index --dry-run` prints the entry and names the branch and title it would open; `tools/github.rs` tests cover the mutation payloads against recorded fixtures; the first nightly after landing records its entry through a pull request that merged itself, and the quiet-repository skip still holds the next day.

### D14 (2026-10-17, reversed 2026-10-27 — AUDIT): The flavor lint keeps the set closed and exclusive, not absent

- **Why:** under D10 as reversed, a flavor `cfg` is legitimate, so a lint that forbids them would forbid the point. What can still go wrong is structural: a flavor name nothing declares (`beta`), a crate that gates on `stable` but never declares `preview` so `--features preview` fails to resolve on it, a crate that gates on a flavor `src-tauri` does not forward to it, and — the one that bites silently — feature unification enabling two flavors on a shared crate, since Cargo features are additive and flavors are not.
- **Nobody passes two flags; the graph does.** Features on a dependency are the union of what every path to it asks for, and the release suite runs `cargo nextest run --workspace`, which compiles every member's test targets whatever the filterset later selects. So under `--features stable` a crate reached by a second path that names `preview` carries both, from two dependency lines neither author sees together. Empty features make it harmless today; the day `stable` gates telemetry, the suite exercises a crate carrying both paths and passes. That is an error in a dependency declaration, which no generated workflow controls, surfacing in a crate nobody touched — exactly what a `compile_error!` turns from undetectable into a failed build.
- **`development` is not a channel, and is additive by rule.** The tree already unifies it into every test build: `cartograph` and `store` each enable `development` on themselves through their own dev-dependencies (`cartograph` on itself and on `store` with `development, test-utils`; `store` on itself the same way), and `tooling/xtask` enables it on `cartograph` besides. That is correct — it is what turns the mocks on for tests — and it means a guard treating `development` as exclusive with a channel flavor would make the release suite unbuildable under every channel. So exclusivity holds among the three _shipped_ flavors only, and `development` has a different rule: it may add (mocks, test utilities), never override a channel gate — no `cfg(not(feature = "development"))` around a channel path, and no `cfg(all(feature = "development", …))` that selects behaviour a channel otherwise owns. It never reaches an artifact, because `xtauri build` compiles `src-tauri` alone, without dev-dependencies; the suite tests each channel's behaviour with the mocks beside it, which is the point of the mocks.
- **The release suite still builds nothing under `tooling/`**, by the group file's scope rule: those crates ship in nothing, gate no release, and their test targets are compile time spent for no verdict. Not a correctness fix — `development` is allowed in the suite now — but the same boundary as everywhere else in this change.
- **Shape:** a test in `xtask` walks `crates/` and `src-tauri/src/` for `cfg(feature = …)`, `cfg!(feature = …)`, and `cfg_attr(feature = …)` and asserts: every flavor-looking name is one `Flavor` in `channel.rs` declares; every crate declaring any shipped flavor declares all three; every such crate carries a `compile_error!` on any two shipped flavors together; `src-tauri` forwards each flavor to every crate that declares it; and `development` only adds — no `cfg(not(feature = "development"))` and no `cfg(all(feature = "development", …))` on a path a shipped flavor gates. `Flavor::Development`'s chain to `store/mock` stays the declared-but-unshipped flavor, outside the exclusivity and inside the additive rule.
- **Rejected:** removing the feature declarations (`xtauri` passes `--features {flavor}` and cargo must accept it); a flat ban on flavor `cfg`s, per D10; a runtime assertion instead of `compile_error!`, which would surface a doubled flavor only when the doubled code ran.
- **Gate:** the test passes on the tree, fails on an injected `#[cfg(feature = "beta")]`, and fails on a crate declaring `stable` without the guard; `cargo check` with two flavors enabled on `src-tauri` fails naming the conflict.

### D15 (2026-10-17, proposed — AUDIT): Release notes keep reading branch commits; summary-aware notes are a follow-up

- **Why:** `git-cliff --latest` renders the release notes, with `require_conventional = true` and merge commits filtered out of the body. Under D5 the merge commit carries the summary and the branch commits beneath it are read by neither planner nor gate — so they could in principle go free-form, and then the notes step would fail on the first unconventional one, which is how the first cut lost its draft. Pointing git-cliff at merge commits instead would duplicate every conventional branch commit under its merge.
- **Shape:** one `commit_parsers` entry skipping `^summary:`, beside the `^chore\(release\):` skip already there. The per-group headers live in a body, which cliff does not parse as subjects, so they need no entry of their own. Branch commits stay conventional per CONTRIBUTING, which the notes already depend on; the PR gate does not check them.
- **Rejected:** teaching git-cliff to walk first-parent and expand summary bodies — the right end state, but it is release-notes work with its own design, and nothing here depends on it.
- **Gate:** `git-cliff --latest` renders notes for a merge-landed pull request whose branch commits are conventional, and renders no entry for a `summary:` merge commit.

### D16 (2026-10-19, proposed — AUDIT): Two published requirements are modified rather than worked around

Protecting the branches contradicts two requirements `nix-release-index` published, so this change amends them instead of bending around them.

- **_A series branch carries only cherry-picks of `main`_** admits "the planner's version commits and cherry-picks of commits already on `main`", and nothing else. Landing a version commit through a pull request adds a merge commit, a third kind. The requirement is modified to allow the planner's version commit to arrive as the merge commit of a bot pull request, which is what protection forces; its purpose — that no change originates on a series branch, so a tagged tree is self-sufficient — is unchanged and restated.
- **_The manifest version names the channel_** ends `No other file SHALL declare a channel`, which a lockstep `cartograph` version carrying `-nightly` would appear to violate (D9). The requirement is modified to say that a versioned group member mirrors its anchor and is never read as a version or channel source, so the app manifest remains the only one consulted.
- **Rejected:** keeping lockstep to the base version only, which would make "every member equals its anchor" untrue the moment a prerelease exists; and exempting series branches from protection, which John's decision does not allow.
- **Gate:** `openspec validate release-groups --strict` passes with both requirements quoted in full under `## MODIFIED Requirements`, and the archive diff shows only the stated edits.

### D17 (2026-10-19, revised 2026-10-23 — AUDIT): Three rulesets, two repository settings, and bypass scoped to tag minting

No branch protection exists today: the only ruleset, `default`, is disabled, and the `protected-versions` ruleset of 2026-10-19 has since been deleted. What this change configures:

| Ruleset               | Targets                                                                                 | Rules                                                                                                                                                                                                                    | Bypass              |
| --------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------- |
| `protected-main`      | `~DEFAULT_BRANCH`                                                                       | pull request with **0** approvals, required checks (`Test Linux`, `Audit the workflows`, `version-integrity`), merge methods restricted to merge commits, restrict deletions, block force pushes, require signed commits | none                |
| `protected-versions`  | `refs/heads/v*.x`                                                                       | the same                                                                                                                                                                                                                 | none                |
| `protected-releases`  | `refs/tags/v*`, `refs/tags/*-v*`, **excluding `refs/tags/v*-nightly.*`** (target `tag`) | restrict creations, updates and deletions; block force pushes                                                                                                                                                            | wp-botswain, exempt |
| `protected-nightlies` | `refs/tags/v*-nightly.*` (target `tag`)                                                 | restrict creations and updates; block force pushes — **no deletion rule**                                                                                                                                                | wp-botswain, exempt |

- **Zero approvals is what makes it unattended.** The rule requires a _pull request_, not a reviewer, so botswain's writes are gated by checks and merged by GitHub rather than by a person (D13).
- **One pattern for the series branches.** `v?.?.x`, `v?.??.x`, `v?.???.x` each pinned the major to a single character, so `v10.1.x` matched none of them. `refs/heads/v*.x` covers every major and minor; `v[0-9]*.[0-9]*.x` is the tighter form if the extra specificity is wanted, since character classes are supported and `?` is undocumented.
- **Nightly tags are protected from everything but deletion, by design of the pipeline.** The published requirement _A shortfall withdraws what the run created, and nothing else_ makes a run delete the tag it minted, which only nightly does, and `delete_minted_tag` does it under `GITHUB_TOKEN` — not the bypass actor. A `deletion` rule on `v*` would refuse that step and leave a withdrawn nightly's tag standing, contradicting the published spec. So nightly tags live in their own ruleset without `deletion`, and are excluded from the one that has it. Creation and update stay restricted on them: the planner mints with the App token.
- **The transitions only ever create tags, so for `v*-pre.*`, `v*.*.*`, and the group tags only the creation rule is ever engaged.** `cut`, `advance`, `promote`, and `patch` each end in one `create_tag`; `promote` mints a new `v0.2.0` and leaves `v0.2.0-pre.N` untouched. Nothing updates, moves, or force-pushes a tag anywhere, so `update` and `non_fast_forward` are free safety rather than constraints the pipeline has to satisfy.
- **`--verify-tag` is what keeps the release workflows compatible.** `steps::create_release` runs `gh release view … || gh release create … --verify-tag` under `GITHUB_TOKEN`. The flag makes `gh` abort rather than create a missing tag, so that path never attempts a ref creation the ruleset would refuse. `gh release upload`, `edit`, and `delete` act on the release object, which a tag ruleset does not govern.
- **The tag patterns cover the group tags too.** `refs/tags/v*` does not match `bedrock-v0.4.0`; `refs/tags/*-v*` closes that. The repository's one non-release tag, `conventional-commits`, matches none of the patterns and stays unprotected, which is right.
- **Bypass is scoped to the one thing the rules would otherwise forbid.** Botswain needs no bypass to open a pull request, and none for a fast-forward version commit or for not deleting a branch — and on a ruleset that requires checks a bypass would skip the gate that is doing all the work. It is exempt only on the tag rulesets, because restricting tag _creation_ is what stops a person hand-minting a `v*` tag that the index and release pipelines would then act on, and the planners must still mint them.
- **The branch, not the tag, is the risk in a cut.** `cut` creates `v{minor}.x` with `github::create_branch`, and `protected-versions` deliberately carries no "restrict creations" rule, so that should be permitted — but whether a ruleset requiring a pull request also refuses the _initial creation_ of a matching branch is not settled by the documentation, and it is cut-breaking if it does. Verify when enabling (task 2.3). If creation is refused, the fallback is a bypass actor on `protected-versions`: it costs the enforcement guarantee, not the behaviour, since the bot's writes go through pull requests by construction and a bypass only permits skipping rather than causing it.
- **Two repository settings, neither of them a ruleset rule:** `merge_commit_message` moves from `BLANK` to the pull request body, without which every summary body and `Covenant: break` trailer is dropped at merge (D5); and `allow_auto_merge` turns on, without which the auto-merge mutation fails (D13).
- **Ordering:** both tag rulesets are safe to enable at any time. The two branch rulesets break the planners' direct writes the moment they are active, which is why the migration plan lands them together with the pull-request path.
- **Rejected:** one ruleset covering `main` and the series branches together (they will diverge — `main` is where summaries land and series branches only ever take version commits and cherry-picks); one tag ruleset with `deletion` for everything (refuses the published withdrawal); deleting the minted nightly tag with the App token instead (would put botswain's credentials into the `App Release` environment for one step, and the published asymmetry already says nightly tags are the ephemeral ones); a `required_deployments` rule, which `default` carries today and nothing in this pipeline deploys; keeping botswain exempt on the branch rulesets, which would silently defeat every required check.
- **Gate:** `GET /rules/branches/<name>` lists the expected rules for `main`, `v0.1.x`, and `v10.10.x`; a pull request with a free-form title cannot merge and a conventional one can; a hand-pushed `v*` tag is refused while botswain's is accepted; a nightly withdraw still deletes its minted tag.

### D18 (2026-10-26, decided — AUDIT): Channels pin library groups by tag; `main` builds in-tree; a registry is deferred

- **Why:** each channel is to be able to ship a different version of every library crate, and a private registry (Kellnr, which would run on the cluster the fleet already needs) is a later change. Without a registry, a git tag is the only thing a consumer can pin to — which is what the group tags are for.
- **Tags:** every library group's tag is `<group>-v{version}` — `bedrock-v0.2.0`, `outpost-v0.3.1`, `domain-v0.1.1` — and the app's stays bare, `v{version}`. The prefix is the group file's `tag` template, so no name is spelled in Rust. The existing triggers cannot confuse the two: the release workflows match `v[0-9]+…`, the index matches `v*`, and a prefixed tag matches neither.
- **Mechanism:** the crates the app ships — `src-tauri`, `cartograph`, `store`, `importer` — declare each library as a git dependency on this repository at a group tag, with `version` beside `path` on every intra-group dependency so Cargo can rewrite it. `main` carries a `[patch]` in the cargo config mapping each library to its in-tree path, so a nightly builds `HEAD` and is the integration channel. A series branch's first version commit — the app-version pull request the cut opens on it (D3 step 5) — removes that patch, so preview and stable build exactly the tags they pin. Toggling the patch rather than rewriting manifests keeps `main` and a series identical in every manifest, so cherry-picks onto the series never conflict on a dependency line.
- **The cut bumps the pins.** The summary commit on `main` tags each changed group and, in the same commit, rewrites the app-side pins to the tags it just minted — so the series cut from it starts pinned to what was just released, and `main` keeps building in-tree through the patch. A later pin bump on a series is an ordinary pull request, and `version-integrity` checks that every app-side crate moves together: one binary, one copy of each group (the _Pins diverge_ scenario).
- **Bill of materials:** on a series the pin _is_ the version, so `build.rs` reads it from the resolved dependency rather than `git describe`; on `main`, `describe` against the group's tags as D12 says. Injected values still win in CI and Nix.
- **Nix:** the overlay builds a fetched series tag whose `cargoDeps` fixed-output derivation must fetch the git-pinned libraries from the private repository — the same credential the `fetchTree` already carries, and a vendor hash that differs per channel, which is accepted: channels differing in library versions is the point.
- **Caching a library version falls out of the pins, given crane.** On a series branch a pinned library is an _external_ dependency, so crane's deps-only artifact compiles `bedrock 0.1.0` once and caches it keyed on the lockfile; every series build with the same pin reuses it from the binary cache, and that artifact _is_ the cached build of that group version. On `main` the libraries are workspace members and recompile with the app, which is what sccache covers in CI. A standalone derivation per group version would add nothing, since Cargo takes prebuilt artifacts only through that mechanism. Pushing the outputs to a private cachix cache is the follow-up change that makes this reach consumers, and it also means the credentialed fetch below runs once, in CI, rather than on every consumer's machine.
- **Rejected:** a registry now (deferred — the tags are what it would publish from, so nothing here is redone when it arrives); path dependencies everywhere, under which no channel could differ from another; rewriting dependency lines per branch instead of toggling the patch, which puts a manifest diff on every cherry-pick; a Nix derivation per group version, per above.
- **Gate:** a scratch series pinned at `bedrock-v0.1.0` builds while `main`'s `crates/bedrock` declares `0.2.0`; `version-integrity` refuses a pull request pinning two app-side crates to different tags of one group; `nix build` of a pinned series tag resolves every pin.

## Risks / Trade-offs

- [Per-channel pins fork the dependency graph] → every app-side crate must pin the same tag per group or the binary carries two copies of it and the types stop unifying. The lockstep check holds the pins together (D18), and the cut writes all of them in one commit.
- [The overlay fetches git dependencies from a private repository] → the credential already exists for the tree fetch; the cost is a per-channel vendor hash and one more place a lapsed token breaks a build, loudly (D18). **AUDIT:** the first pinned series builds under Nix.

- [One file per Contents API commit] → `update_file` would turn a cut into one commit per manifest. `commit_files` makes one signed commit over all of them (D3, D13).
- [`main` and series branches are protected] → every transition becomes two-phase (open PR → merge → tag or build), tags go on the merge commit (D3), and the index write follows (D13). John's local `merge: … into main` commits can no longer be pushed; a feature branch lands by pull request with a conventional title. The `merge` type that 11 first-parent commits carry today is not one CONTRIBUTING lists; `next_version` parses it as a non-feature change (any word is a type to it), and the gate will refuse it going forward.
- [Unattended merges make the check set the only gate] → with zero required approvals and auto-merge, nothing but the required checks stands between a bot pull request and `main`. Accepted deliberately (D13), which is why `version-integrity` is required rather than advisory, and why a check that cannot report — a path-filtered one — must never be required.
- [Enabling branch protection before the write path lands] → the nightly index write starts failing that same day, since the Contents API push is refused. The migration plan bundles them; the tag rulesets are the only pieces safe to enable early (D17).
- [A `deletion` rule on nightly tags breaks withdrawal] → the pipeline deletes a minted nightly tag under `GITHUB_TOKEN`, as the published spec requires. Nightly tags get their own ruleset without that rule (D17).
- [`createCommitOnBranch` has a shape of its own] → base64 file contents, an expected head oid, and a size ceiling per mutation. The manifests and the index entry are kilobytes; the oid is read immediately before the commit, and a mismatch is a clean retry rather than a corrupt write. Covered by fixture tests in `tools/github.rs`.
- [Feature unification enables two flavors at once] → Cargo features are additive, so a dependency graph that reaches a shared crate through two paths can switch on `preview` and `stable` together with no diagnostic, and the binary silently carries both channels' behaviour. Every crate that gates on a shipped flavor carries a `compile_error!` on any pair of them, and the release suite runs under exactly one; `development`, which the dev-dependencies unify into every test build, is additive by rule and outside the exclusivity (D10, D14).
- [A flavor-gated path ships untested] → only if the release suite runs under a flavor other than the build's. Task 7.3 makes the suite take the channel's flavor; until it lands, D10's permission is not yet safe to use, which is why the tree's flavor `cfg` count stays at zero.
- [Pre-1.0 hides severity bugs] → `features_always_increment_minor(true)` makes feat and break look identical; every severity test uses a `1.x` base (D6 gate).
- [cargo-semver-checks cost] → it builds each touched group twice, including the pinned turso pre-release. Run it on Linux only, only for touched groups, through the CI cache the test jobs will share once the build-cache follow-up reaches them. **AUDIT:** `--baseline-rev` builds `publish = false` crates on the pinned toolchain and the time is acceptable.
- [A required check that is path-filtered never reports] → `check-generated` is path-filtered and would leave a pull request waiting forever if required. Only the `Tests` workflow's jobs and the new checks are required; `check-generated` stays advisory until it runs unconditionally.
- [Formatter rewrites a fixture] → formatting amends the commit it belongs to, treewide passes go in `.git-blame-ignore-revs`, and fixtures are excluded from treefmt (D8).
- [Summary bodies drift from the diff] → the gate requires exactly one header per touched group, no more and no fewer (D5).
- [The cut's pull request runs the whole test suite] → every group's manifest changes, so `test-plan` resolves nearly `all()`. Accepted: a cut is rare and deliberate, and the gate is the point.
- [Phase two of a cut runs on a merge event, which a person could also produce] → the event handler acts only on a merged pull request authored by `wp-botswain[bot]` whose head commit is a `summary: cut …`; anything else is ignored and logged.
- [A tag is pushed before the merge commit's checks are visible to a later planner] → tags are created only from the merge commit the event names, so the planners' first-parent walk always contains what every tag points at.
- [`git describe` in `build.rs` costs a git call per build] → it already runs `rev-parse` twice; `describe` with a `--match` is the same order. Injected values short-circuit it in CI and Nix (D12).
- [Lockstep `cartograph` carries a prerelease version on `main`] → cargo accepts a prerelease in a path dependency; nothing consumes `cartograph` by version, and D16 settles the spec-level reading.
- [Four uncommitted workspace members] → `importer-sdk` and the three importer plugins sit outside `tooling/`, so the day they are committed the planners refuse until a group claims them. That is D1 working as intended; which group is the committing change's call, and nothing here pre-decides it.

## Migration Plan

1. **Guards first** (D1, D9, D11, D13's groundwork): the group file, its schema, the manifest cleanup, the `version-integrity` task and workflow, and the CONTRIBUTING amendments. Landable with no change to any planner; from here on a hand-edited version fails a pull request. The two tag rulesets (D17) can land here too, since they break nothing.
2. **Protect the branches** — the two branch rulesets and both repository settings (D17), audited — together with the `tools::github` calls and their three callers (the index write, the cut's `main`-side writes, the series-branch writes). These land in one step because protection breaks the direct writes the moment it is on.
3. **Attribution and severity** (D4–D6): the group-aware walk, summaries, the trailer, and `--major`. The planners read richer history but still mint only the app.
4. **Minting at cut** (D3): per-group plans and the two-phase cut. Proven in a scratch repository before the first cut that mints libraries.
5. **Evidence floors** (D7, D8): cargo-semver-checks and the fixture directories, at PR time and at cut.
6. **Build data** (D12) and the flavor lint (D14), independent of each other and of 3–5.
7. **The next cut** mints the first library tags; the nightly after it reports them in its build data.

Rollback: steps 1 and 6 are additive. Step 2 reverts by setting the rulesets back to `disabled` and restoring `update_file`'s callers, which is why the writes stay behind `tools::github`. Steps 3–5 revert planner-side without touching history; tags already minted stay valid.

## Open Questions

- How "the tag and the build succeeded" gates an index entry. A required status check cannot see it: the build ran on the tag, in another workflow, not on the index pull request's own commits. The cleaner reading is to gate upstream — the index workflow waits for the release run to conclude before opening its pull request — but the alternative, a check the index job posts itself, is also available. Affects D13's job wiring and task 2.4, not the specs.
- Whether the second phase of a cut lives in `release-plan`'s workflow (a `pull_request: closed` trigger alongside the dispatch) or in its own generated workflow. Affects no spec and no task boundary; the generator makes either a one-module choice.
- Whether `tombi lint` runs in the `version-integrity` job or only through `treefmt`'s tombi formatter step. The schema-currency test in `xtask` holds either way; the question is only where a misspelled key is reported first.
- Whether a cut's dry run should also print the bill of materials the next nightly would embed (D12). Convenience only.
