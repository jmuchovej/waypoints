## Why

Bedrock, Outpost, Domain, and Waypoints are meant to version independently, but only the app's version is ever planned: every library manifest still says `0.1.0`, nothing writes them, and `the_app_declares_its_own_version` in `tooling/xtask/src/workspace.rs` records the intent without a mechanism. The one planner that reads history (`cut`) treats every commit in the repository as a statement about the app, reads subjects only — so trailers and body footers are invisible — honours `!` as breaking, and runs with `features_always_increment_minor(true)`, which makes a feature and a break produce the same bump before 1.0. After v1 the same history would mint false majors, and a monorepo commit such as `feat(outpost)!: deployable Station` that also edits callers elsewhere would read as breaking for every group it touched.

Why now: a first series branch exists, so the next cut is the first one that could mint libraries — and `main` and the `v{major}.{minor}.x` series branches are to become protected branches, landing every change as a merge commit through a pull request (decided). Two direct writes to `main` already exist — the cut's provisional version bump in `planners/release.rs` and the release index entry in `bin/xtask/tasks/release_index.rs`, both through `tools::github::update_file` — and both carry a `TODO` deferring the protected-branch case to the change that protects the branch. This is that change. Commit messages are also increasingly written by agents, so a version claim needs evidence behind it, not just a well-formed header.

## What Changes

- **Group file.** `tooling/release-groups.toml` names every workspace crate outside `tooling/` as a versioned member of one group or an unversioned internal of one group, and declares four groups: `bedrock`, `outpost`, `domain`, `waypoints`. Crates under `tooling/` build the repository rather than the product and are out of the file's scope by rule, never by listing. Versions stay in the manifests; the file never takes a bookkeeping commit.
- **Generated schema.** `xtask` generates `tooling/schemas/release-groups.schema.json` from its own config types, and the group file binds it with a `#:schema` directive so tombi lints it, as the Tauri configs already are.
- **Path attribution over first-parent history.** The single `git log` both planners read (`releases::index::product_commits`) becomes group-aware: it walks `main`'s first-parent history, one merge commit per pull request, and reads each commit's changed paths, subject, body headers, and `Covenant` trailer. Each group owns disjoint paths; a library counts commits touching its own paths; the app counts its own paths plus every group's, because the binary ships them. Bookkeeping — `nix/releases/`, commits listed in `.git-blame-ignore-revs`, and the release bot's `chore(release):` commits — counts toward no group.
- **Summary commits.** A commit touching more than one group's paths uses the `summary` type in its subject and carries one conventional header per touched group in its body. Each group reads its own header; the subject counts for no group.
- **Library minting at the cut, or on their own.** `release-plan cut` computes every library group's next version, lands all of them in one summary commit on `main` through a botswain pull request, and — once the merge commit exists — tags each changed group at the merge commit and cuts the `v{minor}.x` branch from it. `release-plan cut --group <name>` mints one group alone the same way: no branch, no other version moved, no release workflow raised. Groups follow semantic versioning as Cargo reads it, with `--bump major|minor|patch` as a floor; they have no prerelease and so no promote. Advance, promote, and patch never touch a library version.
- **App severity.** The app ignores `!`. Its only breaking signal is a `Covenant: break` trailer, and a cut targets a major for the app only when a person passes `--major`; a trailer since the last stable makes a cut without `--major` refuse and name the commits.
- **Evidence floors.** A group's bump is the greater of what its commits declare and what evidence shows: `cargo semver-checks` against each library group's last tag, and append-only covenant fixtures under `covenant/fixtures/<group>/` whose modification is breaking for the owning group and the app.
- **Pull-request checks**, generated like the other workflows and required by the rulesets: the merge message (PR title and description) is a conventional commit; a multi-group PR is a complete summary; `chore(release):` is reserved to the bot; only the bot writes a versioned member's `[package].version`; group members are in lockstep; an undeclared API break fails; fixtures are append-only unless declared; the committed schema is current.
- **Every bot write lands through a pull request**, made entirely from `tools::github`, the `octocrab` module that already carries `xtask`'s Contents and Refs calls: one signed commit over every changed file through the `createCommitOnBranch` mutation, a pull request opened with the App token (so its checks run), auto-merge enabled, and the tags created on the merge commit afterwards. `update_file`'s planner callers go. **BREAKING (contributor workflow):** nothing pushes to `main` or a series branch directly any more, including the local `merge: … into main` commits that land today.
- **Build data.** Each build embeds every group's version — described from that group's latest tag, or injected where the source carries no tags — alongside `BuildInfo`, for the About surface, `--version`, and bug reports.
- **Flavor rule.** A channel's build may differ at compile time: `nightly`, `preview`, and `stable` are legitimate `cfg` gates for behaviour a channel must carry built-in — telemetry fidelity inversely related to stability is the canonical case, where a runtime toggle would be disableable exactly where the data matters most. What makes that safe is that every channel release, promotion included, is a fresh build whose release suite runs under the same flavor. Because Cargo features are additive and flavors are not, every crate that gates on a flavor refuses to compile with two enabled, and a lint keeps the flavor set closed to what `Flavor` names. Today no Rust code reads a flavor, so this lands the rules and the guard, not a migration.
- **Per-channel library pins.** Every library group's tag is `<group>-v{version}`; the app's stays bare. The crates the app ships declare each library as a git dependency on this repository at a group tag; `main` patches them to the in-tree paths, so nightly builds `HEAD`, while a series branch drops the patch and builds exactly the tags it pins. A cut pins the series it opens to the tags it just minted, and `version-integrity` holds every app-side crate to the same pin per group, so one binary carries one copy of each.

## Capabilities

This change stays inside the `distribution` domain, which `nix-flake-overlay` introduced and `nix-release-index` extended with `release-planning` and `release-index`. Pull-request checks on versions and commit messages are release integrity, the front half of distribution, not toolchain reproducibility — `toolchain` deltas may never constrain product behaviour, and these checks exist precisely to constrain what a release claims. Nothing here touches `distribution/release-publishing`, whose latest amendments (`consolidated-release-publish`, archived 2026-10-26) are already published, and no active change touches `release-planning`.

### New Capabilities

- `distribution/version-integrity`: the pull-request checks that make every version claim verifiable before it reaches history — who may write a version, lockstep within a group, conventional and complete landing messages, declared-versus-detected API breaks, append-only covenant fixtures, and a current group-file schema.

### Modified Capabilities

- `distribution/release-planning`: gains eight `ADDED` planner-side invariants — every workspace crate outside `tooling/` is named in the group file; groups own disjoint paths and the app counts what it ships, read over first-parent history; library versions are minted only by a cut; a multi-group commit is a summary; the app breaks only on a covenant trailer; evidence floors each group's bump; builds embed every group's version; each channel builds the library versions its branch pins, with `main` building in-tree.

  Two published requirements are also `MODIFIED`, because protecting the branches contradicts them as written:

  - _A series branch carries only cherry-picks of `main`_ admits only the planner's version commits and cherry-picks. Landing a version commit through a pull request adds a merge commit, a third kind, so the requirement is amended to allow the planner's version commit to arrive that way. Its purpose — no change originates on a series branch, so a tagged tree is self-sufficient — is unchanged.
  - _The manifest version names the channel_ ends `No other file SHALL declare a channel`, which a lockstep `cartograph` version carrying `main`'s `-nightly` prerelease would appear to violate. The requirement is amended to say that a versioned group member mirrors its anchor and is never read as a version or channel source.

  Everything else stays as published: _The app manifest is the sole source of a build's version_ still governs the app, _Release refs are minted so their pushes are observable_ is what makes the App token mandatory for the new tags, and _Release-bookkeeping commits are not product work_ stays true — the new attribution requirement widens the bookkeeping set around it rather than restating it. The `release-publishing` requirement that a run deletes only a tag it minted is honoured by the tag rulesets, not amended.

## Impact

- **New files:** `tooling/release-groups.toml`; `tooling/schemas/release-groups.schema.json`; `covenant/fixtures/{bedrock,outpost,domain,waypoints}/` with a README stating the append-only rule; `.git-blame-ignore-revs`.
- **`tooling/xtask` (library, `src/`):** `releases/groups.rs` (the group-file parser deriving `schemars::JsonSchema`, its semantic checks, and the schema writer); `releases/index.rs`, where `product_commits` becomes the group-aware first-parent walk and `fixture::Repo` grows paths, bodies, and merges; `planners/release.rs`, which gains per-group plans, `--major`, and the two-phase cut, and whose `write_version` is replaced by the pull-request path; `planners/integrity.rs`, the pull-request check; `tools/github.rs`, which gains `commit_files`, `open_pull_request`, and `enable_auto_merge` beside the Contents and Refs calls it has; `workflows/version_integrity.rs`, the generated workflow, with `workflows/release_plan.rs` and `workflows/release_index.rs` gaining the App-token steps; `workflows/_jobs.rs`, where the build jobs fetch tags and inject group versions; `typegen.rs`, which registers the new build-data type so the TypeScript bindings stay generated.
- **`tooling/xtask` (CLI, `src/bin/xtask/`):** new `tasks/release_groups.rs` and `tasks/version_integrity.rs`; `tasks/release_plan.rs` gains `--major`; `tasks/release_index.rs` opens a pull request instead of calling `update_file`.
- **Manifests:** `crates/store` and `crates/importer` drop `version`; `crates/cartograph` takes `src-tauri`'s exact version, prerelease included; each library anchor gains the `#:tombi toml-version = "v1.0.0"` directive the Nix reader needs; `schemars` joins `xtask`'s dependencies; `cargo-semver-checks` joins the pinned toolchain. `tooling/xtask` and `tooling/gh-workflow` are outside the group file's scope by rule; the working copy's `crates/importer-sdk` and `plugins/importer-*` fall inside it the day they are committed and must be placed in a group then.
- **Build data:** `crates/cartograph/src/build_info.rs`, `src-tauri/build.rs`, `src-tauri/src/commands/meta.rs`, `src-tauri/src/bin/waypoints.rs`, and `nix/packages/waypoints/package.nix` (the overlay builds a fetched tag with no git metadata, so it injects the values).
- **Formatting and notes:** `.config/treefmt.toml` excludes `covenant/fixtures/`; `.config/cliff.toml` gains one `commit_parsers` entry skipping `^summary:`, beside the `^chore\(release\):` skip already there.
- **Rulesets and repository settings (audit items):** no branch protection exists today — the only ruleset is disabled. Two tag rulesets: `protected-releases` on `refs/tags/v*` and `refs/tags/*-v*`, excluding nightlies, restricting creations, updates and deletions; and `protected-nightlies` on `refs/tags/v*-nightly.*` restricting creations and updates but **not** deletions, since the withdraw job deletes a minted nightly tag under `GITHUB_TOKEN` as the published `release-publishing` spec requires. Both with wp-botswain as the only bypass actor, so no one hand-mints a release tag the pipeline would act on. Two branch rulesets on `~DEFAULT_BRANCH` and `refs/heads/v*.x`, each requiring a pull request with zero approvals, the `Tests` workflow's jobs and `version-integrity` as checks, and merge commits only, with no bypass actor, since a bypass on a checked ruleset would skip the gate. And two settings that are not ruleset rules at all: `merge_commit_message` moves from `BLANK` to the pull request body, without which every summary body and `Covenant: break` trailer is dropped at the moment of merging, and `allow_auto_merge` turns on, without which a bot pull request cannot merge itself.
- **Release pipeline:** every transition becomes two-phase (open PR → merge → tag or build), and the release-index workflow's write follows the same path; the nightly planner's history walk becomes first-parent too, since both planners share one walk, but its decision — did anything land — is unchanged.
- **Docs:** `docs/CONTRIBUTING.md` gains the `summary` type, the `Covenant: break` trailer, the merge policy, and the rule that comma-joined regions must fall in one group.

## Non-goals

- No release-please or release-plz; `xtask` is extended instead, and the orphaned `.config/release-plz.toml` is removed.
- No crates.io publishing: `publish = false` stays.
- No channels for library groups; they have no installed population.
- No new conventional-commit type for release bookkeeping. `chore(release):` is what the planner already writes and what `.config/cliff.toml` already skips; only `summary` is added.
- No new GitHub transport. The bot writes extend `tools::github` and the `octocrab` client `xtask` already carries; `devenv-update` keeps the `create-pull-request` action, since its write is a tree diff rather than a value a planner computed.
- No private crate registry. Channels pin libraries by git tag, which needs no registry; Kellnr on the fleet's cluster, or a static sparse registry on R2, is a later change that publishes from the same group tags, so nothing here is redone when it arrives.
- No covenant fixture coverage. This change ships the directories, the append-only rule, the trailer, and the floors. A fixture per migration, payload type, ACL record, and envelope version is a follow-up change touching `bedrock`, `outpost`, and `store`.
- No versioning for components that do not ship yet; each becomes its own group when it does.
- No change to nightly versions (`{target}-nightly.N+YYYY.MM.DD`), to the app's four transitions, or to which tags a withdrawing run may delete.
- No store build numbers for preview and stable mobile builds. The release planner's `Plan` carries neither `WAYPOINTS_VERSION` nor `WAYPOINTS_BUILD_CODE` — only nightly's does — so those builds fall back to the Gradle and Xcode defaults. That is a gap in the app's release pipeline, not in group versioning, and is left to its own change.
- No removal of the flavor feature declarations themselves: `xtauri` passes `--features {flavor}` and cargo must accept it. They stay declared and empty; the lint keeps them unread.
- No re-linting of history. The checks apply to pull requests from the landing of this change; the planners read older first-parent commits as `next_version` does today, dropping non-conventional subjects.
