## Goals / Non-Goals

**Goals:**

- One bump workflow, one release workflow, one builder.
- A release run builds the tree a tag names and nothing else, and every write that advertises a release follows every write it depends on, the index entry last.
- A failed release leaves the repository as it was before its bump, and the retry is the same bump a person would run anyway.
- The builder can be called by anything that has a ref, and holds no publishing credential.
- Nothing a job does, declares, or resolves changes beyond what the model requires; the required checks keep their names; zizmor stays clean with no configuration file.

**Non-Goals (design-level, beyond the proposal's):**

- No command the workflows run is defined here; `release-commands` defines them, and this change is their wiring.
- No nightly tag minted by the release workflow; the release workflow mints nothing.
- No second body: the builder is the only nested workflow.
- No rendering of the release index into the builder; the builder's outputs are the tree's identity and the targets it built.

## Decisions

### D1 (2026-11-20): One `release.yaml` on the tag, one `build-distributables.yaml` it calls, and a `describe` job that reads the tag

- **Why:** the three channel workflows differ only in strings the tag carries, and the tag carries them because a tag's version classifies its channel (`Version::channel`, `releases/version.rs` 107–113) and the index already refuses a tag whose tree disagrees (`releases/index.rs` 85–95). John's model puts the planning before the tag and the building after it, so the release run needs no planner: it needs to read the tag it was started by, which `release describe` does. The builder is separate because testing and building a tree is a thing other callers may want, and because a job that builds should hold no publishing credential (`release-publishing`, _The store's write credential is an integrity credential_).
- **Shape of the builder.** `build-distributables.yaml`, `on: workflow_call` with inputs `ref` (string, required) and `platforms` (string, default `All`), `secrets: inherit` expected from its caller, and outputs `tag`, `version`, `channel`, `flavor`, and one per platform slug. Its first job, `describe`, checks out `ref` with full history and tags and runs `release describe --ref "$REF"`, publishing the version, the channel, the flavor, and the two store build codes; a rehearsal from `main` with no tag describes the nightly it would be, since `describe` appends today's date to a nightly manifest's version. The three test gates follow, each `test-plan --release` and the suite under the tree's flavor, as `jobs::test` builds them today, needing `describe`. The five builds need the gates, are gated on `platforms` alone, check out `ref`, inject `WAYPOINTS_VERSION` and `WAYPOINTS_BUILD_CODE` from `describe`'s outputs, build under the flavor, `distributables rename --platform <p> --tag "$TAG"`, upload `waypoints-{platform}-{channel}`, and record their target. The builder's outputs are `describe`'s and each build's recorded slug. The builder's behavior varies on nothing but its two inputs: no election, no publishing, no knowledge of why it was called.
- **Shape of the release.** `release.yaml`, `on: push: tags: v*`, `workflow_dispatch` with `tag` (string, empty default), `dry_run` (boolean, true), `build` (boolean, true), and `platforms`, and `workflow_call` with the same four as inputs. A `guard` job refuses, as expressions over the inputs and the event: a real dispatch with no tag; a real dispatch pairing a tag with a platforms subset (today's `guard_dispatch`); `build` off without `dry_run`. The `build` job calls `$/.github/workflows/build-distributables.yaml` with `ref` as the pushed tag, the dispatched tag, or `github.sha` when a rehearsal names none, `platforms` passed through, `secrets: inherit` under the job-scoped suppression (D6), and `if: inputs.build` on a dispatch; it needs `guard`. `create-release` needs `build` and drafts the record from `git-cliff` over the tag. `publish` needs both, gated on the completeness count over the builder's outputs and a real-or-rehearsal flag read from the event (`github.event_name == 'workflow_dispatch' && inputs.dry_run`), and runs today's order with the counterparts: download, listing, `distributables upload`, publish the record, mark the point of no return, both submissions, `distributables commit`, then the dry renders and the one artifact. `record` is D2. `withdraw-release` is D3. Concurrency is one queued group, `release-cycle`, shared with `bump.yaml` (D4): one release cycle runs at a time, so a scheduled nightly waits out a release run and cannot mint from a `main` that run is about to revert (D3); the builder runs inside its caller's run, and a future caller of it sits outside the group. GitHub holds one running and one pending run per group and cancels the pending one when another queues, so a nightly waiting behind a release is cancelled by a bump dispatched meanwhile and retries on its next schedule.
- **Why not `workflow_run`.** It would start the release when `bump` completed, but the release would have to learn the tag from an artifact, skip failed bumps by hand, and sit one level into a three-level cap; the tag push carries the tag in `github.ref_name` and fires only for a tag that exists. Library tags (`bedrock-v…`, `release-groups.toml` 29, 42, 49, 55) do not match `v*`, so a group bump starts no release, as today's index workflow already relies on (`release_index.rs` 28–30).
- **Rejected:** a channel-blind body with three callers (the shape the unlanded 2026-11-19 draft took; the tag carries the channel, and the callers would carry triggers the tag already is); `describe` in the release workflow and a second read in the builder (one compile, one answer, and the builder has to stamp its own build anyway); passing the version into the builder as an input (the builder would then build whatever it was told, which is the thing John wanted it unable to do); dropping `build` from the dispatch (the published scenario _No build, no publish steps_ reads it, and a rehearsal that exercises the guard and the record render without a forty-minute build matrix is worth the input); a per-tag concurrency group (two tags of one channel would then race on the manifest).
- **Gate:** generator tests: `release.yaml`'s triggers are the push pattern, the dispatch inputs above, and the call; no job of the builder declares `App Release`'s store scope, mints an App token, or names the store, the forge, or a submission; the builder's build jobs read `WAYPOINTS_VERSION` and `WAYPOINTS_BUILD_CODE` from `describe`'s outputs and nothing else; `every_channel_builds_and_publishes_its_own_flavor` becomes one assertion that the build recipe, the listing, and the submissions read the flavor from `describe`; `the_publish_steps_run_in_order_of_retractability` holds with `record` after `commit`; `the_committed_tfvars_are_the_generated_ones` is unchanged; `zizmor .github` reports nothing.

### D2 (2026-11-20): A `record` job writes the index entry after `publish`

- **Why:** the entry records a published release, and a tag-push trigger cannot know whether the publication succeeded; `protected-branches` left this as its first open question. Inside the release workflow, after `commit`, the answer is structural: the job runs only when the manifest was written, and a run that withdrew never reaches it.
- **Shape:** a `record` job, not a step of `publish`: the publish job checks out the tag's tree for `git-cliff`, and the pull-request action commits against the checked-out base, so the entry has to be written in a job that checks out `main` with tags, as `release-index.yaml` does today (101–105). The job needs `publish`, runs on a real run only, declares `CI`, enters the devenv shell for `nix flake prefetch`, runs `release record --tag "$TAG"`, reads the botswain credentials, mints a token, opens the pull request on `botswain/release-index/{channel}`, and runs `release merge --no-wait`. The dry render stays in `publish`'s counterparts. A backfill for a tag that predates this is `cargo xtask release record --tag <v>` on a workstation, which writes the entry and prints the landing for the person to open as a pull request; the `release-index.yaml` dispatch goes with the workflow.
- **Rejected:** a step in `publish` (the checkout problem above, and the App token would then sit in the job that holds the store credential); keeping `release-index.yaml` gated on the release run through `workflow_run` (passes no outputs, three-level cap, and a second workflow for one job); a `record` dispatch path on `release.yaml` (a dispatch that neither builds nor publishes but writes the index is a new grammar for a rare repair).
- **Gate:** the regenerated `release.yaml` has `record` needing `publish` with `if` on a real run; `the_index_entry_follows_the_commit_point` asserts the order; `release-index.yaml` is absent and `check` reports no orphan; a nightly dry run's `dry-run-nightly` artifact still holds `nix/releases/nightly.json`.

### D3 (2026-11-20, revised 2026-11-21): A failed run undoes the bump that minted its tag — the tag goes, the write is reverted by a pull request, and a cut's series and library tags go with it

- **Why:** John asked that a withdrawal return the repository to the state it was in before the bump ran, on every channel, because a tag deleted over a write that stays is a split brain: the files say `0.2.0-pre.3` and no tag does. Today only nightly's tag is deleted, because preview and stable tags were pushed before the run and might be fetched elsewhere (`_steps.rs` 1220–1224); under the tag-driven model every tag that starts a release run was minted for that publication minutes earlier by `bump`, nothing has recorded it (D2), and the tag ruleset already permits a run to delete one (`github.tf` 148). The write is undone the way it landed: a pull request the bot opens and auto-merges, which needs no bypass and keeps every write to a protected branch checked and signed. A rewind by force-push was weighed and declined: it needs the bot exempt from the branch rulesets, which exempts its direct pushes from the pull-request, check, and signature rules too, and it fails whenever the branch moved under it, which `main` does during a two-hour cut, so the revert path would have to exist anyway.
- **Shape:** `withdraw-release` keeps its gate — a tag, a real run, failure or a shortfall, no submission — and runs in order: discard the draft, `distributables withdraw`, delete the tag, then undo the bump; the tag and undo steps are conditioned on `github.event_name == 'push'`, in place of `tag_minted`, which goes from `Plan` (D7), so a dispatched re-publication of an existing tag leaves both the tag and its write, since that release may already be out. `release undo --tag "$TAG" --commit "$GITHUB_SHA"` (`release-commands` D4) refuses a nightly tag and a commit that is not the write's merge, and otherwise leaves the reverted write in the working tree with its landing published; the job mints an App token, the same pull-request action every write uses commits, signs, and opens the revert, and `release merge` waits for the merge, so the shared concurrency group (D1) holds the cycle until the tree is consistent again. For a `-pre.1` tag the bump was a cut, which also advanced `main`'s nightly, and the series exists only because of it: `undo` deletes the cut's library tags and the series branch through the API, checks `main` out, and reverts the cut's write there, so the one landing targets `main` and is opened and waited for the same way. Deleting the series needs `protected-versions` to drop its `deletion` rule (`github.tf` 118), the one ruleset change this design makes: a human with write access can then delete a series branch by hand, which today is John alone, and a series stays recoverable from its tags. `main` keeps every rule. While a revert is open, every bump refuses (`release-commands` D1). A failed nightly leaves no tag, no write, and no entry, and retries on the next schedule, since a `Taken` decision cannot block a tag that is gone. The retry of a preview or stable is the same bump a person would run anyway: the revert restored `pre.2`, the counted work that motivated `pre.3` is still on the series, and the bump writes `pre.3` again.
- **Rejected:** keeping the write and re-tagging the branch head on the next bump (the split brain John named: a declared version no tag names, for as long as nobody bumps); a rewind by force-push (above); a bypass for the bot on `protected-versions` in place of dropping the deletion rule (a bypass is ruleset-wide for the actor); keeping a cut's `main` write and library tags and re-opening only the series on the next bump (a recovery state of the kind this decision removes, with `main` declaring a target two minors above the newest series); the third shape, in which the series branch is created only after its first preview succeeds (the cleanest implementation, deferred for what it needs — Follow-ups).
- **Gate:** `nightlys_withdraw_deletes_the_tag_and_the_others_do_not` becomes `a_pushed_tag_is_withdrawn_with_its_write_and_a_dispatched_one_is_not`; the generator reads no `tag_minted`; the withdraw job's steps run in the order above with the undo steps conditioned on the push event; `tofu plan` over `tooling/infra` shows the one deletion rule leaving `protected-versions` and nothing else.

### D4 (2026-11-20): One `bump.yaml`, whose schedule means nightly

- **Why:** the three channels and the library groups are one planner's shapes, and John chose one workflow with the channels as dispatch choices and the cron as nightly.
- **Shape:** `bump.yaml`, `on: schedule: 0 7 * * *` (today's `NIGHTLY_CRON`) and `workflow_dispatch` with `target` (choice: `nightly`, `preview`, `stable`, then every library group the group file names at generation time, default `nightly`), `major` (boolean, false), `floor` (choice: none, `patch`, `minor`, `major`), and `dry_run` (boolean, true). One job, `bump`: the planner step runs `release bump`, mapping `target` to `--channel` or `--group` by membership in the channel list, passing `--major` and `--floor` as today's expressions, and passing `--dry-run` on a dispatch when `dry_run` is set or the target is nightly, so a nightly dispatch is always dry and the schedule alone mints one; the token, landing, merge, tag, and open-series steps are `release-plan.yaml`'s, gated as today on the inferred transition the planner publishes; nightly's path ends at the mint. `serialize("release-cycle")`, the group `release.yaml` shares (D1), so one release cycle runs at a time. The generator reads the group names from `release_groups::load`, which it already does for `WorkflowContext`-adjacent facts, so a new group is a dispatch choice on the next regeneration.
- **Rejected:** `bump-nightly.yaml` beside `bump.yaml` (one planner, one workflow; John chose this); `channel` and `group` as two inputs (a choice cannot be empty, and a nightly default beside a set group reads as a contradiction); groups as free text (the planner refuses an unknown name, but a choice is read before the run starts).
- **Gate:** `each_workflow_offers_its_dispatch_inputs` holds on `bump.yaml`; a test that a scheduled run's planner step carries `--channel nightly` with no `--dry-run` and a dispatched nightly carries it; `release-plan.yaml` and the three channel workflows are absent and `check` reports no orphan; `every_bot_pull_request_is_opened_by_the_app_and_signed` counts five openers (bump's two landings, the record, and the undo's two reverts).

### D5 (2026-11-20): The two setup prefixes are generated composite actions; checkout stays in the job; references use `$/`

First drafted on 2026-11-19 in the unlanded draft the Context names; John accepted it there, and nothing in the tag-driven model changes it.

- **Why:** a composite action is the only step-level reuse GitHub offers, and the prefixes are steps.
- **Shape:** `.github/actions/setup-mise/action.yaml` with inputs `mise-version` (required), `cache` (`false`), `free-disk` (`none`, `all`, `keep-android`), and `rust-cache` (`false`); `.github/actions/setup-nix/action.yaml` with inputs `packages` (`devenv`) and `extra-nix-config` (empty), the package list read from an environment variable. Each job checks out as today — its depth, tags, and ref are its own — then `uses: $/.github/actions/<name>` with the values it passed the constructors before. What stays in the job: the R2 snapshot pair and the compiler-cache server, which bracket the compile and carry the environment credential; the Android SDK, NDK, and Java; the Linux build dependencies. A `CompositeAction` in `workflows/_actions.rs`, serialized through the same backend, rendered with the generator's disclaimer by an `ActionFile` beside `WorkflowFile`, swept by `generated_files` over `.github/actions/*/action.yaml`; the suppression pass places a step directive under `runs:`; `.github/actions/**` joins `single-source-constants`' ledger of generated outputs and `devenv_update.rs`'s committed paths; `.github/renovate.json5` disables the `github-actions` manager under `.github/actions/**`; the pull-request audit becomes `zizmor .github`. - **Rejected:** checkout inside the action; a reusable workflow per prefix; one action with a toolchain input; a reusable test workflow in place of the action, which would have renamed the one required check it served.

## Risks / Trade-offs

- [Two `xtask` compiles per release instead of one] → `bump` compiles the planner in its run and `describe` compiles again in the builder; both go through the registry snapshot and the compiler cache the build jobs fill, as `prepare` does today (`_jobs.rs` 145–149), so each is minutes, not the twenty a cold compile costs.
- [A nightly's quiet-skip and its build are now two workflows] → the skip costs one short `bump` run and no release run at all, where today a skipped nightly still starts twelve jobs that each skip.
- [Deleting a preview or stable tag that something fetched] → the tag existed for the minutes between the bump's mint and the run's failure, nothing recorded it, and the ruleset allows the delete; the website and the updater read the manifest, which was never written.
- [A `target` choice listing library groups goes stale] → the generator reads the group file, and `check-generated` refuses a tree where `bump.yaml` was not regenerated after a group was added.
- [`build-distributables.yaml` is one level of nesting] → GitHub allows ten; the draft's non-goal against nesting was about the body-and-callers shape, which is gone.
- [`workflow_call` on `release.yaml` has no caller today] → declared so a later consumer, the nix build-and-cache pipeline John is specifying elsewhere, can call it; one `on:` key.
- [A revert takes the checks' length to land] → the window is the split brain John named, shrunk from "until someone bumps" to under an hour; every bump refuses in it naming the open revert, and the withdraw job waits for the merge, so the shared concurrency group holds the cycle closed until the tree is consistent.
- [A revert conflicts with a commit that landed meanwhile] → the write's hunks are the `version` lines of the group file and the manifests and the lockfile's workspace entries; a dependency bump touching other lockfile lines merges clean. A real conflict fails `undo` naming the files, the tag is already gone, and a person finishes the revert by hand.
- [`protected-versions` loses its deletion rule] → a human with write access can delete a series branch by hand, which today is John; every commit stays reachable from the series' tags, so a deletion is a branch to re-create, not a loss. `main` keeps every rule.
- [This change lands with the old workflows calling commands `release-commands` renamed] → it does not: `release-commands` regenerated them, and this change's first task touches only prefixes; the planners are deleted in the same tasks that delete the workflows reading them (D7).
