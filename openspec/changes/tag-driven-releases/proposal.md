## Why

The release pipeline is five workflows that each know a piece of the whole. `release-nightly.yaml`, `release-preview.yaml`, and `release-stable.yaml` are one generated shape rendered three times, 1,319 to 1,326 lines each, differing in a channel string, a tag pattern, and a schedule; each opens with a `prepare` job that is a planner on nightly, where it reads history and mints the day's tag, and a validator on the others, where it reads back the tag that was pushed. `release-plan.yaml` holds the four release-cycle transitions a person chooses by name, and the hour-long wait and second App token that landing a protected-branch write costs. `release-index.yaml` fires on every `v*` push and records the tag before the build that the tag names has finished, so a nightly whose builds fail has its tag withdrawn after its index entry has landed; the archived `protected-branches` design left exactly that ordering as an open question. And a preview or stable release that fails leaves its tag in place over a version write that stays, a split brain between what the tags say and what the files say.

John settled the shape in conversation on 2026-11-20 and 2026-11-21, and this change records the workflow half of it; `release-commands`, which lands first, records the command line it dispatches. The train stays as it is: a cut branches `v0.X.x` at `0.X.0-pre.1` and moves `main` to the next minor's nightly, previews and patches live on the series, and nightly is `main`. What changes is who does what. One `bump` workflow decides and mints for every channel and every library group, from one workflow whose schedule means nightly. One `release` workflow runs on the tag that `bump` pushed, calls a builder that knows only how to test and build the tree it is handed, and publishes in order of retractability with the index entry recorded last, after the manifest, so a withdrawn tag is never recorded. A run that fails undoes its bump, every channel alike: the tag goes, and the write is reverted through the same gate it landed by, so the files and the tags disagree for no longer than a revert takes to land, and the next bump recomputes from a clean tree. The sequence is `single-source-constants`, then `release-commands`, then this change, each landing alone so one review reads one kind of change; this one is the only one that changes what a workflow does.

## What Changes

- **One workflow releases, started by its tag.** `release.yaml` runs on `push: tags: v*`, on dispatch with an existing tag, and as a called workflow, replacing the three channel workflows. It calls the builder, whose first job, `describe`, derives channel, version, flavor, and store build codes from the tag; then the draft, the upload, the publication, the store submissions, the manifest, and the record, in that order. `withdraw-release` deletes the uploaded objects, the draft, and the tag when the run is the tag's own push, and undoes the bump that minted it: the write is reverted by a bot pull request through the same gate it landed by, and a failed first preview also deletes the series branch and the cut's library tags and reverts the cut's write on `main`. The one ruleset change is that `protected-versions` drops its deletion rule so the run may delete a series; `main` keeps every rule and the bot gains no bypass (design D1, D3).
- **One builder knows only the tree.** `build-distributables.yaml` is `workflow_call(ref, platforms)`: it checks out the ref, runs the release test gates with the existing filterset, builds the five platforms stamping version and build codes it derives from the ref, renames the outputs, and uploads them as GitHub artifacts. It holds no store, forge, or App credential and knows nothing of channels beyond the flavor the tree declares (design D1).
- **The index entry is written by the publishing run.** A `record` job runs `release record` after `publish` inside the release workflow, so an entry exists only for a tag whose release was committed. `release-index.yaml` retires; a backfill is a run of the command on a workstation (design D2).
- **One workflow bumps.** `bump.yaml` replaces `release-plan.yaml` and nightly's schedule: its schedule runs `release bump --channel nightly`, its dispatch takes a `target` choice of the three channels and the library groups, with `major`, `floor`, and `dry_run` defaulting to true; a nightly dispatch is always dry. It shares one concurrency group with `release.yaml`, so one release cycle runs at a time (design D4).
- **The old planners go.** `release prepare`, `release plan`, the nightly planner's `tag_minted`, `SKIP`, `should_build`, and `dry_run` are deleted in the task that rewrites the workflows that read them; `release-commands` left them in place for exactly this moment (design D7).
- **The shared setup prefixes become composite actions**, and the generator's audits read through both the action boundary and the called-workflow boundary (design D5, D6).

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `distribution/release-publishing`: six requirements are **ADDED** — _One pipeline publishes every channel, started by its tag_, _The builder knows only the tree it is given_, _The publishing run records the release it committed_, _A shortfall withdraws what the run created, its tag included_, _A withdrawal undoes the bump that minted the tag_, and _A failure past the point of no return is not withdrawn_ — two are **MODIFIED** with every existing scenario kept: _Each channel elects what it publishes_ (the election is the bump's; the run publishes the tag that started it) and _A channel advertises a release only once every target has succeeded_ (the manifest is the last write to the store; the record follows it) — and one is **REMOVED**: _A shortfall withdraws what the run created, and nothing else_, whose two unchanged scenarios continue in the withdrawal requirements above and whose tag rule they reverse, since every tag that starts a run was minted for that publication.
- `distribution/release-planning`: one requirement is **ADDED** — _One workflow bumps every channel and every group_ — and _A dry run decides as a real run and mints nothing_ is **MODIFIED**, every scenario kept, two re-pointed at the bump workflow. `release-commands` adds _A bump infers the transition from the series_ and _Bookkeeping alone moves no tag_ to this spec; the open deltas of `library-minting`, `group-file-versions`, and `explicit-group-ownership` modify other requirements of it; none overlap.
- `distribution/release-index`: _The index is written after its tag exists_ is **MODIFIED**, every scenario kept and one added: the writer is the publishing run, after its commit point, so a withdrawn tag is never recorded.
- `toolchain/workflow-generation`: two requirements are **ADDED** — _Shared setup prefixes are generated composite actions_ and _A generated action holds setup alone, and is audited as the job's steps_ — and two are **MODIFIED** with every scenario kept: _Lint suppressions are declared on the step they concern_ extends to a job-scoped finding, and _Generated workflows pass the workflow linter in CI_ extends to the composite actions and names what the generator holds where the linter cannot see.

## Impact

- `tooling/xtask/src/workflows/`: `release.rs` becomes the tag-driven workflow, `build.rs` (new) the builder, `bump.rs` the bump; `release_plan.rs` and `release_index.rs` go; `_jobs.rs`, `_steps.rs`, `_helpers.rs`, `_types.rs`, and `_suppressions.rs` carry the calling job, the composite-action references, the job-scoped suppression, and the builder's outputs; `_actions.rs` (new) holds the two actions; `workflows.rs`'s list, sweep, and audits follow.
- `tooling/xtask/src/bin/xtask/tasks/release/{prepare,plan}.rs` and `planners/nightly.rs`'s `tag_minted`, `SKIP`, `should_build`, and `dry_run`: deleted with the workflows that read them; `main.rs`'s `Release` enum loses the two variants.
- `tooling/gh-workflow/src/{job,step}.rs`: a job carries lint suppressions as a step does, and a step's `uses` can be a path.
- `.github/workflows/`: `bump.yaml`, `release.yaml`, `build-distributables.yaml` (new); `release-nightly.yaml`, `release-preview.yaml`, `release-stable.yaml`, `release-plan.yaml`, `release-index.yaml` (removed); every other workflow's jobs open with a checkout and a `$/.github/actions/…` step. `.github/actions/{setup-mise,setup-nix}/action.yaml` (new).
- `tooling/infra/github.tf`: `protected-versions` loses its `deletion` rule, so a withdrawal can delete the series a failed cut opened. `tooling/infra/github.auto.tfvars.json`: unchanged; the required checks are `pull-request.yaml`'s and `version-integrity.yaml`'s jobs, and neither workflow changes beyond its setup prefix.

## Non-goals

- No change to the train: which branches exist, what a cut writes, how a series is pinned, how a nightly is named.
- No change to the command line beyond deleting the two planners and the four outputs the old workflows read; every command this change dispatches arrived in `release-commands`.
- No change to how a bump sizes a version or infers its transition; that is `release-commands`' D1.
- No patch previews: a fix to a candidate line is the next `-pre.N`, as today.
- No merge-triggered tagging handler: the wait stays inside the bump run, so no workflow runs on every ordinary merge to `main`.
- No use of `workflow_run`: it passes no outputs, fires on failed runs too, and caps chains at three levels, while the tag already carries the one datum the release needs.
- No change to the release test filterset: the gates run the roots and what they pull in, as today.
- No store, forge, or App credential in the builder; the builder holds only what signing needs.
- No rewind of a protected branch and no bypass for the bot: a withdrawal undoes a write by a pull request through the same gate the write landed by, and the only ruleset change is the deletion rule a cut's undo needs.
- No change to the required checks or to `main`'s rules.
- No `xtask`-minted App tokens: the pull request is still opened and signed by the action, and the tokens by `create-github-app-token`.
