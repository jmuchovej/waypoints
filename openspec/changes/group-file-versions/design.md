## Context

See proposal.md — Why. Verified 2026-11-17 against the tree `library-minting` left on 2026-11-16, at the commit that stamps group versions in builds; each paragraph below names where a fact lives and, where it matters, which change put it there.

**The group file and its parser.** `tooling/release-groups.toml` names five groups, each with `members`, `anchor`, `tag`, `breaking`, `floors`, `fixtures`, and `minted`, and no group carries a version. In `tooling/xtask/src/release_groups.rs`, `Group.anchor` is required, `load` refuses an anchor outside its members, `members_anchored_at` finds a group by it, and the generated `tooling/schemas/release-groups.schema.json` lists `anchor` as required (`release-groups-guards` D1, D6). The file opens with `#:tombi toml-version = "v1.1.0"` and a `#:schema` line. It is already strict TOML 1.0, holding no inline table and no 1.1 construct: on scratch copies formatted beside the project's `.config/tombi.toml`, `tombi format` leaves it byte-identical under either directive, `tombi lint` passes it under `v1.0.0`, and `builtins.fromTOML` reads it as it stands.

**What the versions are today.** Every library manifest declares `0.1.0`; `src-tauri` and `cartograph` declare `0.1.0-nightly`. The remote carries one nightly tag and no `<group>-v*` tag, and no series exists, so the next cut is the first.

**How the planners read a version.** The app's version comes through `workspace::version()`, which asks `cargo metadata` for the `Waypoints` package, in `plan` for every transition but cut, in the nightly planner, and for `release-stage`'s default tag (`tooling/xtask/src/planners/release.rs`, `workspace.rs`, `src/bin/xtask/tasks/{publish_plan,release_stage}.rs`). A cut reads each library group's current version through `anchor_version(metadata, &group.anchor)`, and the app's group and members are found by `anchor == "src-tauri"` in `app_group` and `app_members`.

**How a version is written.** Every write is `write_members(members, version)` in `planners/release.rs`: `set_package_version` on each member manifest and `set_locked_version` on its lockfile entry, both line edits that keep tombi's alignment. `execute` calls it on a cut for each minted group and `main`'s bump, and otherwise for the app on its series; `open_series` calls it for the app, then `pin_workspace` and `cargo update --workspace`; a patch moves pins the same way. `written_paths` and `Plan::main_landing` list the manifests and the lockfile for the pull-request step (`library-minting` D1, D7). A dry run renders `main.patch` and `series.patch` from `git show` through `manifest_changes`, covering the member manifests and lockfile entries, plus the root manifest where pins move, beside `refs.md` and `notes.md` (`release-dry-runs`, extended by `library-minting`).

**What `version-integrity` holds.** `tooling/xtask/src/version_integrity.rs` reads `[package].version` changes in versioned members' manifests between the merge base and head and refuses them unless the bot authored the pull request (`differing_versions`, `version_writes`); `lockstep_violations` compares every member's declared version, from `cargo metadata`, with its anchor's; `pin_violations` reads a series' pins by tag shape through `release_groups::pins_in` and `group_of_tag`. The planners' `load` refuses a tree the file does not describe (`release-groups-guards` D5, `protected-branches`, `library-minting` D8).

**What a build embeds.** `src-tauri/build.rs` reads the group file as plain TOML, skips the group carrying `owns`, and for each other group reads `tag` and `anchor`, then that manifest's `name` and `version`. `group_versions::resolve` in `src-tauri/src/group_versions.rs` answers injected first, then `pinned(lockfile, anchor_package)` by package name, then `git describe --match '<prefix>*'`, then the anchor's declared version (`library-minting` D6).

**What Nix reads.** The recipe's `group-versions` in `nix/packages/waypoints/package.nix` reads the group file's `group.<name>.anchor`, that manifest's `package.name` and `version`, and `pinOf name` from `distribution/nix/lockfile.nix`; its `manifest-version` reads `src-tauri/Cargo.toml`. `distribution/nix/channel.nix` reads the same manifest for the channel and the series, and `distribution/nix/overlay.nix` and `flake.nix` import it. The overlay's Station asks `pinOf "outpost"`, which is a crate's revision rather than a group's version. `builtins.fromTOML` reads strict TOML 1.0, so the root, `src-tauri`, and `crates/{bedrock,domain,outpost,transload}` manifests carry `#:tombi toml-version = "v1.0.0"` under the comment "Must use TOML v1.0.0 because of nix's `builtins.fromTOML`"; `cartograph`'s carries none. `.config/tombi.toml` sets `v1.1.0` for the tree and aligns `=` per table (`library-minting` 5.2).

**Other readers of the anchor and the manifest.** `semver_check::library_members` leaves the app's own crate out of the app group's measurement by comparing each member's directory with the app group's `anchor`, finding the app group through `remainder_group` (`library-minting` D5). `index::classify` in `tooling/xtask/src/releases/index.rs` refuses a tag whose version classifies as one channel while the tagged tree's app manifest, read with `git show`, classifies as another.

**What counts as bookkeeping.** The walk counts a `tooling/` path for no group (`owner_of` in `release_groups.rs`), and every commit the release bot authored, every revision in `.git-blame-ignore-revs`, and every reserved subject as bookkeeping (`attribute` in `tooling/xtask/src/releases/history.rs`; `library-minting` D2). `docs/CONTRIBUTING.md`'s _Landing a pull request_ says that `chore(release):` and version writes belong to the release bot, and names "a change to a versioned crate's `[package].version`" as the write it means.

**What does not exist yet**, and this change proposes: a `version` key in the group file, a projection routine, a `generate versions` subcommand, a lockstep check against the file, and a by-prefix pin lookup.

## Goals / Non-Goals

**Goals:**

- One key per group answers "what version is this group" for every reader — planner, build script, Nix, and a person opening the file — and no reader opens a manifest to find it.
- A landed tree never holds a manifest that disagrees with the file: the bot writes both in one commit, a command projects a hand edit, and the pull-request check refuses drift.
- A series' file states what the series ships: the app's version and every pinned group's.
- Nothing the first cut mints changes; the cut writes one more file.

**Non-Goals (design-level, beyond the proposal's):**

- No reading of the file by Cargo or Tauri. Cargo resolves what the manifests say; the file's job is to be what the manifests are held to.
- No version for an internal (`store`) or for `tooling/`; neither is versioned today.
- No second lookup rule for the app. The app's version is a group's `version` like any other, suffix and all (D4).

## Decisions

### D1 (2026-11-17): The group file declares every group's version; the manifests are projections

- **Why:** `release-groups-guards` D1 kept versions out of the file so the file would never take a bookkeeping commit and the manifest would stay the sole source. Both reasons have since moved. The walk now counts `tooling/` for no group and treats every commit the bot authors as bookkeeping (`library-minting` D2), so a cut's commit touching the file counts for nothing whatever it touches; and the manifest was never one source but five, one per anchor, with every reader deriving "which manifest" from a key whose only job was to say so. The file is the place every non-Cargo reader already opens — the planners, `build.rs`, the Nix recipe — so declaring there removes a lookup from each rather than adding one. What the file takes on is one line per group, rewritten by the same commit that already rewrites every minted manifest.
- **Shape:** `[group.<name>] version = "…"`, beside `members`; a library group's is bare (`0.1.0`), the app's carries its channel suffix (D4). `version` is required; `anchor` goes (D2). The parser reads it as a semantic version and refuses one that does not parse.
- **One projection routine.** `write_members` becomes `project(group, version)`: the file's `version` line, each member manifest's `[package].version`, and each member's lockfile entry, all as the line edits already written so tombi's alignment survives. Every planner write goes through it — a cut's minted groups and `main`'s bump on `main`, the app's version on a series for advance, promote, and patch, and a patch's moved pins (D5) — and nothing else in `xtask` writes a version. `cargo xtask generate versions` runs the routine for every group from the file as it stands: for a hand-edited file, for a crate newly joining a group whose manifest has to take the group's version, and for the scratch repositories the audits use. The command's effect is idempotent; on an agreeing tree it changes nothing.
- **What one commit carries.** A cut: the file, every changed member manifest, and the lockfile, in the one summary commit on `main`; the series' first write then sets the file's app version beside the app's manifests and the pins, with each pinned group's `version` held to its pin (a no-op where the cut minted it). Advance and promote: the file and the app's manifests. Patch: those, and for each pin it moves, that group's `version` in the series' file. `written_paths` and `main_landing` list the file so the pull-request step commits it with the rest.
- **The bot writes it; a person projects it.** The version-writes rule reserved to `wp-botswain[bot]` covers the file's `version` values (D5), so a person cannot land a hand-edited version through either file; `generate versions` exists so that when a person has to touch the file — a new group, a new member — the manifests follow in the same pull request and the lockstep clause passes.
- **Rejected:** a `version` key as a mirror of the manifests (the two-sources hazard `release-groups-guards` named — one of the two has to be the declaration, and the file is the one every non-Cargo reader opens); a ledger beside the file, `.release-please-manifest.json` style (a third file saying what the second could); `version.workspace = true` in every member (Cargo's inheritance gives one version to the whole workspace, and five groups need five; it also reads the series' root for a crate that on a series is resolved from a tag's tree).
- **Gate:** `release plan cut --dry-run --into` renders the file's hunk in `main.patch` beside the manifests' (D6); `tests/version_write.rs` shows a cut leaving the file, the manifests, and the lockfile written together and an advance leaving the file and the app's manifests; `generate versions` on a hand-edited file leaves every member manifest and lockfile entry equal to it and is a no-op on the tree as landed; `treefmt --fail-on-change` is clean after either write.

### D2 (2026-11-17): `anchor` goes; a pin is read by its tag's shape; the app is found by what it owns

- **Why:** lockstep makes every member equivalent, so "the member whose version is the group's" is a distinction without a difference once the file declares the version. Its readers were: which manifest to read (the planners, `build.rs`, the recipe — all now read the file); which lockfile entry carries the pin (`group_versions::pinned`, `lockfile.nix`'s `pinOf`); which group is the app and which crate is the app's own (`app_group`, `app_members`, `semver_check::library_members`).
- **The pin by prefix** (withdrawn 2026-11-26 with the pins, `library-minting` D7: a series builds in-tree, so no lockfile entry is sourced from this repository, and `group_versions::pinned`, `pins_in`, and `lockfile.nix`'s lookups go with the single-pin check; the record of what was built follows). Every lockfile entry sourced from this repository carries `?tag=<prefix><version>` in its `source`, and `pins_in` already reads a manifest's pins by that shape against each group's template. `group_versions::pinned(lockfile, prefix)` and a by-prefix lookup in `lockfile.nix` read the lockfile the same way: the first entry whose source names a tag with the group's prefix is the group's pin, and every member of a pinned group names the same tag, which the single-pin check holds. A registry crate sharing a member's name has another source and never matches. The overlay's Station keeps `pinOf "outpost"`: it fetches a crate's revision, and the crate's name is the right key for that.
- **The app by what it owns.** The app group is the one with `owns = "remainder"`, which `remainder_group` already answers and `semver_check` already uses; `app_group` reads it. The app's own crate — the one `library_members` leaves out of the app group's measurement, and the manifest Tauri reads — is the `Waypoints` package `workspace.rs` names as `APP`, at `src-tauri`. This is the one reader the brief did not settle; the choice is to name the crate, as `workspace::app_dir` already does, rather than keep a key for it.
- **Shape:** `Group.anchor` and `members_anchored_at` are removed; `deny_unknown_fields` refuses a file still carrying `anchor`; the schema is regenerated without it; every test fixture drops the line. `group_versions::Group` becomes `{ name, prefix, declared }`.
- **Rejected:** keeping `anchor` with no reader (a key nothing reads drifts into meaning something); the first member as an implicit anchor (an ordering rule hiding in a list); reading the Station's pin by prefix too (it needs a crate, not a group, and the by-name lookup already exists).
- **Gate:** the file parses without `anchor` and is refused with it; `pinned` finds a group's pin among several members' entries and ignores a registry crate of a member's name; `nix eval` of `lockfile.nix` on a fixture lockfile answers by prefix; the regenerated schema lists `version` as required and no `anchor`; `library_members` on this tree still leaves `src-tauri` out and measures `cartograph`.

### D3 (2026-11-17): Readers read the file

- **Planners:** `GroupFile::version_of(group)` is the one reader. `group_plan` takes a library's current version from it in place of `anchor_version`; `plan` takes the app's from it for advance, promote, and patch in place of `workspace::version()`, as do the nightly planner and `release-stage`'s default tag; `workspace::version()` goes, and `the_app_declares_its_own_version` becomes the agreement test — the file and the app manifest say the same version on this tree. A planner reads the file from the checkout it reads the manifest from today, and `load` refuses a tree whose manifests disagree with it (D5), so a stale projection cannot be planned from.
- **`index::classify` stays.** It compares a tag's version with the tagged tree's app manifest through `git show`. A tag is minted from a landed tree, where the manifest equals the file, so either read gives the same answer, and the published scenario _A tag and its tree cannot disagree_ keeps its wording.
- **`build.rs`:** already reads the group file; it now takes each library group's `version` as the declared fallback and stops opening the anchor manifest. _Revised 2026-11-26:_ the pin step goes with the pins (`library-minting` D7); the order is injected, described, declared.
- **Nix:** the recipe's `group-versions` reads `group.<name>.version` (and, until 2026-11-26, the by-prefix pin); `manifest-version` is renamed for what it is and read from the file's app version through `channel.nix`, which reads the group carrying `owns` — the same filter the recipe uses to tell libraries from the app. The `app-version` assertion that a recorded tag extends the declared version is unchanged. The overlay and the flake import `channel.nix` as before.
- **The group file's directive** becomes `#:tombi toml-version = "v1.0.0"`. `builtins.fromTOML` already reads the file, and under the project's config tombi formats it identically either way (Context), so the edit is one line; what it buys is that tombi refuses a 1.1 construct — a multi-line inline table — before a Nix reader fails on it.
- **The three crate manifests' TOML 1.0 directives stay.** The files are 1.0 now (tombi reformatted `domain`'s inline table on the way in), the root and `src-tauri` and `outpost` manifests carried the directive before them, and crane's dependency-only pass — the follow-up `library-minting` lists — needs every crate manifest readable by `fromTOML`. Removing them would let a 1.1 construct back in that nothing catches until a reader needs it. The comment above each stays as it is: it names the reader class, and crane's vendoring is one.
- **Rejected:** `workspace::version()` reimplemented over the file (keeps a name that says "workspace" for a value the file declares; callers switch instead); `channel.nix` keeping the manifest path (one more reader of a projection, and the one the overlay's every message depends on).
- **Gate:** `release plan cut --dry-run` on this tree prints the five groups at the versions the file declares; `release prepare` dry prints the same target as before; `nix eval` of `channel.nix` on this tree answers `nightly` and `v0.1.x` as before; `nix build` of the development app logs `bedrock=0.1.0,domain=0.1.0,outpost=0.1.0,transload=0.1.0` as before; `tombi lint` and `nix eval --expr 'builtins.fromTOML …'` pass on the file.

### D4 (2026-11-17): The app's version joins the file, channel suffix included

- **Why:** the alternative — libraries in the file, the app in `src-tauri/Cargo.toml` — leaves two rules for "where is a group's version", one per kind of group, and every reader branching on the kind; the file would describe four of five groups; and a series' file would not say what the series ships, which is the app's version first. Uniformity wins: one key, one reader, one projection, one clause in `version-integrity`.
- **Shape:** `[group.waypoints] version = "0.1.0-nightly"` on `main` today; `0.2.0-pre.1` from the commit that cuts a series, `0.2.0` from the one that promotes it. The channel is read from it as `Version::channel` reads a manifest's; `channel.nix` reads the same string. `src-tauri` and `cartograph` project it exactly, prerelease included, as the lockstep clause already demanded of `cartograph`. `build.rs`'s flavor check still reads `CARGO_PKG_VERSION_PRE`, which is the projection's — equal by the check.
- **What `distribution/release-planning` says afterwards:** the file declares a build's version and the app manifest projects it; every build reads one or the other and gets the same value; a flavor config still declares none; a publish-time suffix still extends the declared version rather than replacing it. _The manifest version names the channel_ keeps every scenario: the manifest still names the channel, because it projects the version that does.
- **Rejected:** libraries only (above); the app's version in the file without its suffix, the channel being derived elsewhere (a second place to say the channel, which the published requirement forbids).
- **Gate:** a fixture series whose file says `0.2.0-pre.1` reads as preview in the planner and in `channel.nix`; `the_app_declares_its_own_version`'s successor holds the file and `src-tauri/Cargo.toml` equal on this tree; the overlay's three packages evaluate on `main` as before.

### D5 (2026-11-17): `version-integrity` holds the projections to the file

- **Lockstep against the file.** `lockstep_violations` compares every workspace member's declared version, from `cargo metadata`, with its group's `version` in the file, naming the manifest and the file on a difference. _Revised 2026-11-26:_ a series builds in-tree (`library-minting` D7), so every library crate is a workspace member on a series too and is held to the file like `main`'s; the clause that held a pinned group's `version` to its pin's tag goes with the pins, as does the risk it answered.
- **Version writes cover the file.** A change to a group's `version` value between the merge base and head is a version write, refused unless the bot authored the pull request, exactly as a manifest's `[package].version` is. A key that appears where none was — this change's own landing, or a new group joining the file — is not a write; what that pull request may claim is bounded by the lockstep clause, which holds the new value to the manifests beside it.
- **The planners apply the same rule.** `release_groups::load` refuses a tree whose member manifests disagree with the file, with the lockstep clause's message, so a planner never plans from a projection the check would refuse.
- **Unchanged:** the series-pin and single-pin checks, the summary gate, the fixture rule, the schema-currency test.
- **Rejected:** holding only the manifests to one another and leaving the file unchecked (the file would be a declaration nothing enforced); refusing every file edit by a person (a new group or member has to be declared by someone, and the bot cannot know it).
- **Gate:** tests: a hand-edited `version` in the file fails naming the file; the bot's write of the file and every member passes; a member manifest differing from the file names both; a new member's manifest at another version names both; a series fixture pinning `bedrock-v0.2.0` with the file at `0.2.0` passes and at `0.1.0` fails naming the pin; a fixture of `main`'s root manifest passes as in-tree; `this_workspace_is_in_lockstep` holds against the file; `cargo xtask check version-integrity` on this tree reports agreement.

### D6 (2026-11-17): The dry run renders the file's write

- **Shape:** `rehearse` adds the group file to the changes it renders: in `main.patch`, each minted group's `version` and `main`'s next app version; in `series.patch`, the app's version on every series transition (until 2026-11-26 a patch also rendered each moved pin's line; the pins went with `library-minting` D7). `manifest_changes` reads the file at the same `git show` reference it reads the manifests at, so the checkout stays clean. `refs.md` is unchanged; the file is a write, not a ref.
- **Why here and not in `library-minting`'s requirement:** that requirement is already `MODIFIED` by an open change; a second modification would have to restate a text that is not yet in the main spec. This change adds a requirement beside it.
- **Gate:** a dry cut's `main.patch` carries the file's hunk with every minted group's line and the app's; a dry patch's `series.patch` carries the app's line in the file and no library's; _The tree is clean afterwards_ still holds.

## Risks / Trade-offs

- [Two places say a version during the landing window] → the `version` keys, the lockstep clause, and the planners' agreement rule land in one pull request, with the keys equal to the manifests; from the first run the check holds them together, and the write rule reads the keys' introduction as agreement, not as a write (D5).
- [The bot's commit touches `tooling/`] → `tooling/` counts for no group and the bot's commits are bookkeeping; the cut's summary already carries every minted manifest, and the file joins it (D1).
- [A person hand-edits the file on a workstation and forgets the manifests] → `generate versions` makes them follow; the check refuses the pull request either way, naming the manifest and the file.
- [A series' file lies about what the series builds] → a series builds in-tree (`library-minting` D7, 2026-11-26), so lockstep holds every library member's manifest to the file there as on `main`; the file's library versions are the cut's, and the build data describes any cherry-pick past them.
- [A 1.1 construct reaches the group file and `fromTOML` fails at evaluation] → the `v1.0.0` directive makes tombi refuse it in `treefmt`; the gate evaluates the file with `fromTOML`.
- [Cargo's workspace inheritance tempts a later refactor] → rejected in D1 for a structural reason, one version per workspace, that does not change.
- [The app crate found by name rather than by a key] → `workspace::APP` is already the name `xtask` builds and stages; renaming the package would break those first and loudly.
- [`index::classify` reads the manifest while everything else reads the file] → a tag is minted from a landed tree, where the two are equal; the scenario holds under either reading (D3).

## Migration Plan

1. **The file and its parser** (D1, D2): `version` in, `anchor` out, the directive to `v1.0.0`, the schema regenerated, every fixture updated. One pull request by a person; the keys equal the manifests, so the check landing with it reports agreement.
2. **Readers** (D3, D4): the planners, `build.rs`, the recipe, `channel.nix`. Each reads the same values it read before, from the file.
3. **Writers and the dry run** (D1, D6): the projection routine, `generate versions`, the landings, the patches.
4. **Checks** (D5): the lockstep clause against the file, the write rule over the file, the planners' agreement rule.
5. **The first cut**, after this lands: `library-minting`'s scratch run, rehearsal, real cut, group-scoped cut, and patch, run with the file in place (tasks.md group 6).

Rollback: steps 2–4 are code; step 1 reverts by restoring `anchor` and dropping `version`, one pull request. Nothing minted depends on the key until the first cut, which this change precedes.

## Follow-ups

- The lockfile edits in the projection are still line edits (`set_locked_version`); `cargo update --workspace --offline` would let cargo write them, as `library-minting` already notes.
- CONTRIBUTING's _Landing a pull request_ could show the group file's shape; the one sentence this change amends is enough for the rule.

## Open Questions

- Whether `generate versions` should also refuse, rather than silently overwrite, a manifest whose version is ahead of the file's — a sign the file was the stale side. Nothing here depends on the answer; the check refuses the pull request in either case.
