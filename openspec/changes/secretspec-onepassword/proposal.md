## Why

Every secret CI uses — the signing material for five platforms and the wp-botswain credentials — sits in the repo as `secrets.sops.yaml`, and one age key in GitHub secrets (`SOPS_AGE_KEY`) decrypts all of it. That shape has three costs that compound as the maintainer set grows: rotating any one value is a commit, the encrypted history is permanent, and the credential that mints a pull-request token is the same credential that unlocks every signing key. The `automation` profile was split from `release` precisely so a token-minting run would not resolve the signing set, but a single decryption key makes that separation nominal.

The migration is small because the manifest is already provider-agnostic: each secret is declared once and addressed in the store by coordinates secretspec translates per provider. Pointing the CI-facing profiles at 1Password is the provider aliases, two `defaults` blocks, and a second set of coordinates beside the sops ones. The only real work is in the CI generator, which currently stamps the backend choice onto every workflow rather than onto the steps that resolve secrets, and which does not yet know about GitHub environments.

## What Changes

- **1Password becomes the store CI reads.** `release` and `automation` resolve from the `wp-prod` vault through secretspec's `onepassword+token://` provider by default. `default` and `development` stay on `env://`, so local development is untouched.
- **sops stays as the local development store.** Each CI-facing secret carries coordinates for both stores (`refs = { op = …, sops = … }`), so selecting `SECRETSPEC_PROVIDER=sops` resolves the same declarations from a local `secrets.sops.yaml` encrypted to the user's own key. That file leaves version control and is ignored from here on; nothing in CI reads it, and the CI age recipient is retired. This is the contributor path: supply your own values, in sops or in any provider, against the committed declarations, with no vault access.
- **Vaults by reference-safe title, items by title and field.** `op`'s secret-reference grammar admits only alphanumerics, `-`, `_`, `.`, and space, so the vaults are titled `wp-prod` and `wp-web` and the aliases name them directly. The production vault groups related values into one item each (`Apple Notary`, `Android Keystore`, `Google Play Store`, `Tauri Updater`, `botswain`), so the 1Password coordinates are `{ item, field }`, with file attachments read by naming the file as the field. The secret declarations do not change, with one exception: the Play Store key is stored as its raw JSON document rather than base64, so that declaration drops its `encoding`. The keystore stays base64 because secretspec cannot carry non-UTF-8 output from the 1Password CLI — 0.19.1 mangles it and 0.21.1 refuses it.
- **Five signing secrets are retired.** `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_DISTRIBUTION_CERTIFICATE`, `APPLE_DISTRIBUTION_PASSWORD`, and `APPLE_DISTRIBUTION_PROFILE` were not migrated and belong to no platform scope — no CI job ever resolves them. Their declarations are removed rather than left pointing at items that do not exist.
- **GitHub environments carry the credential.** Each job that resolves secrets declares the GitHub environment whose work it does — `App Release` for the release builds and publishes, `CI` for release planning and the devenv refresh — and reads `OP_SERVICE_ACCOUNT_TOKEN` from that environment. The repo-level copy of the token is removed once the generated workflows declare their environments. `App Release` and `CI` hold the same service account today; splitting them later is a 1Password change and an environment-secret change, with no edit to the repo.
- **Provider selection scoped to the steps that resolve secrets.** `helpers::named_workflow` stops stamping `SECRETSPEC_PROVIDER: sops` onto every workflow. Each step that runs `secretspec` carries the provider alias and the token, and nothing else in the job sees either. This is a prerequisite as much as a cleanup: the workflow-level stamp is why the weekly `devenv-update` run has failed on every schedule since September — its first step enters `devenv shell`, reads no secret, and dies looking for a `sops` binary the runner does not have.
- **Clean-room build recipes forward the selection.** The platform recipes that scrub the environment (`env -i`) forward `SECRETSPEC_PROVIDER` and the credential for whichever provider is selected, instead of forwarding only the sops key, which today pins those builds to the profile default.
- **Website admin secrets move the same way.** `website/secrets.sops.yaml` is a separate surface: three `website/justfile` recipes shell out to `sops -d` directly, with no CI consumer, and the Worker reads its secrets from Cloudflare at runtime. Its ten values now live in the `wp-web` vault with its own alias, its own `website` profile carrying both coordinate sets, and its own service account in the `Website` environment for the day a deploy job needs it. The three recipes are rewritten over `secretspec export`, so there is one resolver for secrets at rest and no recipe calls `sops` directly.
- **Toolchain follows the consumers.** `op` (the 1Password CLI, which secretspec's provider shells out to) joins the mise base because every CI lane that resolves secrets needs it. `sops` and `age` become shell-only tools: the devenv shell still provides them for local development, but no projected environment carries them because no CI job decrypts.

Nothing here is user-visible. The signing and update keys are the same keys in a different store.

## Capabilities

This change lands in **`toolchain`**, not `distribution`. The registry defines `distribution` as packaging and delivery _outside the Tauri bundler pipeline_ — the Nix overlay and the release record — and the signing material here feeds the bundler pipeline directly. What this change actually governs is how the repository's own CI and shells obtain credentials, which is a reproducibility concern of the same kind as tool projection: it constrains how the repo builds, never what the app does. The automation token was never in doubt; the signing material follows because the mechanism is one mechanism, and splitting it across two domains would spec the same invariants twice. `toolchain` is a tree, so this takes a new area beside `lockfile-integrity` and `tool-projection`.

### New Capabilities

- `toolchain/secret-provisioning`: how CI and shells obtain credentials. Secrets are declared once with coordinates per store; CI resolves from a vault and nothing committed holds secret material; a local development store exists outside version control; a job reaches a credential only through the GitHub environment it declares; provider selection is carried by the step that resolves and by nothing wider; each profile resolves exactly what its consumer needs; a contributor satisfies the same declarations from a provider of their choosing; and the website's at-rest secrets go through the same resolver.

### Modified Capabilities

None. `toolchain/tool-projection` (pending in `mise-env-configs`) specifies how tools are declared and projected, not which tools are declared — moving `sops`/`age` to shell-only and adding `op` to the base are declaration edits under its existing invariants.

## Impact

- **`secretspec.toml`**: `[providers]` keeps `op`, `op-web` (both already in the working copy), and `sops`, and gains `sops-web`; `release` and `automation` default to `op` (`automation` already does); every `release`, `automation`, and `website` secret carries `refs` with both coordinate sets; five declarations are removed; `GOOGLE_PLAY_JSON_KEY_PATH` drops `encoding`; `automation` and the new `website` profile set `inherit = false`.
- **`.gitignore`**: `secrets.sops.yaml` and `website/secrets.sops.yaml` ignored; the files are removed from version control but may stay on disk. `.sops.yaml` keeps only the maintainer's recipient.
- **`tooling/xtask/src/tasks/workflows/_helpers.rs`, `_steps.rs`, `_jobs.rs`**: `named_workflow` loses the `SECRETSPEC_PROVIDER` env; `SOPS_AGE_KEY` and its env pair go; the `SecretSpec` step and the platform `build` step carry the alias and `OP_SERVICE_ACCOUNT_TOKEN`; every secret-resolving job declares its GitHub environment. Every file under `.github/workflows/` regenerates from that.
- **`src-tauri/.just/{macOS,android,iOS}.justfile`**: the `env -i` whitelists forward `SECRETSPEC_PROVIDER`, `OP_SERVICE_ACCOUNT_TOKEN`, and `SOPS_AGE_KEY_FILE`/`SOPS_AGE_KEY`. `linux` and `windows` do not scrub and need nothing.
- **`website/justfile`**: `gen-dev-vars`, `secrets-push`, and `secrets-export` read `secretspec export --profile website` in `dotenv`, `json`, and `shell` format respectively, each with a stated reason.
- **`devenv.nix`**: `op` added to the base (`pkgs._1password-cli`, mise spec `aqua:1password/cli`); `sops` and `age` declared shell-only. `.config/mise.toml` and the lockfiles regenerate; `just check-generated` gates it.
- **Outside the repo** (done, except where noted): two vaults populated; `OP_SERVICE_ACCOUNT_TOKEN` in the `App Release`, `CI`, and `Website` environments. Still to do: the Android keystore re-stored as base64 text, the repo-level `OP_SERVICE_ACCOUNT_TOKEN` and `SOPS_AGE_KEY` removed from GitHub, and the `waypoints-ci` age recipient retired.
- **Risk**: the migration is verified end-to-end only by a real release workflow run, because the signing material cannot be exercised locally by anyone but the maintainer. The CI side rolls back by reverting the generator commit; the sops files are off version control from the first commit by the maintainer's decision, so the un-migrated certificates are regenerated if ever needed, not recovered.

## Non-goals

- Changing how `scopes` partition the release secrets per platform.
- Moving `default` or `development` off `env://`, or changing how `GH_TOKEN` reaches `just mise-lock`.
- Rotating any of the migrated material as part of the move. Rotation becomes a vault edit afterwards; this change only makes that true.
- Any change to what the Worker reads at runtime from Cloudflare's store, or to `wrangler secret bulk` itself — only how the values reach it from the maintainer's machine.
- Declaring a website secret for the `GitHub OAuth Key` item. The Worker reads a token, a client id, a client secret, and an app id, and those map to `GitHub PAT` and `GitHub OAuth App`; the SSH-key item has no consumer today.
- Splitting `App Release` from `CI` into separate service accounts or vaults. The generator declares environments per job so that split needs no repo change when it happens.
- Removing the `require_reason` policy or any audit behavior; every new `secretspec` call site states a reason like the existing ones.
- Upgrading secretspec. 0.21 made secret values byte-preserving in general, but its 1Password provider still rejects non-UTF-8 output from `op` (verified against the keystore with 0.21.1), so an upgrade would not let the keystore be a raw attachment. The pin moves with `devenv update` on its own schedule.
