**The group file's generated outputs.** `release groups schema` writes the schema `schemars` derives from `GroupFile` to `tooling/schemas/release-groups.schema.json` (`release_groups.rs` 30, 430–435; `bin/xtask/tasks/release/groups.rs` 35–41); `version-integrity` refuses a stale schema naming the command (`version_integrity.rs` 486, 501–503, 1036), and `.config/treefmt.toml` (32) and `docs/CONTRIBUTING.md` (171) name it. `release groups project` writes every group's declared version into its member manifests and lockfile entries (`groups.rs` 42–57). `single-source-constants`' ledger lists the schema as a generated output under the name this change retires, and its recipe regenerates it by that name, so this change renames the command and follows the mention.

**What the generator spells, and what pins it.** Every workflow step that runs `xtask` goes through `steps::cargo_xtask` and `CI_TASK` (`_steps.rs` 130); the raw command strings for the store steps and the landing steps are in `_steps.rs` (the stage, upload, manifest, withdraw, dry-index, and land steps named above) and the planner steps in `_jobs.rs::prepare` (94–99) and `release_plan.rs` (94–106). `workflows.rs`'s test module and `_jobs.rs`'s tests pin the spellings — the xtask restructuring rewrote them to `cargo ci-task release prepare`, `release plan`, `release upload --from release --tag`, and the land actions — and `just check-generated` holds the committed YAML to the generator. `release-nightly.yaml` runs every night on its schedule, so a command the generator spells has to exist when the workflow runs.

**What `version-integrity` holds a version write to.** `version_integrity.rs` checks what a pull request claims about versions: the group file and every member manifest and lockfile entry agree (`lockstep_violations`, from `group-file-versions`), a series pins its libraries to tags (`pins`, `pin_violations`, from `library-minting`), the schema is current (486–503), and version writes are the bot's — `group-file-versions`' delta _Only the release bot writes versions_ — authored as `wp-botswain[bot]` (`release_groups::RELEASE_BOT`, 34). Nothing in it today expects a version to move backwards, because nothing ever wrote one back.

**The rulesets `undo` works within.** `tooling/infra/github.tf` protects `main` and `v*.x` (72–104, 110–142): deletion and non-fast-forward forbidden, signatures and a pull request with the required checks required, no bypass actor, and the comment that zero approvals rather than a bypass is what lets the bot's merges proceed "instead of a bypass, which would skip the checks _before_ landing on `main`". The tag ruleset (149–171) covers `refs/tags/v*` and `refs/tags/*-v*`, restricts creation, update, and non-fast-forward, grants the botswain App bypass (162–166), and deliberately has no deletion rule, "b/c a failed nightly deletes the tag it minted" (148). So a revert of a write has to land as the write did, by a pull request; a tag can be deleted by a run; and a series branch cannot be deleted until `protected-versions` drops its deletion rule, which `tag-driven-releases` does.

## Goals / Non-Goals

**Goals:**

- The command line names each part of the pipeline by what it does, and every command the tag-driven pipeline dispatches exists and is tested before any workflow calls it.
- `bump` is the one planner a person or a schedule invokes, asked for a channel or a group, never a transition.
- Nothing a committed workflow runs stops existing: the renames are followed in the generator, the workflows regenerate with today's shapes, and the old planners keep working.

**Non-Goals (design-level, beyond the proposal's):**

- No reading of the series' history for severity: a preview or stable bump still increments mechanically; presence of work is the only thing read.
- No change to the nightly planner's decision or outputs; `bump --channel nightly` and `prepare nightly` are one function with two callers.
- No tag deleted by `undo`; the workflow step deletes the tag, as today.

## Decisions

### D1 (2026-11-20, rule revised 2026-11-21): `release bump` infers the transition from the open series, and `--channel` and `--group` are its two shapes

- **Why:** the four transitions are states of one series, and which applies follows from where the series is. A person choosing `advance` on a series that is already stable, or `cut` while a preview is open, is choosing wrong; the planner knows better than the dispatcher. The library-only cut is the one transition that is not a channel's, and John asked for it to be the flag that excludes the channel.
- **Shape:** `release bump` takes one of `--channel <nightly|preview|stable>` or `--group <name>` (a required, mutually exclusive argument group), `--major` only with `--channel`, `--floor <patch|minor|major>` only with `--group`, and `--dry-run [--into <dir>]`. It runs from `main` and reads the remote: the stable tags, the series branches `v*.x`, and each series' group file at `origin/<branch>` through `git show`, so it knows the open series' declared version without checking it out. For `--channel preview`: a series whose declared version is a preview and is tagged advances when counted commits landed on the series since that tag, and refuses when only bookkeeping did; when the newest series is stable or there is none, a cut from `main` as today, refused while a series is still in preview. For `--channel stable`: a series in preview promotes, with or without new commits, since a promotion declares the candidate final and moves no work; a stable series with counted cherry-picks since its tag patches; otherwise a refusal naming the series, its version, and its tag. The rule under both is John's (2026-11-21): a sequence of bookkeeping commits never moves a tag, on any channel — nightly's `Current` decision applied to a series, reading presence of counted work through `history`'s first-parent walk with bookkeeping excluded, never severity, which the series' history still does not decide. Before any of this, every bump — nightly included — checks that the tree is accounted for: a series whose declared version no tag names, or a `main` whose declared nightly target is more than one minor above the newest series or, with none, the last stable, is a withdrawal in flight (the state `tag-driven-releases`' withdrawal leaves until its revert lands; D4 holds the reader), and the bump refuses naming the version and the revert pull request it finds open. For `--channel nightly`: `plan_nightly`, the function `prepare` keeps calling (D6) — skip when nothing landed, refuse a taken day, else mint `{main's target}-nightly.{date}` at `HEAD` through the App token. For `--group`: today's `plan cut --group --floor`. Everything downstream is unchanged: `cut_target`'s `--major` rule, `Version`'s four arms, `execute`'s checkouts, `open_series`, the dry run's `refs.md` and patches. The inferred transition is reported and published as an output, so a workflow's later steps can branch on it.
- **Rejected:** `bump <channel>` as a positional with `--group` excluding it (clap cannot make a positional optional and conflicting without an awkward `required_unless_present`; two flags read as what they are); a `--transition` override (the point is to stop choosing); inferring a cut's major from the series state (a major stays a product decision no state can prove); re-tagging a declared-but-untagged version on the next bump (the split brain John named; the state is refused and `tag-driven-releases` removes it by revert).
- **Gate:** planner tests over `fixture::Repo`: a preview bump on an open preview with counted work since its tag advances, and with only bookkeeping since refuses naming the tag; on a stable newest series cuts; with a preview open and a cut implied, refuses naming the series; a stable bump on a preview promotes with nothing new since its tag, on a tagged stable with cherry-picks patches, on a tagged stable with none refuses; a declared version no tag names refuses naming it and the open revert, on either channel, and a nightly bump refuses when `main`'s target is two minors above the newest series; a group bump mints on `main` and opens nothing; `--major` with `--group` and `--floor` with `--channel` fail to parse; `the_release_planner_refuses_an_unnamed_crate` and `the_release_planner_refuses_a_stale_projection` hold through `bump` and still through `plan`; `cargo xtask release bump --channel preview --dry-run --into "$dir"` on the tree prints the inferred transition and renders `refs.md`.

### D2 (2026-11-20): Landing is `merge`, `tag`, and `open-series`; the wait stays in the run

- **Why:** `land auto-merge` and `land wait` run back to back in every workflow that lands a write (`release_plan.rs` 121–126, 174–178); the one place that does not wait, the index, is one flag. The `land` prefix was the thing John found opaque. The wait stays inside the run because the alternative, a handler on `push` to `main` and `v*.x`, would start a no-op run on every ordinary merge, which John weighed against the idle runner and declined; `protected-branches` D1 reached the same answer.
- **Shape:** `release merge --pull-request <n> [--no-wait]` enables auto-merge and, unless told not to, waits under `GITHUB_TOKEN` and publishes the merge commit; `release tag --tags <list> --commit <sha>` and `release open-series --version <v> --commit <sha>` are today's actions with the prefix dropped. `release_plan.rs` keeps today's sequence under the new spellings — a token, the planner, the main landing, `merge`, a second token, `tag` for the groups, `open-series`, the series landing, `merge`, a third token, `tag` — and `release_index.rs` runs `merge --no-wait`.
- **Rejected:** `merge` tagging as well (the token minted before the wait has expired by then, and the mint is an action step between the two); a `--then-tag` flag (same reason).
- **Gate:** `the_cli_names_one_step_of_a_landing` becomes three tests over the three commands; the regenerated `release-plan.yaml` carries `release merge` once per landing and `release tag` once per tag set, `release-index.yaml` carries `release merge --no-wait`, and the step ids the token mints are conditioned on are unchanged.

### D3 (2026-11-20): The store steps are `release distributables {rename, upload, commit, withdraw}`, and the module follows

- **Why:** the four share the tag-derived channel, the store client, and the credential lifetime flag, and they are the four things a run does to what it distributes. John chose `distributables` over the two obvious names because "Bundle" is `transload`'s format and "artifacts" is what GitHub Actions calls the handoff between the rename and the upload in the same job. `commit` says what the manifest write is: the publication's commit point (`releases/manifest.rs` 4–13).
- **Shape:** `release distributables rename --platform <p> [--tag <v>]`, `upload --from <dir> --tag <v> [--ttl-seconds]`, `commit --tag <v> [--ttl-seconds] [--dry-run --into <dir>]`, `withdraw --tag <v> [--ttl-seconds]`, each today's task under its new name; `releases::artifacts` becomes `releases::distributables`, `STAGE_DIR` and its readers unchanged. The step names in the generated YAML follow: "Rename the distributables", "Upload the distributables", "Commit the channel manifest", "Withdraw the distributables".
- **Rejected:** keeping `stage` for the rename (it names a directory, not an act); folding `withdraw` elsewhere (it is the store counterpart of `upload`).
- **Gate:** `cargo xtask release distributables --help` lists the four; the generator tests that pin command spellings pass under the new ones; `xfastlane`'s hint and the fastlane documents name `release distributables rename`; `just check-generated` is clean.

### D4 (2026-11-21): `describe`, `record`, and `undo` arrive as tested commands before any workflow calls them

- **Why:** `tag-driven-releases` dispatches three commands the line does not have, and its first regenerated run would otherwise be the first execution of new Rust. Adding them here, with unit tests over `fixture::Repo` and the planner fixtures, makes that change YAML and generator wiring over commands that already work, which is the whole point of landing the two separately.
- **Shape of `describe`.** `release describe --ref <ref>` reads a build's identity from a ref. For a tag, the version is the tag's, and the tree's group file must name the same channel or the command fails naming both, as `releases/index.rs` already refuses (85–95). For any other ref, the version is the group file's app version, with today's UTC date appended when it is a nightly, so a rehearsal from `main` describes the nightly it would be. It publishes `tag`, `version`, `channel`, `flavor`, `version_code`, and `bundle_version` — the two store build codes from `Version::build_numbers` (`releases/version.rs` 301–307), as `prepare` publishes them today (`planners/nightly.rs` 79–82). It is added beside `prepare.rs`, whose `plan_tagged` half it will replace when the workflows turn over (D6); the two share nothing but the parse.
- **Shape of `record`.** `release record --tag <v> [--rev <sha>] [--dry-run [--into <dir>]]` is today's `release index` task renamed, behavior unchanged: classify, refuse a tag whose tree names another channel, prefetch, write the channel's file and publish its landing, or render it dry. `release_index.rs`'s record step and `_steps.rs`'s dry render spell the new name; the workflow's shape is unchanged.
- **Shape of `undo`.** `release undo --tag <v> --commit <sha>` reverts the bump a tag was minted from. It refuses a nightly tag, which has no write, and a commit that is not the merge of the write declaring the tag's version — the tree at the commit must declare it and its first parent must not. For an advance, promotion, or patch it checks the series out, runs `git revert --no-commit -m 1 <commit>` so the reverted write sits in the working tree, and publishes the landing — `head=botswain/release-undo/<series>`, a `chore(release): revert <version> on <series>` title, the paths — in the form the planners publish theirs, for the pull-request action to commit, sign, and open. For a `-pre.1` tag the bump was a cut, which also advanced `main`'s nightly and minted library tags, and the series exists only because of it, so there is no series write to revert into: the command names every `*-v*` tag pointing at the commit's first parent — the cut's `main` write — and the series branch, deletes them through the API, and checks `main` out and reverts that parent the same way, as a `summary:` whose headers name each version the revert restores where the cut moved a library; the one landing a cut's undo opens targets `main` (settled 2026-11-25: the first draft reverted the series write as well, which would have had no base once the branch went, and the second put the `main` revert behind a flag, which left the advanced nightly in place by default). It deletes no `v*` tag; the workflow step does, as today. The logic lives in `releases/undo.rs`, over the fixture repository, and the task is thin. `version-integrity` already admits a bot revert — the bot writes versions, the lockstep clause holds the file and the manifests together, and a summary names its groups — so no clause moves; a test holds the admission and the refusal of the same write by a person. And `planners/release.rs` gains the withdrawal-in-flight reader D1 uses: a series declaring a version no tag names, or `main` more than one minor above the newest series, with the open revert pull request found by its head branch.
- **Rejected:** adding the three in `tag-driven-releases` (two kinds of change in one review, and new Rust first run by a nightly); `undo` deleting the tag and the series itself in one go (the tag step and the series step are the workflow's, conditioned on the event, and the tag ruleset already lets a run delete); `undo` opening the pull request itself (an `xtask`-authored commit, which the proposal's non-goals exclude).
- **Gate:** `describe` unit tests refuse a tag whose tree names another channel, append the date to a nightly manifest on a non-tag ref, and leave a preview manifest's version as is; `record`'s tests are `index`'s under the new name; `undo` unit tests over `fixture::Repo` cover a series write reverted into the working tree with its landing published, a `-pre.1` tag naming the library tags and the series it deletes and reverting `main` under a summary, and the refusals of a nightly tag and of a commit that is not a write's merge; `version-integrity` passes a revert fixture and refuses a hand-made backwards write; the planner refuses on both in-flight states naming the open revert.

### D5 (2026-11-20): `generate schemas` and `generate versions` replace `release groups`

- **Why:** the schema is generated from the `GroupFile` type and held to it by `version-integrity` on every pull request and by a unit test; that is what `generate` is for, and `single-source-constants`' ledger already lists it as a generator. The projection of the group file's versions into the manifests is likewise generation held to its source by `version-integrity`. Neither is a release act.
- **Shape:** `generate schemas` writes `tooling/schemas/release-groups.schema.json` (one schema today; the plural leaves room); `generate versions` runs today's projection. `version_integrity.rs`'s hint and test, `.config/treefmt.toml`'s comment, `docs/CONTRIBUTING.md`, the `check-generated` recipe where it names the schema command, and the active changes' documents spell the new names; `release groups` goes.
- **Rejected:** `release project` (the manifests' versions are generated from the file whether or not a release is near).
- **Gate:** `cargo xtask generate --help` lists `schemas` and `versions`; `version-integrity` names `generate schemas` when the schema is stale; `the_committed_schema_is_the_generated_one` passes.

### D6 (2026-11-21): The old planners stay until the workflows turn over

- **Why:** `release-nightly.yaml` runs every night and its twelve downstream jobs read `prepare`'s seven outputs; `release-plan.yaml` is how a person cuts, advances, promotes, or patches today. Both shapes change in `tag-driven-releases`, and John chose to land the command line first so each change is one kind of work. So this change must leave every committed workflow runnable: a renamed command is followed in the generator and regenerated; a command the workflows still need is not removed.
- **Shape:** `prepare.rs` and `plan.rs` stay, behavior unchanged. `bump --channel nightly` and `prepare nightly` call one `plan_nightly`; `describe` sits beside `plan_tagged` without replacing it; `Plan::tag_minted`, `Plan::SKIP`, and the `should_build` and `dry_run` outputs stay, since `_jobs.rs` reads them. `_jobs.rs::prepare` keeps spelling `release prepare <flavor>` and `release_plan.rs` keeps spelling `release plan <transition>`; nothing dispatches `bump`, `describe`, or `undo`. Every other spelling follows its rename, the workflows are regenerated after each task, and the diff of each committed workflow is confined to the renamed commands and step names. `tag-driven-releases` deletes `prepare.rs`, `plan.rs`, `tag_minted`, `SKIP`, and the two outputs in the task that rewrites the workflows that read them.
- **Rejected:** making `release-plan.yaml` dispatch `bump` by mapping its `transition` input onto a channel (the dispatch form is the workflow change's to redraw, and a mapped transition would be a chosen one in disguise); deleting `prepare` now and having `bump` mint the nightly (the nightly workflow's jobs read outputs `bump` does not publish); leaving the generator spelling the old names and renaming only the commands (the committed workflows would call commands that no longer exist).
- **Gate:** after every task, `just check-generated` is clean, `release-nightly.yaml` carries `cargo ci-task release prepare nightly`, `release-plan.yaml` carries `cargo ci-task release plan`, and `rg` over `tooling/xtask/src` and `.github/workflows` finds no `release stage`, `release upload`, `release manifest`, `release withdraw`, `release land`, `release index`, or `release groups`.

## Risks / Trade-offs

- [Two planners share the nightly path for a while] → one function, `plan_nightly`, with two callers; a divergence would be a second function, which the tests over the nightly fixtures would have to be duplicated for, and are not.
- [`bump` reads the series from the remote, not a checkout] → `git show origin/<branch>:tooling/release-groups.toml` after a fetch; the planners already read tags from the remote by the published spec (_Planners discover tags from the remote_), and `execute` checks the series out afterwards as today.
- [`version-integrity` has to admit a write that moves a version backwards] → only from the bot, only as a revert whose group file, manifests, and lockfile move together; a hand-made backwards write is still refused, and a test holds both.
- [`describe`, `record`, and `undo` have no caller until the next change] → they are dispatched by `main.rs` so no dead-code lint fires, and their tests are what proves them; the first workflow run that calls them is `tag-driven-releases`' audit.
- [The renames touch every committed workflow] → spelling only; `just check-generated` after each task is the proof, and the diff of each workflow is read in review as the renamed hunks and nothing else.
- [The in-flight refusal names a revert that does not yet exist] → until `tag-driven-releases` lands, nothing produces the state; the reader refuses on the version alone and names the pull request when it finds one.
- [`bump` reads every open series' group file off the remote through `GroupFile::parse`] → a series opened before a key changed shape, or a `main` this stack has not reached, fails to parse and refuses every bump until the current shape lands there; that is a one-time landing — by a merge the checks are relaxed for, if it comes to that — rather than a second, looser parser, and the refusal names the file and line (decided 2026-11-25, when the first dry bump on this tree read an `origin/main` whose file still named the blame file by path).

## Migration Plan

1. **The renames** (D2, D3, D5, `record` of D4): `distributables`, `merge`/`tag`/`open-series`, `record`, `generate schemas`/`versions`; the generator's spellings follow; regenerate after each. The diff of every workflow is the renamed commands and step names.
2. **The new commands** (D1, D4): `describe`, `undo` with `version-integrity`'s admission of a revert and the in-flight reader, then `bump` over that reader; nothing regenerates, since nothing dispatches them.
3. **Validation**: hooks green under both feature shapes, `check-generated` clean, the old planners present (D6).

Rollback: every rename is a commit and every new command is a file nothing calls; reverting a step's commit and regenerating restores the previous tree.
