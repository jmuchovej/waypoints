- [x] 7.4 Deep-link registration: with the darwin app linked into `~/Applications`, verify `open "waypoints://"` (or a pairing link) routes to the Nix-installed flavor (spec: "macOS install is LaunchServices-linkable") → **registration verified statically without launching the app; routing still unverified.** `lsregister -dump` shows `waypoints:` claimed under `so.waypoints`, and the bundle owning the claim is a Nix store path — so LaunchServices registers a store-path bundle directly, _without_ the app-linking into `~/Applications` this scenario assumes. Three findings follow:

  1. **The claim is pinned to a stale store path.** The owner is an earlier build, not the current one. Every rebuild yields a new store path, so the registration goes stale on each rebuild, and would dangle entirely if that path were garbage-collected. This is the real argument for app-linking to a stable path — not linkability, which evidently already works.
  2. **Identity collision across installation methods.** `/Applications/Waypoints.app` (an April build) also declares `so.waypoints`, so two bundles compete for the scheme and LaunchServices picked the store path. Not a defect and explicitly out of scope (user decision, 2026-09-27): installing the same flavor twice by different means is the installer's business, not something Waypoints arbitrates. Noted only because it explains which bundle answered during this inspection — the `/Applications` copy here is a hand-installed build, not a Nix one.
  3. **Registration is not routing.** That the scheme resolves to the bundle says nothing about the app receiving and handling the URL through the deep-link plugin.

  **Closed at launch scope (2026-09-28).** `open "waypoints://…"` against the registered store-path bundle **does launch the app**, so LaunchServices resolves the scheme to a Nix-installed build and hands off — which is what the spec scenario ("macOS install is LaunchServices-linkable") asks for. Whether the URL is then _routed_ to a handler inside the app was not observable from the launch alone and is deprioritized by the user; it is a property of the deep-link plugin rather than of the packaging, and no packaging change would alter it. Recorded honestly as launch-verified, routing-unobserved rather than claimed outright.

  **Bug this surfaced**: `build.rs` reads the channel from `WAYPOINTS_FLAVOR` (as `src-tauri/justfile` exports), which the derivation never set — so every Nix package reported `channel = "development"` regardless of flavor, while its product name, identifier, icons and update endpoint were all correct. Note the spec's flavor-identity requirement lists product name, identifier, icons and endpoint but _not_ the channel — worth adding, since it is the one identity field with no other observable.
