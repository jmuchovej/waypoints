## Goals / Non-Goals

**Goals:**

- One definition for every path or name two modules read; the second definitions go.
- One ledger of generated outputs, by generator, that the check, its trigger, and the listing all read, and that a new generator joins with one entry.
- A generator that computes its own placements proves they fall inside its ledger entry before it writes.
- The bytes every generator produces are unchanged; the recipe's answer is today's set plus the schema.

**Non-Goals (design-level, beyond the proposal's):**

- No reading of `sizes.toml` from the generator at run time. The ledger declares roots; Typst keeps the per-flavor patterns.
- No re-export shims: a moved constant is imported from `constants` at every reader, and its old name is deleted.
- No ledger entry for anything the recipe does not regenerate.

## Decisions

### D1 (2026-11-20): `constants.rs` holds what two modules read; what one module alone reads stays beside it

- **Why:** the duplicates in the Context are all paths and names that two or more modules need and that each module spelled for itself. The `license` lift solved the same shape by giving the shared values one module; `xtask` as a whole needs the same, and a module named for what it is — constants — is where a reader looks first.
- **Shape:** `tooling/xtask/src/constants.rs`, `pub mod constants` in `lib.rs`, with no `cfg` so every feature shape sees it. Grouped by what the names are about, each group under a doc comment: the app — `APP` (`Waypoints`), `APP_GROUP`, `APP_MANIFEST`, `ROOT_MANIFEST`, `LOCKFILE`; the group file — `GROUP_FILE`, `SCHEMA_FILE`, and `BLAME_IGNORE_FILE`, which `explicit-group-ownership` D7 added after this design was written and which the group file, the history walk, and the index fixture read; the repository and its bot — `REPOSITORY`, `RELEASE_BOT`, `RELEASE_BOT_EMAIL`, `MAIN`, `RELEASE_PLAN_HEAD_PREFIX`, `RELEASE_INDEX_HEAD_PREFIX`, `DEVENV_UPDATE_BRANCH`; the generated tree — `WORKFLOWS_DIR`, `TFVARS`, `BINDINGS` (three paths), `ICON_ROOTS` (four globs), `NOTICES`, and the ledger of D2; the licensing inputs the checks read — `THIRD_PARTY_REGISTRY`, `ABOUT_CONFIG`, `ABOUT_TEMPLATE`; the release store — `INDEX_DIR`, `STAGE_DIR`, `APP_STORE_INFO`; scratch — `SEMVER_SCRATCH`. The criterion is mechanical: a constant moves when two modules read it or the ledger names it. Everything else stays where it is — `license`'s `POLICY`, `HOLDER`, the SPDX tags, and its frozen documents; `headers::{PERMISSIVE, HEADER_EXTENSIONS, SCRIPT_DIR, DENY, NUXT_CONFIG, NUXT_ALLOWLIST}`; `notices::{FRONTEND, FIRST_PARTY_SCOPE}`; `tools::mise::MISE_TOML`; the crons, the bucket and its permission, `CI_CACHE_BUCKET`, `CI_TASK`, the env names, `PRE` and `NIGHTLY`, `COVENANT` and `SUMMARY`, the dev server's header and default flavor.
- **Rejected:** every constant into one file (a sixty-entry list in which the only reader of `CRON` has to look elsewhere for it); re-exports from the old homes (two names for one value is the duplication by another route, and a reader following `release_groups::GROUP_FILE` would never learn where it lives); one `paths` submodule per domain (the point is one place to look).
- **Gate:** clippy, check, and the suites green under `cargo xtask` and `cargo ci-task`; `cargo xtask generate workflows --check` in sync, since a move changes no output; `rg` over `tooling/xtask/src` outside `constants.rs` finds no second `const` for a moved name and, outside `#[cfg(test)]` fixtures, no literal `wp-botswain[bot]`, `.github/workflows`, `"main"`, `"Cargo.lock"`, `.config/about.`, `.config/third-party.toml`, or `THIRD-PARTY-NOTICES.md`.

### D2 (2026-11-20): The ledger is one entry per generator, in `constants`; devenv's outputs alone are read at run time

- **Why:** the check needs globs at generation time for the trigger and at run time for the diff; the listing needs them at run time; a new generator should extend all three with one edit. A static table in `constants` is readable from every shape of the binary, including `cargo ci-task`, where the icon generator is not compiled but its outputs still have to be watched.
- **Shape:** `pub struct Generated { pub name: &'static str, pub sources: &'static [&'static str], pub outputs: &'static [&'static str] }` and `pub const GENERATED: &[Generated]`, in this order: workflows (sources `devenv.nix`, `devenv.yaml`, `devenv.lock`, `tooling/xtask/**`; outputs `WORKFLOWS_DIR/**`, `TFVARS`), bindings (sources `crates/domain/**`, `crates/cartograph/**`; outputs `BINDINGS`), icons (sources `src-tauri/res/**`; outputs `ICON_ROOTS`), notices (sources `LOCKFILE`, `pnpm-lock.yaml`, the three licensing inputs; output `NOTICES`), schema (sources `tooling/xtask/**`; output `SCHEMA_FILE`), devenv (sources `devenv.nix`, `devenv.yaml`, `devenv.lock`; outputs empty — `managed_files` supplies them at run time, as `WorkflowContext` does today). Readers fold it themselves: `check_generated.rs` collects every entry's sources, then every entry's outputs, then `context.devenv_files`, deduplicated in first-seen order, into the trigger; `ls managed` prints every entry's outputs then devenv's. The glob dialect is the intersection of what GitHub's `paths:` filter, git's pathspec, and jj's `glob:` fileset accept — `*` within a component and `**` across — which is what every entry already uses.
- **Rejected:** a trait each generator module implements (the icon generator is behind `local-dev` and the ledger must not be); discovering outputs by a header sweep for everything (a PNG carries no header; the workflows' sweep stays what finds an orphan, the ledger is what the check watches); a separate `generated.rs` beside `constants.rs` (the entries are constants, and John asked for one module).
- **Gate:** a test that every ledger output and source appears in the rendered trigger's `paths:`, and that no path appears there which the ledger or the context does not name; `the_committed_tfvars_are_the_generated_ones` unchanged; after regeneration, the diff of `.github/workflows/check-generated.yaml` is confined to `on.pull_request.paths` and `on.push.paths`.

### D3 (2026-11-20): The icon entry declares roots; the generator proves every placement and prune is inside them

- **Why:** the icons' fine-grained ownership is per flavor and comes from `sizes.toml` through the render, so it cannot be read without rendering, and rendering needs `typst` and the `local-dev` feature. The check does not need the files, though; it needs the roots a deletion is visible under, which the recipe's own comment (116–119) says is why it diffs locations and not files. Four static roots state that; what has to be proven is that the generator never steps outside them.
- **Shape:** `ICON_ROOTS` is `src-tauri/assets/icons/app/**`, `src-tauri/gen/apple/Assets.xcassets/*.appiconset/**`, `src-tauri/gen/android/app/src/*/res/mipmap-*/ic_launcher*`, and `src-tauri/gen/android/app/src/*/res/values/ic_launcher_background.xml` — the recipe's spelling, which is the precise one; `OUTPUTS`'s `res/**/ic_launcher*` goes. After `icongen::generate` reads the manifest and before it places anything, every output and every path `prune` would remove, prefixed with `src-tauri/`, has to match one root under the existing `MATCH` options, or the run fails naming the path and the roots, beside the owned-pattern check it already makes (108–119). A unit test expands `sizes.toml`'s `file` and `dir` templates for every flavor in `short` and asserts each falls under a root, so CI, which does not render, still proves the roots cover the data.
- **Rejected:** the generator deriving the roots from `sizes.toml` at run time (a second reader of the layout data and a per-flavor expansion in Rust, to compute what one static line states and the run-time assertion proves); Typst reading the roots from Rust (no channel exists, and the render is the wrong place for the check's concern); moving `owned` out of Typst (the per-flavor and all-flavors prune rules are the render's business, and `app-icons` keeps sizes and formats as data).
- **Gate:** a synthetic manifest placing `assets/icons/other.png` is refused naming the path; the `sizes.toml` test passes; `cargo xtask generate icons` on the tree changes nothing.

### D4 (2026-11-20): The bindings write to the ledger's paths; the schema joins the check

- **Why:** the binding paths are the one output the ledger cannot read today, because the bin derives them from `cargo metadata`; a crate directory is not going to move without the ledger moving with it, and the ledger is what the trigger must be generated from. The schema is already held byte-for-byte by a unit test; the recipe is where every other output is held, and a reader of `ls managed` should see it.
- **Shape:** `BINDINGS` names `crates/domain/typescript/types.g.ts`, `crates/domain/typescript/schema.g.ts`, and `crates/cartograph/typescript/types.g.ts`; `generate/bindings.rs` writes `Exports`'s three fields to `workspace_root.join(path)` and stops asking `cargo metadata` for crate directories; `typegen::Exports`'s field docs point at the constants. The recipe runs `cargo xtask release groups schema` beside the other regenerations, and `the_committed_schema_is_the_generated_one` stays as the in-process signal, since the suite runs before the recipe would. `NOTICES` replaces `license::NOTICES_PATH`, and `lib.rs`'s `license` block keeps the policy constants and the frozen documents, which only `license` reads.
- **Rejected:** keeping the metadata-derived directories and asserting they equal the ledger (two sources with a check between them, for a path that is a literal); dropping the schema's unit test once the recipe covers it (the recipe needs devenv and a shell; the test runs under `cargo test`).
- **Gate:** `cargo xtask generate bindings` changes nothing and writes the three ledger paths; `just check-generated` fails naming a hand-edited schema.

### D5 (2026-11-20): `ls managed` prints the ledger; the recipe keeps no list

- **Why:** `ls managed` was added to list devenv's files and named for the broader thing; with the ledger it can be the broader thing, and the recipe can stop being the third list.
- **Shape:** `ls managed` prints every ledger entry's outputs in ledger order, then devenv's files — `copied_files` under `--copied`, else `managed_files` — one per line, globs as written. The recipe becomes: list, regenerate each generator (bindings, icons, notices, schema), diff the list, run `generate workflows --check`; `set -f` and the jj `glob:` rewrite stay, since the list now carries globs for every reader. The recipe's closing message prints the same list.
- **Rejected:** expanding globs to the files that exist (a deleted output must show as a deletion, which only its root can); a `--sources` flag (no reader); JSON output (one consumer, a shell `for`); a `--by <generator>` filter (nothing asks).
- **Gate:** `just check-generated` passes on a clean tree and fails naming a hand-edited binding, icon, notices line, and schema; `cargo xtask ls managed --copied` prints the ledger's outputs followed by devenv's copied files and nothing else.

### D6 (2026-11-20): Which duplicates fold, and into what

- **Why:** the Context's list is exact; each duplicate gets the one name it folds into so the moves are mechanical.
- **Shape:** `RELEASE_BOT` keeps `wp-botswain[bot]` and `RELEASE_BOT_EMAIL` takes `_helpers`'s address; `_helpers`'s git identity reads both and `BOTSWAIN_GIT_USERNAME`/`BOTSWAIN_GIT_EMAIL` go; the three step names stay prose. `MAIN` is read by `pull_request.rs`, `check_generated.rs`, `release_index.rs`'s `ref:`, and the two bin tasks' `describe`. `RELEASE_PLAN_HEAD_PREFIX` replaces `planners::HEAD_PREFIX`; `RELEASE_INDEX_HEAD_PREFIX` (`botswain/release-index/`) replaces the inline format in `releases/index.rs`; `DEVENV_UPDATE_BRANCH` replaces `devenv_update::BRANCH`. `LOCKFILE` is read by the planners, `planners/test.rs`'s list, `_steps.rs`'s cache key, and the notices entry. `WORKFLOWS_DIR` is read by `WorkflowFamily::path`, the zizmor step, `devenv_update`'s paths, and the workflows entry. `THIRD_PARTY_REGISTRY`, `ABOUT_CONFIG`, and `ABOUT_TEMPLATE` are read by `headers.rs`, `notices.rs`, and the notices entry. Test fixtures keep their literals — a fixture is a foreign file's content — and a test that compares against a path uses the constant.
- **Rejected:** formatting the step names from `RELEASE_BOT` (they say "wp-botswain" without `[bot]`, as a person reads a run); a `BOT_BRANCH_PREFIX` of `botswain/` composed at each site (the two prefixes are read whole, and composition is a second spelling).
- **Gate:** D1's `rg` clause.

## Risks / Trade-offs

- [A wide mechanical diff across some fifteen modules] → pure moves land first (Migration 1) with the workflows proving byte-identical, so the review of the ledger and the generators (2, 3) is small.
- [Three glob dialects — GitHub `paths:`, git pathspec, jj fileset] → the ledger uses `*` and `**` only, as every entry does today; the recipe's jj branch already rewrites `*` entries to `glob:`.
- [The icon roots are wider than the files] → by design: a removed output is visible only under its root (justfile 116–119), and D3's run-time assertion bounds the generator to the roots.
- [`tag-driven-releases` task 1.2 adds `.github/actions/**` to the generated outputs and `devenv_update`'s paths] → it lands after this change and edits the ledger's workflows entry and `WORKFLOWS_DIR`'s neighbor instead; one line each, named in Follow-ups and in that change's tasks.
- [The `sizes.toml` test is a second reader of the layout data] → test-only, and it reads two keys per platform; the run-time assertion is the invariant, and if the TOML's shape changes the test names the key.
- [`ls managed` now prints globs as well as files] → it has one caller, the recipe, which already treats its lines as pathspecs under `set -f`.

## Migration Plan

1. **The constants** (D1, D6): `constants.rs`, every reader imports, every old definition deleted; regenerate. The workflows are byte-identical, which is the proof the move changed nothing.
2. **The ledger and its readers** (D2, D5): `GENERATED`, `check_generated.rs`'s folds, `ls managed`, the recipe; regenerate. The trigger's path list is the diff.
3. **The generators** (D3, D4): the icon assertion and its `sizes.toml` test, the bindings' paths, the schema in the recipe.

Rollback: every file is generated or a move; reverting a step's commit and regenerating restores the previous tree.
