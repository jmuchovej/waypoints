## Goals / Non-Goals

**Goals:**

- One planner mints every group's version on `main`; a library tag always names a commit the planners' first-parent walk contains.
- The bump for every group is `max(declared, evidence)`, and the tests that prove it simulate a `1.x` base so pre-1.0 right-shifting cannot hide a severity bug.
- Each channel is its own build of released library versions: a series compiles the tags it pins under its own flavor, `main` compiles the in-tree libraries under nightly's, and a cherry-pick cannot change a series' bill of materials by accident.
- Every check this change adds is inert on the tree as it stands — no pin, no tag — and arms itself from what the first minting cut creates, so landing it blocks nothing.
- Everything is derivable: the bill of materials from the pins, the group of a path from the group file, the build data from the tree or the lockfile.

**Non-Goals (design-level, beyond the proposal's):**

- No second source of versions: no ledger file, no version field in the group file, no version in any Tauri config. A series' pins are dependencies, not a version source.
- No new checker for behaviour. API breaks come from `cargo semver-checks`; data breaks come from fixtures; everything else is a declaration.
- No new GitHub client or transport. The cut's writes reuse the pull-request path `protected-branches` lands and the `octocrab` calls already in `tools/github.rs`; a group tag is one more `create_tag`.
- No library series branches. A library's tags live on `main` only; a line that has broken there is shipped by a new app cut, not patched (D1).
- No change to the format of a summary or to which checks gate it; that is `release-groups-guards`. This change reads summaries.
- No release, record, or index entry for a library. A group tag is a source ref the series' lockfile pins, not a publish (D1).
- No credential plumbing for git dependencies. The repository is public; the day that changes, D7 says where the plumbing goes.

## Decisions

D1–D7 carry the monolith's decisions, dated as they were settled and revised; D8 answers the two hazards review found. Each `AUDIT` needs sign-off.

### D1 (2026-10-11, revised 2026-11-26): Library versions are minted on `main` by a cut, and a series takes a library fix by cherry-pick

(monolith D3)

- **Why:** with `publish = false` and no channels, a library release has no reader but the app. Minting at the app's cut gives each series a coherent bill of materials — the versions its group file records — and a baseline the API floor measures the next cut against; minting on demand with a group-scoped cut records a library's line between app cuts. Both happen on `main`, so a library tag always names a commit the planners' walk contains.
- **Sequence of an app cut:** (1) `release bump` computes each library group's next version under right-shift; (2) botswain opens a pull request to `main` with one summary commit carrying every `main`-side write — each changed group's manifests and `main`'s provisional `{next minor}-nightly` bump — and enables auto-merge; (3) the required checks run and it lands as a merge commit; (4) the same run, which has waited for that merge as it already does for the app's tag (`wait_for_merge`, then a token minted after the wait), tags each planned group at the merge commit and cuts `v{minor}.x` from it; (5) the series' first pull request writes the app's version (D7), gated by the same checks, landed as a merge commit, then tagged. Advance, promote, and patch follow (5) for the app version. (Revised 2026-11-16: the draft had phase two on a merge event; `protected-branches` landed the wait inside the run, so there is no second trigger and no handler to guard. Revised 2026-11-26: step 5 no longer rewrites dependencies; a run that fails between (4) and (5) is finished by a resume, D9.)
- **A group-scoped cut** (`bump --group bedrock [--floor patch|minor|major]`) runs (1)–(4) for one library: one `chore(release): bedrock 0.2.1` header, one tag, no branch, no app movement, no release workflow. It refuses with nothing counted; a floor raises the bump and never lowers it.
- **How a library fix reaches a series** (revised 2026-11-26). As any fix does: it lands on `main`, soaks in nightly, and is cherry-picked onto the series through a pull request, which version-integrity holds to the file like any other; `patch` then bumps the app. The library's version in the series' group file stays what the cut minted, and the build data describes the drift past the tag (D6, D7). The 2026-10-29 shape — a group-scoped cut minting `bedrock-v0.2.1` and `patch` moving the series' pin to it, refusing where the line had broken on `main` — went with the pins; with no pin to move, a broken line on `main` is no obstacle to a cherry-pick that carries exactly the fix.
- **Tags go on the merge commit.** `main`'s first-parent history contains the merge commit, not the PR branch's commit, so a tag made before the merge would name a commit the planners never walk. Each tag is one `tools::github::create_tag` call, as the app's are.
- **A library tag is not a release.** It has no artifact, no release record, and no index entry: it is a version marker on `main` (D7). The published election and withdrawal rules (`release-publishing`) concern the `v[0-9]…` tags that trigger a channel's run, and the index workflow's `v*` trigger records app releases only; `bedrock-v…` matches none of those patterns, so a group-scoped cut starts no run, no run can withdraw a group tag, and no index entry names one. The question the monolith left open — whether the index entry waits for the build — is answered by the published `release-index` requirement: the entry follows the tag, by the trigger, and a failed build after it leaves a valid release; nothing here changes that.
- **The commit** (revised 2026-11-16): subject `summary: cut 0.3.0-pre.1`; body one `chore(<group>): <version>` header per changed group, scoped by the group's name as the summary guard requires, plus `chore(waypoints): main now targets 0.4.0-nightly` for `main`'s own bump. A cut that moves no library keeps today's `chore(release): main now targets …`, and a library alone lands as `chore(release): <group> <version>`, the subject reserved to the bot. The planner writes every changed manifest into the working tree and the pull-request step commits them together under that message, restricted to the manifests it names — one commit for the whole cut, which the Contents API cannot do. The walk reads every commit the bot authored as bookkeeping, so the summary never counts as the next cut's work, whatever its subject.
- **No tag yet** (added 2026-10-29). The first minting cut finds no `<group>-v*` tag for any group. A group's current version is then its anchor manifest's, and the whole first-parent history is its cycle — the rule `log_range` in `planners/release.rs` already applies to the app before its first release, which is also where the app stands: no stable tag exists, so its first cut is measured from `0.0.0` over the same history. The API floor has no baseline and skips, saying so (D5); declarations and the fixture floor still apply.
- **The bookkeeping marker is `chore(release):`, not a new type.** `baf7e109` made every planner message `chore(release): …` after an earlier cut minted its tag and then failed to draft release notes under `require_conventional`; `.config/cliff.toml` already skips `^chore\(release\):`, and a test holds the planner to the prefix. The per-group headers in a cut's body use the same form.
- **Tokens:** every pull request botswain opens, and the merge that lands it, uses the App token, as `devenv-update` already does and `protected-branches` extends to the planners. The same token mints the tags and branches, which is what the published requirement _Release refs are minted so their pushes are observable_ demands.
- **Rejected:** a ruleset bypass pushing straight to `main`; releasing libraries on merge (bookkeeping at random times wakes nightlies); minting at promote (libraries live on `main`); tagging from the first phase (names a commit outside first-parent history); library hotfix tags on the app's series branch (the app's patch tags live there, but the library tag would then not be on `main`); a hotfix tag on `main` that drags a breaking change along (semver-dishonest); recording group tags in the release index (they are not releases).
- **Gate:** `release-plan cut --dry-run` prints every group's current and next version and the pull request it would open, and with `--into` renders them into the rehearsal's artifact — each group's tag in `refs.md` beside the app's, each changed library manifest's write in `main.patch`, where the summary commit lands them — so the workflow's default dry dispatch audits a cut before any ref exists; the first real cut (2026-11-26) showed one landed summary merge (#183), its four tags on the merge commit, and `v0.1.x` cut from it, with no release run started; a group-scoped cut lands one tag and nothing else — no release run, no index entry; `patch` on a series bumps the app and moves no library version.

### D2 (2026-10-11): Groups own disjoint paths; the app counts what it ships

(monolith D4)

- **Why:** paths cannot misreport, while scopes are optional and unchecked.
- **Ownership:** each library group owns its members' directories. `waypoints` owns everything else except `tooling/` and bookkeeping: `src-tauri`, `cartograph`, `store`, and the frontend. The mapping reuses the longest-prefix rule `test::owning_package` already applies, extended from crates to groups; the group file `release-groups-guards` lands is where the members are read from.
- **Counting:** a library counts commits touching its own paths. The app counts its own paths plus every group's, because the binary ships them; a `fix(bedrock)` is a user-facing fix.
- **Walk:** first-parent, with each merge diffed against its first parent, so a pull request is one commit with the merge message. The nightly planner shares the walk and so becomes first-parent too; its decision — did anything land — is unchanged, since a landed pull request is still one commit.
- **History the walk needs:** full, as the planner jobs already check out. Attributing by path makes that requirement sharper rather than new — a shallow tip is a root commit diffed against the empty tree, so every path would look changed — and the workflow test that holds planner jobs to a non-shallow checkout keeps covering it.
- **Bookkeeping:** `distribution/nix/releases/`, commits listed in `.git-blame-ignore-revs`, botswain's `chore(release):` subjects, and every commit botswain authored count toward no group. The bot authors the merge commits of its own pull requests, so the author rule (added 2026-11-16) is what keeps a cut's `summary: cut …` commit out of the next cycle; the subject rule stays as the group file states it.
- **Rejected:** scope-based attribution.
- **Gate:** tests on the existing `fixture::Repo`, grown to make merges and body-carrying commits: a `bedrock-core`-only commit counts for `bedrock` and `waypoints` only; a tooling-only, ignored-rev, or `chore(release):` commit counts for none; a three-commit pull request counts once.

### D3 (2026-10-11, revised 2026-10-19): A summary is read one header per group

(monolith D5, the reading half)

- **Why:** one header, many groups. Rather than parse multi-scope subjects, a multi-group commit's subject summarizes, and its body carries one header per touched group. This is the convention release-please uses for [multiple changes in one commit](https://github.com/googleapis/release-please#what-if-my-pr-contains-multiple-fixes-or-features).
- **Where the format is decided:** the `summary` type, the one-header-per-group body, the merge message being the pull request's title and description, and the gate that holds a summary to exactly one header per touched group are `release-groups-guards`'; the repository setting that keeps the body at merge is `protected-branches`'. This decision is what a planner does with a summary once the gate has passed it.
- **Where it is read from:** the merge commit. Branch commits underneath are never read by a planner; `--first-parent` skips them, and the PR's diff is the merge commit's diff against its first parent.
- **Severity:** each group reads its own header; the subject counts for no group. A `!` in a library's header breaks that library; `!` never breaks the app (D4). The app's declared type is the highest among the commit's headers.
- **Single-group commits** keep free-form scopes; the path decides the group. CONTRIBUTING's comma-joined regions stay legal only while every region falls in one group — `refactor(app,store): …` is one `waypoints` commit; `refactor(domain,cartograph): …` must be a summary.
- **Library rules:** Cargo's 0.x right-shift (feat → patch, break → minor), which `next_version`'s defaults and cargo-semver-checks both assume. This is what makes a library hotfix tag on `main` honest (D1): everything that landed since the pin on an unbroken line is patch-level by definition.
- **Rejected:** multi-scope subjects such as `feat(bedrock,outpost)!:`; an unscoped `!` applying to every touched group.
- **Gate:** tests for a two-header summary and a single-group commit with a free-form scope, each on a `1.x` base; the format-side tests (a summary missing or naming an untouched group) are the guards'.

### D4 (2026-10-11): The app's only breaking signal is a `Covenant: break` trailer

(monolith D6)

- **Why:** the app's contract is the data covenant (continuity, egress, interop), not Rust APIs. A wire-protocol break is an interop break, so it needs the trailer even though the code lives in `outpost`.
- **Reading it:** the walk reads trailers (`%(trailers:key=Covenant,valueonly)`), not only `%s`. The trailer applies to the whole commit, summaries included.
- **Severity:** feat → minor even in 0.x, unchanged. Before 1.0 a trailer still yields a minor, but it is recorded, and each one is an entry in the covenant exemption log that `git log --grep` can answer.
- **App majors are human-triggered.** A major for `waypoints` is a product decision, which no commit can prove. The cut targets a major for the app only when a person passes `release-plan cut --major`. The trailer is the floor, not the trigger: a `Covenant: break` since the last stable makes a cut without `--major` refuse, naming the commits, rather than cut a silent minor or an unreviewed major. `--major` without a trailer is allowed. Library majors stay automatic, since their contract is a Rust API the checkers can see.
- **`cartograph` API breaks never floor the app.** cargo-semver-checks on `cartograph` runs against the last `v*` tag as PR information only; its sole consumers are `src-tauri` and the frontend, in lockstep, so an API break there is internal.
- **The `!` already in history stays meaningful to its own group.** `feat(outpost)!: deployable Station` and its siblings break `outpost` under D3 while leaving the app's version to the trailer, which is exactly the split this decision wants.
- **Rejected:** honouring `!` or `BREAKING CHANGE:` for the app.
- **Gate:** tests on a simulated `1.2.0` base: `feat!:` without the trailer targets `1.3.0`; a commit with the trailer makes `cut` refuse and `cut --major` target `2.0.0`; `cut --major` with no trailer also targets `2.0.0`.

### D5 (2026-10-11, revised 2026-10-29): Severity is the greater of declared and detected, measured on the stable surface

(monolith D7)

- **Why:** a floor stops a mislabeled commit from producing a wrong version; the PR check stops it from reaching history.
- **API floor:** `cargo semver-checks --baseline-rev <group tag> --features stable` for each library-target member of `bedrock`, `outpost`, `domain`, and `transload`. The proc-macro `bedrock-derive` is declared-only. The tool joins the toolchain through `devenv.nix` like every other tool, projected to the `xtask` mise lane. _Implemented 2026-11-16, without `--baseline-rev`:_ the tool builds each side as a throwaway project depending on the crate, which resolves every dependency afresh — outside the lockfile and the root `[patch]` table — and fails on what they pin (derive_more's `display` grammar, on this tree). So `semver_check` documents each side itself, `cargo rustdoc --lib --features stable` as rustdoc JSON in the crate's own workspace — the baseline tag checked out as a worktree under `target/semver-checks/` — and hands the two JSONs to `check-release`. The app's own crate is left out of its group's measurement: its library target exists for the mobile bindings, its contract is the covenant, and its build drags the GUI toolchain in; `cartograph` is measured, and reported as information only. The `semver` job sits beside `version-integrity`, and the generator lists it among the required checks.
- **Why the stable flavor** (revised 2026-10-29). Once libraries gate behaviour on flavors (`channel-flavors`), a library has three API surfaces. The one every series consumes is the stable one, so that is the contract: an item that exists only under `nightly` or `preview` can change or vanish without breaking any series, and the check must not count it. A nightly-gated change decides its own bump by its header alone. This is also what `patch` reads to tell an unbroken line from a broken one (D1): the same check, same flavor, against the series' pin.
- **No baseline, no measurement** (added 2026-10-29). No `<group>-v*` tag exists until the first minting cut, and `--baseline-rev` needs one. A group with no tag is skipped, at PR time and at cut, with a message naming the group and saying the first cut will mint its baseline; declarations and the fixture floor still apply. Without this the `semver` job would fail every library pull request between landing and that cut (D8).
- **Fixture floor:** a modified, deleted, or renamed file under `covenant/fixtures/<group>/` since the last stable tag is breaking for that group and for the app. The group's own `covenant/fixtures/<group>/README.md` describes the directory and is not a fixture, so editing it sets no floor; the exemption is that exact path, as in the append-only rule. The directories and that rule are `release-groups-guards`'; the floor at cut is here.
- **PR asymmetry:** an undeclared break fails; an over-declared break passes, since behaviour changes and macro output escape the checkers.
- **Rejected:** evidence alone (misses semantic breaks); messages alone; checking every flavor's surface (a nightly-only item is by definition not a contract anyone outside nightly holds); failing a group with no tag (blocks every library PR for the wrong reason).
- **Gate:** fixture-repository tests where evidence exceeds the declaration, at PR time and at cut; a nightly-gated removal reports no break under stable; a group with no tag skips with the message and a group with one measures.

### D6 (2026-10-11, revised 2026-10-29): Builds embed every group's version alongside `BuildInfo`

(monolith D12)

- **Why:** a bug report should name the `bedrock`, `outpost`, `domain`, `transload`, and app versions it ran, not only the app's.
- **Shape:** a structure carried alongside `BuildInfo`, baked by `src-tauri/build.rs`, one entry per group. It is registered with typegen like `BuildInfo`, so the bindings stay generated, and `--version` prints it.
- **Where the value comes from** (revised 2026-11-26): an injected value first, as `build.rs` already takes `GITHUB_SHA`; then `git describe --tags --match '<prefix>*'` against the tree — on `main` the group's latest tag, on a series the tag the branch descends from, so a cherry-picked library fix reads as commits past it (`bedrock-v0.1.1-2-g…`); then the group file's declared version, so a shallow local clone never fails to compile and never claims more than the file says. The 2026-10-29 shape read the tag `Cargo.lock` pinned on a series; that step went with the pins (D7).
- **Nix:** the overlay builds a fetched tag carrying no git metadata, so it injects the group file's declared versions, read with `builtins.fromTOML` as `distribution/nix/channel.nix` already reads the app's. That reader takes strict TOML 1.0; `crates/outpost` and the root already pin that dialect with `#:tombi toml-version = "v1.0.0"`, and `crates/bedrock`, `crates/domain`, and `crates/transload` gain the same directive.
- _Implemented 2026-11-16:_ `GroupVersion` rides in `BuildInfo.groups`; `src-tauri/src/group_versions.rs` holds the resolution in that order and is included by path into `build.rs`, which reads the group file for the groups and bakes `WAYPOINTS_GROUP_VERSIONS` as `group=version` pairs — the same variable a build takes injected values from. The Nix recipe injects it from the group file. (Until 2026-11-26 both read the lockfile's pins first, through `distribution/nix/lockfile.nix`; 7.3 removes that reader.)
- **Gate:** a `main` build at `bedrock-v0.4.0` reports it; a series build after a library cherry-pick reports the described drift past the group's tag while its group file still declares the cut's version; a Nix build reports injected values.

### D7 (2026-10-29, revised 2026-11-26): A series builds in-tree, like `main`; its tags are a bill of materials, not a build input

(monolith D18)

- **What the first cut showed** (2026-11-26). As first designed, a series pinned every library group to its own tag. The real cut landed `main`'s summary (#183, `5c50d3a9`), minted `bedrock-v0.1.1`, `domain-v0.1.1`, `outpost-v0.2.0`, and `transload-v0.1.1` on it, and cut `v0.1.x`; the series pull request (#184) then failed every compile. Cargo makes each git tag a distinct source, and a fetched `transload-v0.1.1` resolves its own `domain` and `bedrock` by path inside its checkout, so they arrive under the transload tag's source rather than `domain-v0.1.1`'s. The series lockfile held four copies of `bedrock-core`, one per group tag, all at the same commit, and `store` failed with the trait `Collection` defined twice. The one escape cargo offers, `[patch."<repository url>"]`, is refused when the patch names the same repository ("patches must point to different sources"), reproduced on #184's tree. Intra-repository path dependencies between groups and per-group tag pins do not compose under cargo without a registry.
- **Why in-tree** (John, 2026-11-26). Three shapes would have kept pins: one `rev` per series (every group from the cut's merge commit — builds, but a `patch` then moves every pin together and the per-group tags become markers a series may not honor); cascade minting (every cross-group dependency spelled `git` + tag, `main` patching that URL to paths, and every dependent group re-minted whenever a dependency moves — correct and version-honest, and it re-tags three groups for a bedrock fix); or a registry for the library crates. None is worth its weight for libraries whose only consumer is this app. A series builds its libraries from its own `crates/`, exactly as `main` does.
- **What the tags are.** Each group's tag on `main` is a version marker: the semver baseline the API floor measures the next cut against (D5), the version the group file records as the series' bill of materials, and the version a build describes (D6). No build fetches a tag. On a series the group file keeps the versions the cut minted; the series' library code may move by cherry-pick, and the build data says so.
- **Mechanism.** The series' first pull request after a cut is the app's version projection alone — the group file's app version, the app's manifests, and the lockfile's app entries — the write an advance makes. Nothing rewrites `[workspace.dependencies]`, nothing leaves `[workspace].members`, and no `cargo update` runs. `patch` on a series is an app patch bump: a library fix reaches a series as a cherry-pick of a commit on `main`, reviewed and landed like any app fix, under the published _A series branch carries only cherry-picks of `main`_. version-integrity's series-pin and single-pin checks, which existed to protect pins, go (D8).
- **Nix.** The Station builds in-tree on every ref: the overlay's pinned-Station path and `lockfile.nix`'s pin readers go, and the `nix-overlay` delta this change carried (_A series builds the Station from its pin_) is withdrawn, so the published requirement stands as written. crane stays as the builder: chosen for vendoring pinned sources, it is the better builder regardless (3.4), and nothing now turns on it.
- **Rejected:** the pin design, for the reason the first cut gave; one `rev` per series; cascade minting; a registry; building in-tree with an equality check against the tag (the tag is a marker, and drift past it is a cherry-pick someone reviewed).
- **Gate:** `cargo metadata` on `v0.1.x` resolves every group from the tree with one copy each; the series' first pull request changes the group file's app version, the app's manifests, and the lockfile's app entries and nothing else; a cherry-pick of a library fix onto a series passes version-integrity; `nix build .#outpost` on a series ref builds the in-tree Station; the resumed first cut (D9) lands `v0.1.0-pre.1` and its release run builds.
- **The design it replaces**, kept for the record:
- **Why:** a channel is a build of _released_ library versions, and a tag is the trivially checkable guarantee of what "released" means. Building a series from its own `crates/` would mean the series ships whatever cherry-picks happened to touch a library; building from the tag means it ships exactly the bill of materials the cut recorded, and a cherry-pick cannot change that by accident.
- **Mechanism:** the series' first pull request after a cut rewrites every library group's dependency in the series' manifests from `path = "crates/…"` to `git = "<this repository>", tag = "<group>-v<version>"`, removes the library crates from the series' `[workspace].members`, and regenerates `Cargo.lock`, which then pins the tag's commit. On this tree the dependencies are declared once, in the root `[workspace.dependencies]`, so the rewrite is that table plus the members list; a crate that bypasses the table with its own `git` entry is what the single-pin check catches. A git dependency on a monorepo tag resolves the named package out of the fetched tree, and takes features like any dependency, so the pinned library compiles under the series' flavor (`channel-flavors`). `main` keeps path dependencies and every member, so nightly is where library work meets the app first. This is what the published _A series ref builds itself_ already asks of a tag — a build from its own lockfiles and pins — with the lockfile's git pins now being the pins.
- **The in-tree copies stay on the series, inert.** They leave the workspace, so Cargo never sees two crates named `bedrock`, but they stay on disk so cherry-picks from `main` that touch both app and library paths still apply. They are never built, and version-integrity refuses a series pull request that changes them (D8), so the only way a library change reaches a series is a pin bump (D1).
- **Pins move only by the planner.** `patch` moves a pin to a newer tag on the same line (D1); nothing else does. Every crate that depends on a group pins the same tag, checked by version-integrity, so one binary carries one copy per group.
- **No credential.** The repository is public, so cargo fetches a tag of it in CI and on a workstation with nothing configured, and the Nix overlay fetches it as it fetches any public source; the build jobs gain nothing. The monolith planned a `CARGO_NET_GIT_FETCH_WITH_CLI` helper and a token for the overlay's fetches on the belief that the repository was private; that plumbing is dropped, and this bullet is where it would return if the repository went private again. The overlay stays self-contained, as the published requirement demands.
- **Nix:** on `main` the overlay's in-tree build is unchanged; on a series it builds a fetched tag whose lockfile pins git sources, which the recipe has to vendor because the sandbox builds offline. `buildRustPackage` does that through `cargoLock.outputHashes`, one hash per pinned tag that moves with every pin — the per-source bookkeeping `nix-pins` already declined to carry as `cargoOutputHashes`. crane vendors git dependencies without per-source hashes, which is the argument already recorded for it. **Decided 2026-11-16 (John): crane.** Every pin bump would otherwise be a hash chase; 3.4 moves the app and Station recipes to crane and deletes the dangling `pins.cargoOutputHashes` read with them. _Implemented 2026-11-16:_ both recipes build with `craneLib.buildPackage`. crane is a flake input, and the recipes read its locked revision out of the tree's own `flake.lock` (`distribution/nix/packages/crane.nix`) rather than take it from the overlay — the overlay stays self-contained, and a tag's recipe builds with the crane it was written for. Neither recipe runs crane's dependency-only pass: it dummifies the sources by re-reading every manifest with `fromTOML`, strict TOML 1.0, and the crate manifests are TOML 1.1 (only the root and app manifests are held to 1.0, D10) — the vendoring is the point, the cache of compiled dependencies is not. The app keeps nixpkgs' tauri hook as its build and install phases under crane's vendoring.
- **The Station package follows the pin** (decided 2026-10-29, John). `distribution/nix/packages/outpost/package.nix` builds `--package outpost --features cli` from the evaluated tree and reads `crates/outpost/Cargo.toml` for its version, and the published `nix-overlay` requirement said exactly that. On a series whose workspace no longer contains `crates/outpost`, cargo cannot apply `--features` to a package outside the workspace and the manifest on disk is inert, so the recipe as written would fail on every series ref. It is amended: on a series ref the overlay builds the Station from the `outpost` tag the lockfile pins — the fetch-by-rev path the recipe's own header anticipates — reading that tag's manifest for its version; on `main` it builds in-tree as today. **Why:** the aim is for `outpost` and `waypoints` to be cached to cachix when built, and a cache entry is only worth having if it names a release — a series' Station must therefore be a build of a released `outpost`, the same tag the app on that series ships, never of an inert in-tree copy that nothing else builds. This is the one `MODIFIED` delta outside `protected-branches` (_Flake overlay exposes desktop packages_, every existing scenario kept, one added). _Implemented 2026-11-16:_ the overlay reads the tree's `Cargo.lock` rather than its channel — an `outpost` entry sourced from a tag of this repository is the pin — fetches that tag by its locked revision with `builtins.fetchGit`, and applies the tag's own `distribution/nix/packages/outpost/package.nix` to the tag's tree; a tree with no such entry builds `crates/outpost` in-tree.
- **Rejected:** building in-tree with an equality check against the tag (the tag becomes a baseline that drift can leave behind; the point is that the tag _is_ the release); vendoring the tagged source into the series' tree (a copy is a second source of truth); library series branches (puts library tags off `main`); keeping `crates/outpost` a member on a series so its package still builds (two packages named `outpost`, one in-tree and one pinned, which is the two-copies case the single-pin check exists to refuse, and a cache entry for a Station no release describes).
- **Gate:** `cargo metadata` on a series resolves every group from its tag with one copy per group; a build on the series ignores an edit to its in-tree `crates/bedrock`; a series build job fetches its pins with nothing configured; `nix build` of a series package evaluates and builds offline after vendoring; `nix build .#outpost` on a series ref resolves `outpost` from the pin, reports the pinned manifest's version, and is unchanged by an edit to the series' in-tree `crates/outpost`.

### D8 (2026-10-29, revised 2026-11-26): The API floor arms from the tree, not from the calendar

- **Why:** no `<group>-v*` tag exists until the first minting cut, so an API check that demanded a baseline would fail every library pull request until then.
- **Shape:** the `semver` job and the cut's floor list `<prefix>*` tags first; none means skip, naming the group and saying the first cut mints its baseline. The check does nothing before the first cut and everything after it, with no switch to flip.
- **Withdrawn 2026-11-26:** the series-pin check (a series pull request touching a library path refused, naming the pin) and the single-pin check (every crate pinning one tag per group). Both protected pins a series no longer carries (D7). A library path on a series is a cherry-pick, which the published _A series branch carries only cherry-picks of `main`_ governs, and version-integrity's lockstep rule holds its manifests to the file like `main`'s.
- **Why the check lives here and not in `release-groups-guards`:** a measurement against a tag needs a tag, which this change creates.
- **Rejected:** a flag or date that turns the check on (a second record of the tree's state, which the tags already carry); failing a group with no tag (D5).
- **Gate:** tests: a group with no tag skips with the message; a group with a tag measures; a library cherry-pick onto a series passes version-integrity.

### D9 (2026-11-26): A preview bump resumes a cut whose series write never landed

- **Why:** a cut is two landings in one run: the summary on `main`, then the series' first write. The first real cut landed its summary, tagged the groups, and cut `v0.1.x`, and its series write failed its checks (D7). Nothing could put the tree back: `release undo` plans from a released tag and a landed series write, which did not exist, and a hand-made revert of the summary is refused by version-integrity, which reserves version writes to the bot. A pipeline that only moves forward has to be able to finish from where it stopped.
- **Shape:** the planner reads the newest series' group file. A series whose app version still carries `main`'s nightly channel — what the branch inherited from the merge commit it was cut from — is a half-finished cut. The plan is the series write alone: the app at `{major}.{minor}.0-pre.1` from the branch's name, the same projection an advance writes, landed on the series by the workflow's series steps and tagged. The `main` landing, the group tags, and the branch creation do not run; they exist. The dry run names it: `preview bump: resume — v0.1.x was cut and never wrote its version`. A resume whose landing pull request is already open refuses as any in-flight bump does.
- **Rejected:** a dispatchable undo for a cut that never shipped (a second bot path to maintain for a case the resume finishes); hand edits on the bot's branches (refused by the bot-only rule, and rightly).
- **Gate:** planner tests: a fixture series declaring `0.3.0-nightly` plans `resume` with `v0.3.0-pre.1`, writes the app alone, and publishes the series landing and no `main` landing; the generated `bump.yaml` runs its series steps and none of its cut-only steps on `transition=resume`; `tests/version_write.rs` resumes a fixture series against its remote; the real `v0.1.x` resumes to `v0.1.0-pre.1`.

## Risks / Trade-offs

- [A series' library code drifts past its tags by cherry-pick] → accepted (D7, 2026-11-26). The group file keeps the cut's versions as the bill of materials, the build data describes the drift (`bedrock-v0.1.1-2-g…`), and a library cherry-pick is reviewed and landed like an app fix. The pin design that would have prevented the drift could not be built under cargo.
- [A cut lands its summary and fails its series write] → the first cut did exactly this (2026-11-26). The resume (D9) finishes it from the series' state; the tags and `main`'s bump stand, because they are true.
- [The pin design's risks, retired 2026-11-26 with D7: a line broken on `main` unpatchable into a series; the repository going private; the `outpost` package failing on a series ref; inert crates confusing a reader; a cherry-pick summary refused on a pinned series; a pin rewrite missing a dependency; a pre-minting series passing library paths forever] → none applies to a series that builds in-tree.
- [cargo-semver-checks per flavor cost] → it runs once, under `stable`, per touched library group, Linux only, through the CI cache the test jobs will share once the build-cache follow-up reaches them. **AUDIT:** `--baseline-rev --features stable` builds `publish = false` crates on the pinned toolchain in acceptable time.
- [Pre-1.0 hides severity bugs] → `features_always_increment_minor(true)` makes feat and break look identical for the app; every severity test uses a `1.x` base (D4 gate). For libraries, right-shift is the intended behaviour, not a hazard.
- [The first minting cut counts every group over the whole first-parent history] → that is the honest reading: nothing has been released, and the `!` headers already in history break their own groups under right-shift, so `outpost` and `bedrock` land at `0.2.0` rather than `0.1.1`. The dry run prints every group's target before anything is written, and 6.2 has John sign off on the first bill of materials.
- [The group tags are minted after a wait that can outlast an App token] → the same answer `protected-branches` gave the app's tag: one token minted after the wait, with `contents: write` only, covers every tag the run creates on that merge commit; a run that fails between the merge and the tags leaves a landed summary and no tags, and re-dispatching the cut is refused until the tags exist, so the gap is visible rather than silent (3.2's scratch run covers it).
- [The cut's pull request runs the whole test suite] → every group's manifest changes, so `test-plan` resolves nearly `all()`. Accepted: a cut is rare and deliberate.
- [Summary bodies drift from the diff] → the guards' gate requires exactly one header per touched group, no more and no fewer; this change reads only what that gate passed.
- [The pin rewrite misses a dependency declared outside the workspace table] → the single-pin check names both manifests the moment two tags for one group appear, and `cargo metadata` on the series is a gate before the first pull request lands.
- [A series cut before this change carries `path` dependencies and the check passes its library paths forever] → intended: such a series is never pinned retroactively, and every series cut after this change starts pinned (D1 step 5), so the in-tree case is confined to series that predate minting, if any are cut.
