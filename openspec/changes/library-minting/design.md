## Goals / Non-Goals

**Goals:**

- One planner mints every group's version on `main`; a library tag always names a commit the planners' first-parent walk contains.
- The bump for every group is `max(declared, evidence)`, and the tests that prove it simulate a `1.x` base so pre-1.0 right-shifting cannot hide a severity bug.
- Each channel is its own build of released library versions: a series compiles the tags it pins under its own flavor, `main` compiles the in-tree libraries under nightly's, and a cherry-pick cannot change a series' bill of materials by accident.
- Every check this change adds is inert on the tree as it stands — no pin, no tag — and arms itself from what the first minting cut creates, so landing it blocks nothing.
- Everything is derivable: the bill of materials from the pins, the group of a path from the group file, the build data from the tree or the lockfile.

**Non-Goals (design-level, beyond the proposal's):**

- No second source of versions: no ledger file, no version field in the group file, no version in any Tauri config. A series' pins are dependencies, not a version source.
- No new checker for behaviour. API breaks come from `cargo semver-checks`; data breaks come from fixtures; everything else is a declaration.
- No new GitHub client or transport. The cut's writes reuse the pull-request path `protected-branches` lands and the `octocrab` calls already in `tools/github.rs`; a group tag is one more `create_tag`.
- No library series branches. A library's tags live on `main` only; a line that has broken there is shipped by a new app cut, not patched (D1).
- No change to the format of a summary or to which checks gate it; that is `release-groups-guards`. This change reads summaries.
- No release, record, or index entry for a library. A group tag is a source ref the series' lockfile pins, not a publish (D1).
- No credential plumbing for git dependencies. The repository is public; the day that changes, D7 says where the plumbing goes.

## Decisions

D1–D7 carry the monolith's decisions, dated as they were settled and revised; D8 answers the two hazards review found. Each `AUDIT` needs sign-off.

### D1 (2026-10-11, revised 2026-10-29): Library versions are minted on `main` by a cut, and a series takes them only by pin

(monolith D3)

- **Why:** with `publish = false` and no channels, a library release has no reader but the app's series. Minting at the app's cut gives each series a coherent bill of materials; minting on demand with a group-scoped cut gives an existing series a way to take a fix. Both happen on `main`, so a library tag always names a commit the planners' walk contains.
- **Sequence of an app cut:** (1) `release-plan cut` computes each library group's next version under right-shift; (2) botswain opens a pull request to `main` with one summary commit carrying every `main`-side write — each changed group's manifests and `main`'s provisional `{next minor}-nightly` bump — and enables auto-merge; (3) the required checks run and it lands as a merge commit; (4) the merge event triggers the second phase, which reads the landed summary's per-group headers, tags each named group at the merge commit, and cuts `v{minor}.x` from it; (5) the series' first pull request rewrites its library dependencies to those tags (D7) and writes the app version, gated by the same checks, landed as a merge commit, then tagged. Advance, promote, and patch follow (5) for the app version.
- **A group-scoped cut** (`cut --group bedrock [--floor patch|minor|major]`) runs (1)–(4) for one library: one `chore(release): bedrock 0.2.1` header, one tag, no branch, no app movement, no release workflow. It refuses with nothing counted; a floor raises the bump and never lowers it.
- **How a library fix reaches a series** (revised 2026-10-29). The fix lands on `main` and soaks in nightly. If `main`'s group has taken no break since the series' pin — under right-shift, features are patch-level, so that is the common case — a group-scoped cut mints `bedrock-v0.2.1` on `main`, carrying the fix and whatever non-breaking work landed with it, and `patch` on the series moves its pin to that tag and bumps the app in one pull request. Nothing is cherry-picked into the series' library code; a series pull request that touches a library path is refused (version-integrity, D8).
- **When the line has broken on `main`,** no commit anywhere holds "the old line plus only the fix," and a tag cannot be inserted before the break without rewriting history. `patch` refuses for that group, names the breaking commit, and points at a new cut: the fix ships as a new series. This is accepted rather than worked around with library series branches, which would put library tags off `main`.
- **Tags go on the merge commit.** `main`'s first-parent history contains the merge commit, not the PR branch's commit, so a tag made before the merge would name a commit the planners never walk. Each tag is one `tools::github::create_tag` call, as the app's are.
- **A library tag is not a release.** It has no artifact, no release record, and no index entry: it is a source ref the series' lockfile pins. The published election and withdrawal rules (`release-publishing`) concern the `v[0-9]…` tags that trigger a channel's run, and the index workflow's `v*` trigger records app releases only; `bedrock-v…` matches none of those patterns, so a group-scoped cut starts no run, no run can withdraw a group tag, and no index entry names one. The question the monolith left open — whether the index entry waits for the build — is answered by the published `release-index` requirement: the entry follows the tag, by the trigger, and a failed build after it leaves a valid release; nothing here changes that.
- **The commit:** subject `summary: cut 0.3.0-pre.1`; body one `chore(release): <group> <version>` header per changed group, plus one for `main`'s own bump. The planner writes every changed manifest into the working tree and the pull-request action `protected-branches` adopts commits them together under that message, restricted to the manifests it names — one commit for the whole cut, which the Contents API cannot do. The body is what phase two reads, so the commit describes its own consequences.
- **No tag yet** (added 2026-10-29). The first minting cut finds no `<group>-v*` tag for any group. A group's current version is then its anchor manifest's, and the whole first-parent history is its cycle — the rule `log_range` in `planners/release.rs` already applies to the app before its first release, which is also where the app stands: no stable tag exists, so its first cut is measured from `0.0.0` over the same history. The API floor has no baseline and skips, saying so (D5); declarations and the fixture floor still apply.
- **The bookkeeping marker is `chore(release):`, not a new type.** `baf7e109` made every planner message `chore(release): …` after an earlier cut minted its tag and then failed to draft release notes under `require_conventional`; `.config/cliff.toml` already skips `^chore\(release\):`, and a test holds the planner to the prefix. The per-group headers in a cut's body use the same form.
- **Tokens:** every pull request botswain opens, and the merge that lands it, uses the App token, as `devenv-update` already does and `protected-branches` extends to the planners. The same token mints the tags and branches, which is what the published requirement _Release refs are minted so their pushes are observable_ demands.
- **Rejected:** a ruleset bypass pushing straight to `main`; releasing libraries on merge (bookkeeping at random times wakes nightlies); minting at promote (libraries live on `main`); tagging from the first phase (names a commit outside first-parent history); library hotfix tags on the app's series branch (the app's patch tags live there, but the library tag would then not be on `main`); a hotfix tag on `main` that drags a breaking change along (semver-dishonest); recording group tags in the release index (they are not releases).
- **Gate:** `release-plan cut --dry-run` prints every group's current and next version and the pull request it would open; a scratch-repository run shows one landed summary merge, its tags, and the branch cut from it; a group-scoped cut lands one tag and nothing else — no release run, no index entry; `patch` moves a pin on an unbroken line and refuses on a broken one.

### D2 (2026-10-11): Groups own disjoint paths; the app counts what it ships

(monolith D4)

- **Why:** paths cannot misreport, while scopes are optional and unchecked.
- **Ownership:** each library group owns its members' directories. `waypoints` owns everything else except `tooling/` and bookkeeping: `src-tauri`, `cartograph`, `store`, and the frontend. The mapping reuses the longest-prefix rule `test::owning_package` already applies, extended from crates to groups; the group file `release-groups-guards` lands is where the members are read from.
- **Counting:** a library counts commits touching its own paths. The app counts its own paths plus every group's, because the binary ships them; a `fix(bedrock)` is a user-facing fix.
- **Walk:** first-parent, with each merge diffed against its first parent, so a pull request is one commit with the merge message. The nightly planner shares the walk and so becomes first-parent too; its decision — did anything land — is unchanged, since a landed pull request is still one commit.
- **History the walk needs:** full, as the planner jobs already check out. Attributing by path makes that requirement sharper rather than new — a shallow tip is a root commit diffed against the empty tree, so every path would look changed — and the workflow test that holds planner jobs to a non-shallow checkout keeps covering it.
- **Bookkeeping:** `nix/releases/`, commits listed in `.git-blame-ignore-revs`, and botswain's `chore(release):` commits count toward no group. The index exclusion is the pathspec already in place; the other two extend it, and the third already matches every planner message in history (D1).
- **Rejected:** scope-based attribution.
- **Gate:** tests on the existing `fixture::Repo`, grown to make merges and body-carrying commits: a `bedrock-core`-only commit counts for `bedrock` and `waypoints` only; a tooling-only, ignored-rev, or `chore(release):` commit counts for none; a three-commit pull request counts once.

### D3 (2026-10-11, revised 2026-10-19): A summary is read one header per group

(monolith D5, the reading half)

- **Why:** one header, many groups. Rather than parse multi-scope subjects, a multi-group commit's subject summarizes, and its body carries one header per touched group. This is the convention release-please uses for [multiple changes in one commit](https://github.com/googleapis/release-please#what-if-my-pr-contains-multiple-fixes-or-features).
- **Where the format is decided:** the `summary` type, the one-header-per-group body, the merge message being the pull request's title and description, and the gate that holds a summary to exactly one header per touched group are `release-groups-guards`'; the repository setting that keeps the body at merge is `protected-branches`'. This decision is what a planner does with a summary once the gate has passed it.
- **Where it is read from:** the merge commit. Branch commits underneath are never read by a planner; `--first-parent` skips them, and the PR's diff is the merge commit's diff against its first parent.
- **Severity:** each group reads its own header; the subject counts for no group. A `!` in a library's header breaks that library; `!` never breaks the app (D4). The app's declared type is the highest among the commit's headers.
- **Single-group commits** keep free-form scopes; the path decides the group. CONTRIBUTING's comma-joined regions stay legal only while every region falls in one group — `refactor(app,store): …` is one `waypoints` commit; `refactor(domain,cartograph): …` must be a summary.
- **Library rules:** Cargo's 0.x right-shift (feat → patch, break → minor), which `next_version`'s defaults and cargo-semver-checks both assume. This is what makes a library hotfix tag on `main` honest (D1): everything that landed since the pin on an unbroken line is patch-level by definition.
- **Rejected:** multi-scope subjects such as `feat(bedrock,outpost)!:`; an unscoped `!` applying to every touched group.
- **Gate:** tests for a two-header summary and a single-group commit with a free-form scope, each on a `1.x` base; the format-side tests (a summary missing or naming an untouched group) are the guards'.

### D4 (2026-10-11): The app's only breaking signal is a `Covenant: break` trailer

(monolith D6)

- **Why:** the app's contract is the data covenant (continuity, egress, interop), not Rust APIs. A wire-protocol break is an interop break, so it needs the trailer even though the code lives in `outpost`.
- **Reading it:** the walk reads trailers (`%(trailers:key=Covenant,valueonly)`), not only `%s`. The trailer applies to the whole commit, summaries included.
- **Severity:** feat → minor even in 0.x, unchanged. Before 1.0 a trailer still yields a minor, but it is recorded, and each one is an entry in the covenant exemption log that `git log --grep` can answer.
- **App majors are human-triggered.** A major for `waypoints` is a product decision, which no commit can prove. The cut targets a major for the app only when a person passes `release-plan cut --major`. The trailer is the floor, not the trigger: a `Covenant: break` since the last stable makes a cut without `--major` refuse, naming the commits, rather than cut a silent minor or an unreviewed major. `--major` without a trailer is allowed. Library majors stay automatic, since their contract is a Rust API the checkers can see.
- **`cartograph` API breaks never floor the app.** cargo-semver-checks on `cartograph` runs against the last `v*` tag as PR information only; its sole consumers are `src-tauri` and the frontend, in lockstep, so an API break there is internal.
- **The `!` already in history stays meaningful to its own group.** `feat(outpost)!: deployable Station` and its siblings break `outpost` under D3 while leaving the app's version to the trailer, which is exactly the split this decision wants.
- **Rejected:** honouring `!` or `BREAKING CHANGE:` for the app.
- **Gate:** tests on a simulated `1.2.0` base: `feat!:` without the trailer targets `1.3.0`; a commit with the trailer makes `cut` refuse and `cut --major` target `2.0.0`; `cut --major` with no trailer also targets `2.0.0`.

### D5 (2026-10-11, revised 2026-10-29): Severity is the greater of declared and detected, measured on the stable surface

(monolith D7)

- **Why:** a floor stops a mislabeled commit from producing a wrong version; the PR check stops it from reaching history.
- **API floor:** `cargo semver-checks --baseline-rev <group tag> --features stable` for each library-target member of `bedrock`, `outpost`, `domain`, and `transload`. The proc-macro `bedrock-derive` is declared-only. The tool joins the toolchain through `devenv.nix` like every other tool, projected to the `xtask` mise lane.
- **Why the stable flavor** (revised 2026-10-29). Once libraries gate behaviour on flavors (`channel-flavors`), a library has three API surfaces. The one every series consumes is the stable one, so that is the contract: an item that exists only under `nightly` or `preview` can change or vanish without breaking any series, and the check must not count it. A nightly-gated change decides its own bump by its header alone. This is also what `patch` reads to tell an unbroken line from a broken one (D1): the same check, same flavor, against the series' pin.
- **No baseline, no measurement** (added 2026-10-29). No `<group>-v*` tag exists until the first minting cut, and `--baseline-rev` needs one. A group with no tag is skipped, at PR time and at cut, with a message naming the group and saying the first cut will mint its baseline; declarations and the fixture floor still apply. Without this the `semver` job would fail every library pull request between landing and that cut (D8).
- **Fixture floor:** a modified, deleted, or renamed file under `covenant/fixtures/<group>/` since the last stable tag is breaking for that group and for the app. The directories and the append-only rule are `release-groups-guards`'; the floor at cut is here.
- **PR asymmetry:** an undeclared break fails; an over-declared break passes, since behaviour changes and macro output escape the checkers.
- **Rejected:** evidence alone (misses semantic breaks); messages alone; checking every flavor's surface (a nightly-only item is by definition not a contract anyone outside nightly holds); failing a group with no tag (blocks every library PR for the wrong reason).
- **Gate:** fixture-repository tests where evidence exceeds the declaration, at PR time and at cut; a nightly-gated removal reports no break under stable; a group with no tag skips with the message and a group with one measures.

### D6 (2026-10-11, revised 2026-10-29): Builds embed every group's version alongside `BuildInfo`

(monolith D12)

- **Why:** a bug report should name the `bedrock`, `outpost`, `domain`, `transload`, and app versions it ran, not only the app's.
- **Shape:** a structure carried alongside `BuildInfo`, baked by `src-tauri/build.rs`, one entry per group. It is registered with typegen like `BuildInfo`, so the bindings stay generated, and `--version` prints it.
- **Where the value comes from** (revised 2026-10-29): an injected value first, as `build.rs` already takes `GITHUB_SHA`; then, where the group is a git dependency — every series — the tag `Cargo.lock` pins, which is exact and needs no git metadata in the checkout; then, on `main`, `git describe --tags --match '<prefix>*'` against the in-tree crate; then the anchor manifest's declared version, so a shallow local clone never fails to compile and never claims more than the manifest says. A series never builds anything but the pin, so a build there can never report a described version of an in-tree copy.
- **Nix:** the overlay builds a fetched tag carrying no git metadata. On a series the lockfile's pins are the answer; on `main` it reads each anchor manifest with `builtins.fromTOML`, as `nix/channel.nix` already reads the app's. That reader takes strict TOML 1.0; `crates/outpost` and the root already pin that dialect with `#:tombi toml-version = "v1.0.0"`, and `crates/bedrock`, `crates/domain`, and `crates/transload` gain the same directive.
- **Gate:** a `main` build at `bedrock-v0.4.0` reports it; a series build reports exactly its pin whatever its in-tree copy says; a Nix build reports injected values.

### D7 (2026-10-29, proposed — AUDIT): A series builds its libraries from the tags it pins; `main` builds in-tree

(monolith D18)

- **Why:** a channel is a build of _released_ library versions, and a tag is the trivially checkable guarantee of what "released" means. Building a series from its own `crates/` would mean the series ships whatever cherry-picks happened to touch a library; building from the tag means it ships exactly the bill of materials the cut recorded, and a cherry-pick cannot change that by accident.
- **Mechanism:** the series' first pull request after a cut rewrites every library group's dependency in the series' manifests from `path = "crates/…"` to `git = "<this repository>", tag = "<group>-v<version>"`, removes the library crates from the series' `[workspace].members`, and regenerates `Cargo.lock`, which then pins the tag's commit. On this tree the dependencies are declared once, in the root `[workspace.dependencies]`, so the rewrite is that table plus the members list; a crate that bypasses the table with its own `git` entry is what the single-pin check catches. A git dependency on a monorepo tag resolves the named package out of the fetched tree, and takes features like any dependency, so the pinned library compiles under the series' flavor (`channel-flavors`). `main` keeps path dependencies and every member, so nightly is where library work meets the app first. This is what the published _A series ref builds itself_ already asks of a tag — a build from its own lockfiles and pins — with the lockfile's git pins now being the pins.
- **The in-tree copies stay on the series, inert.** They leave the workspace, so Cargo never sees two crates named `bedrock`, but they stay on disk so cherry-picks from `main` that touch both app and library paths still apply. They are never built, and version-integrity refuses a series pull request that changes them (D8), so the only way a library change reaches a series is a pin bump (D1).
- **Pins move only by the planner.** `patch` moves a pin to a newer tag on the same line (D1); nothing else does. Every crate that depends on a group pins the same tag, checked by version-integrity, so one binary carries one copy per group.
- **No credential.** The repository is public, so cargo fetches a tag of it in CI and on a workstation with nothing configured, and the Nix overlay fetches it as it fetches any public source; the build jobs gain nothing. The monolith planned a `CARGO_NET_GIT_FETCH_WITH_CLI` helper and a token for the overlay's fetches on the belief that the repository was private; that plumbing is dropped, and this bullet is where it would return if the repository went private again. The overlay stays self-contained, as the published requirement demands.
- **Nix:** on `main` the overlay's in-tree build is unchanged; on a series it builds a fetched tag whose lockfile pins git sources, which the recipe has to vendor because the sandbox builds offline. `buildRustPackage` does that through `cargoLock.outputHashes`, one hash per pinned tag that moves with every pin — the per-source bookkeeping `nix-pins` already declined to carry as `cargoOutputHashes`. crane vendors git dependencies without per-source hashes, which is the argument already recorded for it; the task settles which, and the `outpost` recipe's dangling `pins.cargoOutputHashes` read is settled with it.
- **The Station package follows the pin** (decided 2026-10-29, John). `nix/packages/outpost/package.nix` builds `--package outpost --features cli` from the evaluated tree and reads `crates/outpost/Cargo.toml` for its version, and the published `nix-overlay` requirement said exactly that. On a series whose workspace no longer contains `crates/outpost`, cargo cannot apply `--features` to a package outside the workspace and the manifest on disk is inert, so the recipe as written would fail on every series ref. It is amended: on a series ref the overlay builds the Station from the `outpost` tag the lockfile pins — the fetch-by-rev path the recipe's own header anticipates — reading that tag's manifest for its version; on `main` it builds in-tree as today. **Why:** the aim is for `outpost` and `waypoints` to be cached to cachix when built, and a cache entry is only worth having if it names a release — a series' Station must therefore be a build of a released `outpost`, the same tag the app on that series ships, never of an inert in-tree copy that nothing else builds. This is the one `MODIFIED` delta outside `protected-branches` (_Flake overlay exposes desktop packages_, every existing scenario kept, one added).
- **Rejected:** building in-tree with an equality check against the tag (the tag becomes a baseline that drift can leave behind; the point is that the tag _is_ the release); vendoring the tagged source into the series' tree (a copy is a second source of truth); library series branches (puts library tags off `main`); keeping `crates/outpost` a member on a series so its package still builds (two packages named `outpost`, one in-tree and one pinned, which is the two-copies case the single-pin check exists to refuse, and a cache entry for a Station no release describes).
- **Gate:** `cargo metadata` on a series resolves every group from its tag with one copy per group; a build on the series ignores an edit to its in-tree `crates/bedrock`; a series build job fetches its pins with nothing configured; `nix build` of a series package evaluates and builds offline after vendoring; `nix build .#outpost` on a series ref resolves `outpost` from the pin, reports the pinned manifest's version, and is unchanged by an edit to the series' in-tree `crates/outpost`.

### D8 (2026-10-29, proposed — AUDIT): The series-pin refusal and the API floor arm from the tree, not from the calendar

- **Why:** two checks this change adds would, written for the end state, refuse trees this change does not touch. No series exists today, but any series cut before this change lands — under the pipeline `protected-branches` finishes — inherits `main`'s `path` dependencies and builds its libraries in-tree, so a series-pin refusal that fired on every series would reject every legitimate library cherry-pick onto it; the published requirement _A series branch carries only cherry-picks of `main`_ still governs such a branch. And no `<group>-v*` tag exists until the first minting cut, so an API check that demanded a baseline would fail every library pull request until then.
- **Shape:** the series-pin check reads the series' root `[workspace.dependencies]`: a library group declared as `git` + `tag` is pinned, and any change under its own paths is refused naming the path and the pin, unless it is the bot moving the pin; a group still declared as `path` is built in-tree, and the check passes its paths. The `semver` job and the cut's floor list `<prefix>*` tags first; none means skip, naming the group and saying the first cut mints its baseline. Both checks therefore do nothing today and everything the day after the first minting cut, with no switch to flip.
- **Why these two checks live here and not in `release-groups-guards`:** a refusal that names a pin needs a pin to exist, and a measurement against a tag needs a tag; both are created by this change. Landing the checks with the first guards would have been a refusal with nothing to name.
- **Rejected:** a flag or date that turns the checks on (a second record of the tree's state, which the manifests and tags already carry); refusing library paths on every series from day one (breaks any series cut before minting); failing a group with no tag (D5).
- **Gate:** tests: a `path` series passes a library cherry-pick; a `git` series refuses one naming the pin; a bot pull request moving a pin passes; a group with no tag skips with the message; a group with a tag measures.

## Risks / Trade-offs

- [A library line broken on `main` cannot be hotfixed into a series] → accepted (D1). With libraries this churny it will happen; the planner says so and names the cut as the vehicle rather than minting a tag that drags a break into a series. Severity and proximity to the next cut decide between waiting and cutting early.
- [The repository goes private and every series' git dependency stops resolving] → nothing here assumes a credential, so the failure is loud at fetch time rather than silent; D7 names where a cargo credential helper and an overlay token would go.
- [The `outpost` package would fail on every series ref once `crates/outpost` leaves the workspace] → the pin rewrite (3.3) also points the overlay's Station at the pinned tag on a series (D7), and its gate includes `nix build .#outpost` on the series resolving from the pin. The published requirement is amended in this change's `nix-overlay` delta rather than worked around.
- [Inert library crates on a series confuse a reader] → the directories exist, build nothing, and refuse edits. Documented in CONTRIBUTING and in the series' `Cargo.toml` comment the cut writes; version-integrity's refusal names the pin, so the first person to try learns why.
- [A cherry-pick summary touching library paths cannot land on a pinned series] → the operator splits it: the app-group half is cherry-picked, the library half reaches the series by pin if the line is unbroken. The refusal message says exactly that.
- [cargo-semver-checks per flavor cost] → it runs once, under `stable`, per touched library group, Linux only, through the CI cache the test jobs will share once the build-cache follow-up reaches them. **AUDIT:** `--baseline-rev --features stable` builds `publish = false` crates on the pinned toolchain in acceptable time.
- [Pre-1.0 hides severity bugs] → `features_always_increment_minor(true)` makes feat and break look identical for the app; every severity test uses a `1.x` base (D4 gate). For libraries, right-shift is the intended behaviour, not a hazard.
- [The first minting cut counts every group over the whole first-parent history] → that is the honest reading: nothing has been released, and the `!` headers already in history break their own groups under right-shift, so `outpost` and `bedrock` land at `0.2.0` rather than `0.1.1`. The dry run prints every group's target before anything is written, and 6.2 has John sign off on the first bill of materials.
- [Phase two of a cut runs on a merge event, which a person could also produce] → the handler acts only on a merged pull request authored by `wp-botswain[bot]` whose head commit is a `summary: cut …`; anything else is ignored and logged.
- [The cut's pull request runs the whole test suite] → every group's manifest changes, so `test-plan` resolves nearly `all()`. Accepted: a cut is rare and deliberate.
- [Summary bodies drift from the diff] → the guards' gate requires exactly one header per touched group, no more and no fewer; this change reads only what that gate passed.
- [The pin rewrite misses a dependency declared outside the workspace table] → the single-pin check names both manifests the moment two tags for one group appear, and `cargo metadata` on the series is a gate before the first pull request lands.
- [A series cut before this change carries `path` dependencies and the check passes its library paths forever] → intended: such a series is never pinned retroactively, and every series cut after this change starts pinned (D1 step 5), so the in-tree case is confined to series that predate minting, if any are cut.

## Migration Plan

1. **Prerequisites, from the sibling changes:** the group file, its parser, and the `version-integrity` task and workflow (`release-groups-guards`); the pull-request write path and the three rulesets (`protected-branches`); the four flavors in every group crate (`channel-flavors`). Nothing below is landable before them, and none of them depends on anything here.
2. **Attribution and severity** (D2–D5's reading half): the group-aware walk, summaries, the trailer, `--major`, and the stable-surface API floor at cut. The planners read richer history but still mint only the app. Landable alone, after step 1.
3. **The pin checks and the API check, armed from the tree** (D8): the series-pin and single-pin checks and the `semver` job join `version-integrity`. Inert on the tree as it stands — no pin, no tag.
4. **Minting and per-channel builds** (D1, D7): per-group plans, group-scoped cuts, the two-phase cut, the series' pin rewrite, the overlay's vendoring of pinned git sources, the Station package following the pin, and the pin-moving `patch`. Proven in a scratch repository before the first cut.
5. **The fixture floor at cut** (D5), once the fixture directories exist.
6. **Build data** (D6), independent of 4 and 5.
7. **The first cut** — there is no series yet — mints the first library tags and opens the first series, which builds from them; the nightly after it reports the tags in its build data.

Rollback: steps 2, 3, 5, and 6 are additive. Step 4 reverts a series by restoring path dependencies and members, which is one pull request per series; tags already minted stay valid.
