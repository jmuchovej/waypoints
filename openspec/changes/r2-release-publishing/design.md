## Context

See proposal.md — Why. The mechanics that constrain the approach:

The release workflow is generated by `tooling/xtask/src/tasks/workflows/release.rs` as one shape per channel: `prepare` (nightly only, the planner) → `test` on each desktop platform → `create-release` (drafts the record) → `build` on each of five platforms → `publish-release` (flips the draft public). Builds already depend on the test gates and the draft, and `publish-release` already depends on every build — so the dependency graph needed for atomicity exists; its gate does not. `publish_release`'s condition is `!failure() && !cancelled() && <tag present>`, and a skipped job satisfies all three.

`Platform` is a five-variant enum with no architecture dimension, and each platform's `artifacts()` is a glob set over the bundler's output directories. The `platforms` dispatch input exists to build a subset, and today composes freely with a non-empty `tag`.

Tags arrive two ways. Nightly's `prepare` mints one through the refs API before any build runs, so the workflow is the tag's author. Preview and stable are triggered by a tag push created earlier by `release_plan`, so the tag precedes the run and the run has no claim on it.

`tooling/infra` already declares the `releases` bucket and an account token whose policy is scoped to that bucket with R2 read-write permission groups, both through a reusable `cloudflare/r2` module. State lives in a Postgres backend with state and plan encryption enforced, keyed from 1Password through an external key provider, so nothing sensitive is local or committed. Nothing writes to the bucket yet, and the token's value is not yet published anywhere a release workflow could resolve it.

The site deploys as a Cloudflare Worker (`nitro.preset: "cloudflare_module"`, `deployConfig: true`), which can be granted a bucket binding at deploy time — read access with no key pair in configuration.

## Goals / Non-Goals

**Goals:**

- Make "published" a single observable event per channel, with one commit point.
- Achieve atomicity without needing to delete objects, so a partial run is inert rather than requiring cleanup that can itself fail.
- Keep the change inside the generator: the committed workflows stay generated and `check-generated` keeps proving it.
- Keep read access credential-free for the site, and write access scoped to the two steps that write.

**Non-Goals:**

- Transactional guarantees across the store and the forge. The two are separate systems; the design orders them so that no interleaving advertises an incomplete release, but it does not pretend they commit together.
- Deciding the required-target set per channel beyond recording today's five jobs.
- Access control over archived releases. The design bounds retrieval cost without it and says what to reach for if that stops holding.

## Decisions

### The manifest is the commit point (2026-10-11)

A channel advertises a release only through `{channel}.json`, written after every required target has uploaded and as the run's last write. Everything before it is invisible: artifact keys are content-addressed by version/platform/arch and nothing reads them except by way of a manifest that names them.

This buys atomicity without deletion. A run that uploads three of five targets and dies leaves three unreferenced objects; no manifest names them, so no client can reach them, and the store's retention rule collects them. The alternative — upload to a staging prefix and copy into place on success — costs a second full transfer of every artifact and introduces a copy step that can itself half-fail. A third alternative, deleting on failure, makes correctness depend on cleanup running after an arbitrary failure, which is exactly when it is least likely to run.

Rejected: making the GitHub release's draft→published flip the sole commit point. It already exists and is nearly right, but it governs the record, not the bytes; a published record whose artifacts are missing from the store is the failure mode most visible to users.

### Completeness is counted, not inferred (2026-10-11)

The publish gate changes from `!failure() && !cancelled()` to an explicit count of successful target uploads against the channel's required set. GitHub Actions offers no condition meaning "every needed job succeeded" that also treats a skip as disqualifying — `success()` on `needs` is the closest, but a skipped dependency does not make `success()` false in the way required here, and reasoning about the matrix of `needs` states is how the current hole arose.

Counting is explicit and testable: each build records its target on success, and the publish job asserts the recorded set equals the required set. A generator test asserts that no publishing job's condition is a bare `!failure()`.

Consequence: a `platforms` subset dispatch combined with a non-empty `tag` is now a contradiction. It becomes an early error in the run rather than a silent partial publish, because the alternative — letting it proceed and simply never publishing — wastes a full build matrix to produce nothing and reads as a hang.

### A run deletes only a tag it minted (2026-10-11)

Nightly's `prepare` is the tag's author, so it can withdraw it; the planner records that this run created the ref, and the withdraw step deletes it only on that evidence. Preview and stable tags are the workflow's trigger, so withdrawing them would mean deleting a ref that existed before the run and may already have been fetched — deletion cannot un-fetch, and a later re-push of the same name makes the tag appear to move under anyone who had it.

Rejected: uniform deletion across channels, which was the initial framing. It is simpler to state but strictly more destructive, and the asymmetry is not arbitrary — it tracks who authored the ref. Also rejected: provenance-guarded deletion in every channel (delete if the tag points at this run's commit and has no published release). It is defensible, but it makes the rule conditional on repository state at withdraw time, and a stale or concurrently-moved tag turns a cleanup step into a judgement call.

For preview and stable the withdraw is therefore record-only: the draft is discarded, the tag stands, and re-running the same tag reuses the draft — which `create_release`'s existing `gh release view ... || gh release create` guard already supports.

### Targets are the host architecture of each platform (2026-10-11)

"Every target" means the five jobs that exist: macOS arm64, Linux amd64, Windows amd64, Android, iOS. The toolchain declares arm64/x86_64 for all three desktop platforms plus musl, but no job builds them, and a required set naming targets nothing produces would make every run a shortfall.

The architecture is recorded in the key and the URL even though only one value per platform is currently produced, so widening the set later adds rows without changing the scheme. The download surface advertises exactly the produced set — the alternative, advertising the full grid and 404ing most of it, is worse than not offering it.

### Published formats are the bundler's installers (2026-10-11)

macOS `.dmg`, Linux `.AppImage`, Windows `.exe`. The extension becomes a per-platform property of the naming scheme rather than a fixed trio. Rejected: a uniform `.dmg`/`.tar.gz`/`.zip` trio, which reads tidily but has no source — Windows's `.nsis.zip` is the updater payload rather than a portable application, and the bundler emits no plain Linux tarball, so two of the three would need new bundler output to exist at all.

Linux's `.deb` stays a build output without becoming a published target; adding it means a second key per platform and a second thing the completeness count must require.

### Write via the S3 endpoint, read via a binding (2026-10-11)

CI writes with the existing bucket-scoped token over the S3 API, because a runner is not a Worker and has no binding. The site reads through a Worker R2 binding: no key pair in `runtimeConfig`, no request signing, and no egress charge for reads that stay inside the provider. The two paths need different access shapes, and giving the site the write token to avoid having two mechanisms would hand a public-facing surface an integrity credential.

### Upload credentials are minted locally, per job, by xtask (2026-10-12)

Every release job that uploads an artifact gets its own short-lived credential, derived in-process by `xtask` rather than resolved from the vault. The vault holds one long-lived parent; `xtask` resolves it through secretspec's Rust API, signs a scoped JWT with it, builds the store client from the derived credential, and drops the parent once the derivation is done. No client ever holds the parent (see the client decision below).

R2 offers two routes to a session credential. The API route (`POST /accounts/{account_id}/r2/temp-access-credentials`, taking `bucket`, `parentAccessKeyId`, `permission`, `ttlSeconds` up to 604800, and optional `prefixes`/`objects`) returns `accessKeyId`, `secretAccessKey` and `sessionToken`. The local route produces the same shape with no network call: sign a JWT naming the bucket and scope with HS256 under the parent's secret access key, take the SHA-256 hex digest of the signed JWT as the temporary secret, and encode the session token as `base64("jwt/" + <signed-jwt>)`. Either is an ordinary S3 session triple — access key, secret, session token — which any S3 client consumes.

Local signing is the one chosen, for a reliability reason rather than a security one: it puts no service between a finished build and its upload. A release that has already spent an hour compiling should not fail because a credential endpoint is unreachable, and the API route would add exactly that dependency at the worst moment.

Scope is the channel's prefix, which is what the channel-led key layout buys: a job publishing nightly receives `object-read-write` confined to `nightly/`, so a credential leaking out of a third-party build script can neither reach another channel nor outlive the build. `object-read-write` rather than an `admin-` permission, because the job writes objects and has no business altering the bucket.

Lifetime defaults to **3 hours** and is configurable through `xtask`. Three hours is comfortably longer than any current build and far short of the 7-day ceiling; configurable because a new dependency or a cold cache can lengthen a compile without warning, and a credential expiring mid-upload is a failed release for no good reason.

This applies to every release job that uploads through the bundler pipeline, on all three channels — not only nightly. Nix-built packages are outside it: they publish nothing to this store.

### The store is reached through `opendal` in-process, from one client constructor (2026-10-19)

The upload, manifest-write, and withdraw steps are `xtask` subcommands over an `opendal` `Operator` for the S3 service. One shared constructor — `create_r2_client(channel)` or similar — does the whole credential path: it resolves the parent through secretspec's Rust API, derives the channel-scoped session triple by local JWT signing, drops the parent, and returns an `Operator` built from the derived triple alone. No caller sees a credential; each generated `run:` step is one line dispatching to `xtask`, and no transfer tool joins the build lanes.

The upload is `write_with(key, bytes).if_not_exists(true)`, which the S3 service sends as `If-None-Match: *` and R2 honours, so "an upload never overwrites" is enforced by the store atomically rather than by a check-then-act in the client. The withdraw is `delete_iter` over the keys the run recorded.

The rule this follows: `xtask` shells out only where no Rust API exists. `devenv` exposes no queryable output, `gh` holds auth the REST surface would re-implement, `treefmt` is a formatter. R2 is plain S3 with mature Rust clients, so it fails that test, and a vendor-neutral client is preferred since nothing here needs a vendor-specific API.

Why `opendal` over `object_store`: both expose the conditional create, both are 0.x with two or three breaking releases a year, and both bring reqwest 0.13 beside the workspace's 0.12. `opendal` documents R2 specifically (region `auto`, exact-size multipart parts, the 700-key delete cap), carries a retry layer that handles 429 as of 0.59.5, and since 0.59 is modular enough that `services-s3` pulls only the core and the S3 service crate. `object_store`'s one edge is a builder that reads nothing ambient by construction; `opendal` loads `AWS_*` and EC2 metadata unless told not to, so the constructor sets `disable_config_load` and `disable_ec2_metadata`, and a unit test pins both.

Pinned configuration. Default features off; `services-s3`, `layers-retry`, and `http-transport-reqwest-rustls-no-provider` with ring's provider installed at startup, so `aws-lc-rs` stays out of a tree that is on `ring`. Builder: endpoint, bucket, region `auto`, `enable_exact_buf_write`, the two disable flags, and the derived access key, secret, and session token. Task 2.3's live verification is re-run after any `opendal` bump, since the S3 service's `if_not_exists` was reverted once in 0.57 before being restored.

Why the build cache is different: `xcache` runs before the registry snapshot and the sccache server exist in a job, so it cannot be `xtask`. It remains a projected `rclone` driven by a script, by bootstrap order rather than preference.

Rejected: `rclone` for publishing, since `--ignore-existing` is check-then-act and it puts a shell between the workflow and the transfer on three operating systems. `aws-sdk-s3`, a vendor client for a vendor-neutral protocol whose default request checksums are a known R2 friction point. `object_store`, for the reasons above; a close second.

### Nothing published is ever deleted; cold releases change storage class (2026-10-12)

The store keeps every version it has ever published, on every target, including the mobile targets that have no download link. It is an archival registry of what was built and released, not a cache of what is current. Reclaiming space happens by moving an object to the Infrequent Access class, never by removing it.

This dissolves the counted prune that an earlier draft of this design called for. The objection to age-based retention was that a nightly is elected only when work landed, so a quiet fortnight under an expiry rule would empty the channel precisely when the last nightly is the only installable thing. Tiering removes the premise: a cold nightly is still downloadable, only cheaper to store and dearer to fetch. With deletion off the table, age is a perfectly good signal, and age is exactly what a bucket lifecycle rule expresses — so retention returns to a declaration in `tooling/infra` and this change contributes no prune step, no listing, and no ordering rule.

The channels transition on different schedules, nightly soonest, because a nightly's useful life is days and a stable's is years: **nightly at 30 days, preview at 90, stable at 270**. Three rules on one bucket, each selecting its channel's prefix, declared in `tooling/infra` alongside the bucket they govern.

Two sharp edges in writing them. The provider's condition takes `max_age` in _seconds_, not days, so the rules compute from a day count rather than stating a literal — a bare `30` would tier everything after half a minute. And `cloudflare_r2_bucket_lifecycle` does not support `terraform import`, unlike the bucket and token it sits beside, so it must be created by an apply rather than adopted from existing state.

What the class actually costs, from R2's published pricing (checked 2026-10-12): data retrieval at $0.01/GB, which Standard does not charge at all, plus roughly double the per-operation rate — class A $9.00/M against $4.50/M, class B $0.90/M against $0.36/M. There is a 30-day minimum billable storage duration, charged even if the object is deleted, moved, or replaced inside it. Egress remains free in both classes, so the charge is on the retrieval, not on bandwidth to the user. A ~100 MB installer therefore costs a fraction of a cent to serve cold, which is what makes the archive affordable rather than merely principled.

Two constraints came out of reading the docs rather than assuming. Lifecycle transitions are **one-way**: an object in Infrequent Access cannot be moved back to Standard by a lifecycle rule. So a release that turns hot again after ageing out — an old stable suddenly being downloaded heavily — cannot be re-warmed declaratively; it would have to be rewritten. Acceptable, given retrieval is cheap and edge caching absorbs repeat traffic, but it means the transition age should be chosen conservatively rather than aggressively.

And one property this design does **not** assert, because R2's storage-class and pricing pages do not state it: that an Infrequent Access object is served without a restore or rehydration step. It is very likely immediate — the class is priced as a retrieval fee rather than an archival tier — but it is unverified, and it should be confirmed before the lifecycle rule lands. If a restore step did exist, the archive would still be correct; only the latency of a cold download would change.

Rejected: deleting old nightlies, which was the previous decision. It is cheaper still, but it throws away the only copy of something that was publicly released, and the saving is on the smallest artifacts we store.

### Retrieval cost is bounded by immutability, not by access control (2026-10-12)

The worry with a tiered archive is that anything reachable can be hammered, and an Infrequent Access retrieval fee turns traffic into cost. It is a real concern and the obvious reflex — gate archived versions behind sign-in — is the wrong first move.

Every archived object is immutable, which means a retrieval can be cached at the edge effectively forever. So the exposure is not one retrieval per request; it is one retrieval per archived object per cache eviction. The archive is a bounded set — one artifact per target per published version — and an adversary cannot enlarge it. Repeatedly fetching one old nightly costs a single retrieval; fetching all of them costs the archive's size once, which is the same bill as one person legitimately mirroring it. A request for a version that was never published reads nothing at all, because the object is absent, so a miss costs a class-B operation and no retrieval.

That makes the ordering: rely on immutable caching first, add a rate limit on the archived path as a cheap bound on burst, and hold authentication in reserve. Gating a published release behind an account is a meaningful change to what "released" means, and it should not be spent on a cost that caching already bounds.

Rejected for now: requiring a session for archived downloads (the site has auth, so it is available), and serving only the recent window through the API. The second is the real trap — it would quietly break durable links to older stable versions, which is the one thing an archive exists to protect.

### A withdrawal deletes the keys it wrote, best-effort (2026-10-12)

Withdrawal deletes the objects the run uploaded, in addition to discarding the draft record. Atomicity does not depend on this — nothing advertises those keys either way — which is exactly why it is safe here, and why a failed delete is not a failed withdrawal.

This is not a reversal of rejecting deletion as the atomicity mechanism; it is cleanup whose failure is inert. It matters more now than it did when the design still pruned: with nothing ever expiring, an orphan from a shortfall would otherwise sit in the bucket for the life of the project, tiering down but never leaving. The run that wrote the key is the only party that knows it is an orphan — a lifecycle rule cannot tell an unreferenced object from an archived one.

### `latest` is a redirect to the versioned URL, not a copy (2026-10-12)

Each channel exposes a versionless download URL in the same shape as a versioned one, with `latest` standing where the series goes and the final segment naming no version:

```
/api/v1/releases/stable/latest/macos/arm64/waypoints-latest.dmg
      302 →
/api/v1/releases/stable/v0.1.x/macos/arm64/waypoints-v0.1.1.dmg
```

A mutable pointer in front of an immutable resource. The versioned URL keeps its year-long immutable caching; the alias is a short-lived redirect that can be purged on publish. `latest` cannot collide with a real series, which is always `v{major}.{minor}.x`, and the resolved version comes from the channel's manifest rather than from request text — so the alias adds a lookup, not a way to name an arbitrary object.

Rejected: copying the artifact to a `latest` key on publish, which is the closest an object store comes to a link — there is no link primitive, only `CopyObject`. It duplicates every artifact, adds a second write that can half-fail, and makes a key mutable, which would force the immutable caching off the very objects that benefit from it most.

A consequence worth stating: the redirect lands on the versioned response, so the saved file is `waypoints-v0.1.1.dmg`, not `waypoints-latest.dmg`. A file named for a moving target is useless on disk a month later. The known cost is that a fetcher which derives a local filename from the URL it was given — a dotfile manager pinning a download, say — gets a versioned name it did not ask for, and two such fetches at different times produce two differently-named files. Out of scope here; recorded so it is a known limitation rather than a surprise.

### The download page is static; only the displayed version is live (2026-10-12)

The download page stays prerendered and its links are versionless, so the HTML is identical for every visitor and cacheable at the edge without a per-request origin hit. Since the links carry no version, a release published after the last build does not make them wrong — which is what makes prerendering safe here, and why the alias above is load-bearing rather than cosmetic.

The version and date the page _displays_ are fetched from the channel's manifest on the client. They are presentation, not navigation: a stale heading above a correct link is a cosmetic fault, whereas a stale link is a broken download. Keeping the fetch client-side leaves the cached HTML untouched and does not block first paint.

This supersedes an earlier decision in this design to read manifests at request time for freshness. Request-time reads are fresher but defeat full-page caching, and the alias delivers the freshness that actually mattered. The manifest endpoint itself remains request-time — it is the live pointer, and it is small.

### Channel leads the key, because lifecycle rules can only filter by prefix (2026-10-12)

The object key is `{channel}/{series}/{os}/{arch}/waypoints-{version}.{ext}`.

An earlier draft of this design dropped the channel, on the reasoning that a version's channel is already a total function of its tag grammar — nightly carries a counter and a date, preview a `-pre.N`, stable neither — so storing it too would be a second source of truth. That reasoning is sound and the conclusion was still wrong, because retention is per-channel and R2 lifecycle rules filter by **prefix only** (checked 2026-10-12: no object-tag filter, no pattern matching, up to 1000 rules each with its own prefix and age). A series prefix is useless for the purpose, since one minor line holds all three channels' versions — `v0.2.x/` eventually contains `v0.2.0-nightly.3+…`, `v0.2.0-pre.1`, and `v0.2.0`. Without the channel leading, "tier nightlies after weeks and stable after years" is not expressible at all.

So the channel is materialised into the path, and the duplication is disarmed rather than avoided. The uploader never accepts a channel as input: it derives one from the version and writes where that says. The download surface recomputes it and refuses a request whose channel segment disagrees with its version. A misfiled object is therefore representable, but not readable: any read of it fails closed. That is a weaker invariant than the earlier draft's and the only one that admits per-channel retention.

Two things improve as a side effect. The URL becomes an exact mirror of the key rather than the key plus a segment, which removes a translation step. And enumerating a channel's history becomes a prefix listing again, instead of listing every series and filtering by grammar.

One refinement the layout forces either way: a target may produce more than one artifact. Android emits both an `.apk` and an `.aab`, differing only by extension under one `{channel}/{series}/android/arm64/` prefix. Completeness therefore counts _targets_, not keys.

### Notes stay in the forge; enumeration moves to the store (2026-10-11)

The store answers _what exists_ (versions, per-channel current release, available targets); the forge answers _what changed_ (notes, from `git-cliff`). `ungh.cc` is dropped because it is unauthenticated and cannot read a private repository — which is why the download page renders blank in production today, not any defect in the page.

Rejected: uploading notes to the store so the forge leaves the render path entirely. It would make the store self-sufficient, but it duplicates content that the release record already owns and makes the notes' source ambiguous. Kept instead: a release whose notes cannot be read is still listed with its downloads, so the forge is a soft dependency for presentation rather than a hard one for distribution.

## Risks / Trade-offs

- **The manifest write succeeds and the record publish fails** → The channel advertises a version whose notes are absent. The delivery spec requires a release to list with its downloads even when its notes cannot be read, so this degrades presentation rather than distribution. Ordering the manifest last means the reverse (a published record with no artifacts) cannot happen.
- **Orphaned objects accumulate from repeated shortfalls** → Each failed run leaves up to one artifact per succeeded target, unreferenced, and nothing expires it now that retention only tiers. Withdrawal deletes them best-effort; what survives is a shortfall whose withdrawal also failed, which tiers down to the cheapest class and is never served. Publishing never depends on the delete succeeding.
- **A tiered archive turns traffic into cost** → Infrequent Access charges per-GB retrieval, so archived downloads are not free the way warm ones are. Bounded by immutability: one retrieval per archived object per cache eviction, over a set an adversary cannot enlarge. A rate limit on the archived path bounds burst; authentication is held in reserve rather than spent on a cost caching already bounds.
- **The storage class has a 30-day minimum billable duration** → Charged only when an object is deleted, moved, or replaced within 30 days of entering Infrequent Access. Nothing in this design does that: an archived release is meant to outlive the window by years, uploads never overwrite, and withdrawal cleanup acts on objects minutes old that are still in Standard. The one way to trigger it is a deliberate re-warm (rewriting an object to Standard) inside a month of its transition, which is a manual act on a single object.
- **Tiering is one-way under lifecycle rules** → An archived object cannot be returned to Standard by a lifecycle rule, so a release that becomes hot again after ageing out stays on the dearer retrieval path unless rewritten. Argues for a conservative transition age rather than an aggressive one.
- **Whether an archived object needs a restore step is unverified** → R2's storage-class and pricing pages do not say. Pricing it as a retrieval fee rather than an archival tier suggests it is immediate, but it must be confirmed before the lifecycle rule lands. A restore step would change a cold download's latency, not the archive's correctness.
- **Counting targets adds a cross-job data path** → Each build must record its success somewhere the publish job reads. This is more moving parts than a condition expression, and a bug in the recording could block a complete release. Mitigated by failing closed — an unreadable record means no publish — and by a generator test over the gate.
- **A nightly withdraw burns a version number** → The planner's counter advances even when the run is withdrawn, so a deleted nightly tag leaves a gap in the sequence. Accepted: the counter exists to distinguish rebuilds, not to be contiguous.
- **Dropping GitHub release assets breaks any existing direct link** → Marked BREAKING in the proposal. No release has ever been published, so the practical blast radius is zero at the time of the change; the risk is only that the habit of linking assets re-forms later.
- **The site cannot read the store in local development** → A Worker binding is absent under a plain dev server, so downloads are unavailable locally. The download surface reports an unavailable service rather than a missing artifact, which keeps the distinction legible; exercising a real download locally requires binding emulation.

## Migration Plan

No data to migrate: the store is empty and no release exists. The sequence is ordered so each step is independently verifiable.

1. Land the required-target set and the counted gate, with the generator tests. The committed workflows regenerate; `check-generated` proves they match. At this point a subset dispatch with a tag errors instead of publishing.
2. Add the store scope to the declared secrets and the upload step. Verify with a build-only run that elects nothing, confirming no upload occurs without a tag.
3. Add the manifest write and the withdraw job. Exercise both paths with a nightly dispatch: one complete, one with a platform forced to fail, confirming the second leaves no manifest and no tag.
4. Point the site at the store — binding, enumeration, notes from the forge — narrow the download page to the targets with a download path, and move it to versionless links with a client-side version fetch.
5. Add the `latest` redirect. It depends on a manifest existing, so it follows the first complete publish; until then it correctly reports a missing release.

The storage-class transition is a lifecycle rule in `tooling/infra` and lands on its own schedule. It is safe at any point: it changes what an object costs, never whether it resolves.

Rollback: steps 1–3 are confined to the generator, so reverting the commit and regenerating restores the previous workflows. Steps 4 and 5 are site deploys and revert independently. Because the store is only ever written and never mutated in place, a rollback at any step leaves published artifacts readable by the previous code path.
