## Why

The five release build jobs — macOS, Windows, Linux, iOS, Android, in each of the nightly, preview, and stable workflows — start from nothing on every run: every tool downloaded, every dependency fetched, every crate compiled. They are the slowest jobs in the repository, and the test jobs that gate them already use the Actions cache to avoid exactly that.

Everything those builds consume is pinned: `Cargo.lock`, `pnpm-lock.yaml`, `mise.lock` with per-asset checksums, `rust-toolchain.toml`, the Gradle version catalog and wrapper. Given the same pins, a cold build on a fresh runner produces the same dependency tree and the same compiled objects as the last one. That is where the repository's reproducibility comes from, and a cache does not add to it — but it can exploit it. A compiler cache keyed on the exact compiler, flags, and inputs serves an object only to a compilation that would have produced it anyway; a directory cache keyed on a manifest that carries content hashes restores only bytes the manifest would have verified. The hit rate of a warm rebuild of the same commit is then a measurement: near-total hits on the dependency graph is the pins doing their job, and a miss on an unchanged crate is non-determinism to go and find.

The store is a Cloudflare R2 bucket rather than the Actions cache, for three reasons. The Actions cache is at 8.9 GiB of its 10 GB default already, in five test-job entries; five release-profile build caches would roughly double that and set the two sets evicting each other. Its entries are scoped by ref and evicted after seven days idle, so a stable release weeks after the last one restores nothing unless nightly happened to keep the entry warm; R2 has one store for every channel and tag, and evicts only what its lifecycle rule says. And a bucket this repository owns, writable only with a credential CI holds, is a trust surface we control end to end rather than one borrowed from a third party — which also means the same store can later serve caching outside the release workflows, on terms we set, rather than inheriting whatever the Actions cache's scoping allows. Cost is not a factor: at this scale both stores round to zero.

Two kinds of cache, because the content is of two kinds. Compilation goes through sccache, which caches per compilation unit, content-addressed, and sits in front of `rustc`, clang, and gcc. Everything that is fetched rather than compiled — the pnpm store, the cargo registry, Gradle's dependency and wrapper caches, the Android NDK — is snapshotted as a directory, keyed by the manifest that pins it, and written once.

The credential that writes to the store is an integrity credential, not a confidentiality one: whoever holds it can plant compiled objects that end up in signed releases. So it is handed only to the two processes that contact the store — the sccache server and the store client — and never to the build, the job environment, or the third-party build scripts that run inside the compile.

## What Changes

- **Release build jobs compile through sccache, backed by one R2 bucket.** Every `build-*` job in `release-nightly`, `release-preview`, and `release-stable` sets `RUSTC_WRAPPER=sccache` and points sccache at the bucket. Reads and writes both require the bucket credential; there is no anonymous path.
- **C and C++ compile through it too.** The workspace builds `ring`, `zstd`, `mimalloc`, and `blake3`'s C sources on every platform; `xtauri`, which already decides the C compilers per target, wraps them in the same cache whenever a compiler wrapper is in effect. Windows is the exception for C in this change: cc-rs locates MSVC's `cl.exe` itself only when `CC` is unset, so wrapping it is a separate problem.
- **Fetched directories are cached in the same bucket.** Generated restore and save steps bracket each consumer: the pnpm store before `pnpm install`, the cargo registry before the build, Gradle's module and wrapper caches and the NDK before the Android build. An entry is keyed by the hash of the manifest that pins its contents and is written only when absent — never overwritten — so a key names one immutable snapshot. The steps are `run:` steps over `rclone`, generated by xtask; no caching action is involved.
- **Gradle dependency verification is turned on.** `gradle/verification-metadata.xml` carries a checksum for every artifact the Android build resolves, and Gradle refuses a mismatch. This is what makes the Gradle directory cache a faithful substitute for a fresh resolve; without it the cache would freeze whatever was fetched first, unverified. The wrapper distribution gets its checksum pinned the same way.
- **mise's own install cache is switched on for the build jobs.** The credential resolver (`secretspec`, `op`) is itself a mise tool, so mise cannot be restored from R2 before mise has run. `mise-action`'s built-in cache — the Actions cache, keyed by the lane's config and protected by GitHub's default write rules — is the one directory cache that stays third-party, and is marked as such.
- **The store is a bucket named `ci-cache`.** The name says who writes — CI, and only CI — which is the invariant the design rests on, and the aim is for every cache CI uses to live here, release workflows first. Release artifacts, when they move to R2, go to a different bucket in a later change. The former `releases-sccache` bucket has already been deleted; its vault item was renamed to `r2-ci-cache` and its token reused.
- **A `ci` secretspec profile, resolved only under a scope, replaces `automation`.** The profile holds every non-signing credential CI uses, grouped by scope: `cache` (the store's endpoint and S3 key pair, from `r2-ci-cache`) and `botswain` (the wp-botswain App id and private key, moved from the retired `automation` profile). It is standalone (`inherit = false`), and no generated workflow resolves it without naming a scope, so a job gets exactly one consumer's secrets. `devenv-update` is regenerated to resolve `--profile ci --scope botswain`; nothing about what it receives changes.
- **The store credential never enters the job environment.** The sccache server is started in its own step under `secretspec run --profile ci --scope cache`, holds the credential in memory, and the build is run with none: the sccache client only needs the server's local port. Each `rclone` invocation in the restore and save steps is wrapped the same way. Nothing is exported into `$GITHUB_ENV`, so no later step, no third-party action, and no `build.rs` in the dependency graph ever sees the key pair.
- **The clean-room build recipes forward the wrapper and wrap the C compilers.** `xtauri` scrubs the environment on macOS, iOS, and Android; `RUSTC_WRAPPER` joins the forwarded set — nothing else is needed, since the client carries no store configuration. When a wrapper is in effect, `xtauri` also prefixes the C and C++ compilers it selects — the system `cc`/`c++` on macOS and Linux, the per-target clang on iOS and Android — with that wrapper, in the form cc-rs recognises.
- **sccache and rclone are projected like every other tool.** Both join the `build-desktop` and `build-mobile` mise lanes from devenv, so their versions have one source and the lockfiles pin them. No marketplace action installs either.
- **Each build job reports what the caches did.** Every restore step logs hit or miss for its key, and a step after the build prints sccache's hit, miss, and error counts and the store it used, then stops the server; it runs whether or not the build succeeded.
- **The generator's cache guard is restated, not relaxed.** The test that forbids a cache action in a publishing job keeps forbidding every cache action; it additionally asserts that a step wrapping the compiler follows a server start that resolved the cache scope, that every directory-cache step resolves the cache scope itself, and that both sit in a job declaring an environment. The `zizmor` ignore comment is updated to say what the permitted caches are and why.
- **The generator stops deriving a job's environment from a profile.** With one profile serving jobs in two environments, the environment follows the job's work: builds declare `App Release`, automation declares `CI`, and the resolving steps read the credential from whichever the job declared.
- **All of this is generated.** The change is made in `tooling/xtask` and the committed workflows are regenerated with `cargo xtask workflows`; `check-generated` proves they match.

Nothing here is user-visible. The shipped artifacts are built by the same compiler from the same pinned sources; only the time it takes changes.

## Capabilities

This change lands in **`toolchain`**: it governs how the repository builds — how fast, from what store, and under what guarantees about what a restored byte is — and constrains nothing about what the app does. It relies on `toolchain/tool-projection` (pending in `mise-env-configs`) for how sccache and rclone reach CI, and it amends one requirement of the published `toolchain/secret-provisioning` spec, below. `toolchain` is a tree, so the new capability takes a new area.

### New Capabilities

- `toolchain/build-cache`: how release builds reuse what earlier builds compiled and fetched. One remote store shared by every release build job; written and read only under a credential CI holds, handed only to the processes that contact the store; compilation cached per unit through a compiler wrapper carried intact through the clean-room build recipes; fetched directories cached as immutable snapshots keyed by the manifests that pin them, and only where those manifests carry content hashes; the store's unavailability degrading to a cold build rather than a failed release; and every job reporting what its caches did.

### Modified Capabilities

- `toolchain/secret-provisioning`: "A profile resolves exactly what its consumer needs" is restated for a `ci` profile that groups CI's non-signing credentials by scope. The automation identity becomes one scope of that profile rather than a profile of its own, the cache credential becomes another, and no generated workflow resolves the profile unscoped. The guarantee — one consumer, one set of secrets — is unchanged; the shape that delivers it is.

## Non-goals

- The test jobs in the release workflows, and every job in `pull-request`, `check-generated`, `release-plan`, and `devenv-update`. They keep `Swatinem/rust-cache` or no cache, as today. Extending the R2 store to them is a later change with a different access model (pull-request runs would need a read-only credential), which this change's store layout and the `ci` profile's scoping are designed not to preclude.
- Caching C compiles on Windows (see above), or anything outside cargo's build: Xcode's Swift and Objective-C compilation of the iOS shell, Gradle's Kotlin and Java compilation, and linking everywhere. sccache caches compiler invocations it can see; these are driven by other build systems and are seconds of work in this repository.
- Caching apt packages, Xcode's DerivedData, or the Android SDK beyond the NDK. Small, fragile, or both.
- Gradle signature verification (`verify-signatures`). Checksums are what the directory cache needs; a trusted-keys list is a separate undertaking.
- Local development. No developer machine is pointed at the bucket; the wrapper and the directory caches exist only in the generated build steps.
- Hosting release artifacts in R2. That is a different bucket and a later change; `ci-cache` holds only what builds reuse.
- Declaring the bucket, its token, or its lifecycle (eviction) rules in code, and rotating the token. All of that will be OpenTofu in infrastructure tooling that is its own change; the bucket and token already exist, and the repository assumes the token in the vault item can read and write the bucket.

## Impact

- `tooling/xtask/src/tasks/workflows/` — `_helpers.rs` (`Profile` becomes `Release` | `Ci`, a `Scope` type, and a `Environment` enum the jobs declare directly), `_steps.rs` (the server start, the sccache wrapper env, the directory restore/save pair, the stats step; `SecretSpec::with_scope` gains its first callers), `_jobs.rs` (`build`), `devenv_update.rs` (resolves `ci` under `botswain`), and the tests in `workflows.rs`.
- `.github/workflows/release-{nightly,preview,stable}.yaml` and `devenv-update.yaml` — regenerated.
- `.github/zizmor.yml` — comment only.
- `secretspec.toml` — the `ci` profile and the `cache` and `botswain` scopes; the `automation` profile removed.
- `devenv.nix` — the `sccache` and `rclone` tool entries; `.config/mise.build-desktop.{toml,lock}` and `.config/mise.build-mobile.{toml,lock}` regenerate from them.
- `tooling/bin/xtauri` — `RUSTC_WRAPPER` joins the forwarded list, and the C/C++ compiler selection gains the wrapper prefix.
- `src-tauri/gen/android/gradle/verification-metadata.xml` — new, committed, regenerated by a `just` recipe when the Android dependency set moves.
- `nix/devenv/android.nix` — the generated `gradle-wrapper.properties` gains `distributionSha256Sum`.
- `justfile` — the verification-metadata recipe.
- `openspec/specs/toolchain/secret-provisioning/spec.md` — one requirement restated, via this change's delta.
- Operations, outside the repo: the service account behind `App Release` must be able to read the `r2-ci-cache` item, the one behind `CI` must still read `botswain`, and the item's token must read and write the `ci-cache` bucket.
