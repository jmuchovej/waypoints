## Goals / Non-Goals

**Goals:**

- Each channel is its own build: compiled under one shipped flavor that agrees with the tree, tested under that same flavor, never relabelled from another channel's artifacts.
- A library crate can gate questionable work to nightly, and the gate is invisible to every series' build of the same code.
- Both invariants are compile-time: the wrong combination fails to build rather than ships.
- Nothing that compiles the workspace today without a flavor — the pull-request suite, the pre-commit hooks, a dev server — starts failing for lack of one.

**Non-Goals (design-level, beyond the proposal's):**

- No runtime channel flag; the channel is decided when the binary is compiled.
- No per-flavor API floor; `library-minting` measures under `stable` alone, and this design is what makes that the right surface.
- No change to what `BuildInfo.channel` reports; it keeps reading `WAYPOINTS_FLAVOR`, which the guard now makes agree with the enabled feature on every release build.

## Decisions

D1 and D2 carry the monolith's decisions under their revised dates; D3 is John's decision as recorded there. D4 and D5 are this change's own, resolving what the monolith left to the implementer. D2, D3, and D5 need sign-off (**AUDIT**).

### D1 (2026-10-11, reversed 2026-10-29): Flavors gate behaviour in a staircase, and a build enables exactly one (monolith D10)

- **Why the reversal:** the first draft made flavors identity-only, because `promote` rebuilds a preview as stable and any gated behaviour would ship in a combination no preview user ran. That argument holds only if the stable build is otherwise the preview build relabelled. D3 makes each channel its own build, tested under its own flavor, which is a stronger guarantee than "nothing is gated" and is what lets nightly carry questionable library work at all.
- **The staircase:** nightly compiles preview-gated code; preview compiles the ungated baseline; stable _is_ the ungated baseline. Preview-level code gates on `any(feature = "preview", feature = "nightly")`, nightly-only code on `feature = "nightly"`, and a feature graduates by loosening its gate until it has none. `stable` gates nothing but is still demanded: it is how a build selects its channel, and it is the feature `library-minting`'s `cargo semver-checks --features stable` names on every library crate.
- **Exactly one shipped flavor per build,** and it must agree with the channel the manifest declares. Cargo features are additive and flavors are not, so two shipped flavors is a `compile_error!` in every crate that declares them (D2), and a flavor that disagrees with the manifest's channel is refused in `src-tauri/build.rs`, the one place both facts are visible.
- **`development` is not a channel.** It adds (`store/mock`, dev tooling), never overrides a channel gate, never reaches a released artifact, and may sit beside one shipped flavor so another channel can be compiled on a workstation; beside it, the agreement check is relaxed. It never reaches a release because `Flavor::Development` is unreachable from a `Channel` and the generated build steps take their flavor from a `Channel` — the type already enforces what the requirement states.
- **Every group crate declares all four.** Today only `store` and `src-tauri` do, `domain` lacks `nightly`, `cartograph` has `development` alone, and `bedrock*`, `outpost*`, `transload` have none. They all gain the four features and the forwarding (D4), which is what makes "gate questionable bedrock work to nightly" possible. A git dependency on a tag takes features like any dependency, so a series' pinned library is compiled under the series' flavor.
- **Identity stays where it is:** bundle id, updater endpoint, data directory, icon, product name remain Tauri config, `WAYPOINTS_FLAVOR`, and Gradle resources.
- **Rejected:** identity-only flavors with a lint (the first draft); a runtime channel flag instead of compile-time gates (ships every channel's code to every user, and cannot keep an unfinished storage format out of a stable binary).
- **Gate:** D2's checks; a nightly-only test that the stable suite does not run.

### D2 (2026-10-17, reversed 2026-10-29 — AUDIT): The flavor rule is two compile-time refusals, not a lint, and the no-flavor refusal binds release builds only (monolith D14)

- **Why the reversal:** the first draft's lint kept flavor features unread, enforcing D1's first draft. With flavors gating behaviour, the invariants to hold are different: one shipped flavor per build, and the right one.
- **Two shipped flavors:** every crate that declares the flavors carries one `compile_error!` per pair — `all(feature = "nightly", feature = "preview")` and its two siblings — naming the conflict. Feature unification is how this arises — one dependency path asks for `preview`, another for `stable` — so the error names the crate where they met. The guard sits in every declaring crate rather than only in crates that gate today, because no crate gates today and the first gate must land behind a guard that already exists.
- **The wrong flavor:** `src-tauri/build.rs` reads the enabled `CARGO_FEATURE_NIGHTLY` / `_PREVIEW` / `_STABLE` / `_DEVELOPMENT` and classifies `CARGO_PKG_VERSION_PRE` the way `Version::channel` does — empty is stable, a first identifier of `nightly` is nightly, anything else is preview. More than one shipped flavor is refused. One shipped flavor that disagrees with that channel is refused, naming both, unless `development` is also enabled: compiling stable on `main` is a workstation test, not a release. Reading `CARGO_PKG_VERSION_PRE` rather than parsing `CARGO_PKG_VERSION` keeps the build script free of a semver dependency, and the rule is already duplicated once by design (`nix/channel.nix`), so a third copy of a three-way match is accepted; a test in `xtask` holds `Version::channel` to the same three cases.
- **No shipped flavor is refused only under `WAYPOINTS_BUILD`** — the hazard the monolith's task 7.2 did not see. Verified 2026-10-29: the `Tests` workflow and the three release-suite jobs run `cargo nextest run --workspace --no-fail-fast -E …` with no `--features` (`_steps.rs::cargo_nextest`, `_jobs.rs::test`); the hooks run `cargo clippy --workspace --all-targets` and the same nextest line with none (`.config/hk.pkl`); and `xtauri dev` passes `--features development` alone by default. An unconditional refusal would fail every pull request, every pre-commit hook, and every dev server on the day it landed. `WAYPOINTS_BUILD` is set by exactly one thing, `xtauri build`'s `run-build`, and `build.rs` already reads it to mean "this is a build, stamp `built_at`", so it is the existing boundary between a release build and a compile. Under it the rule is the monolith's in full: exactly one shipped flavor, agreeing with the manifest, with `development` relaxing the agreement alone. Without it, no shipped flavor compiles the ungated baseline, and the two refusals above still apply when a flavor _is_ enabled. The suites nevertheless take a flavor (D5), so that gated code is tested, not merely compiled around.
- **Why `build.rs`:** it is the only point that sees both the manifest version and the enabled features, and it already bakes `BuildInfo` from exactly those inputs.
- **Rejected:** a runtime check (too late — the wrong code is already in the binary); a lint over `cfg` uses (keeps nothing out of a binary); keying the no-flavor refusal on `CI` or `GITHUB_ACTIONS` (the test jobs run there too, and a local `xtauri build` is as much a release build as CI's); giving the suites a flavor and leaving the refusal unconditional (still breaks the hooks and the dev server); a `build.rs` dependency on `xtask` for `Version::channel` (compiles the whole tooling crate before the app's build script, for a three-way match).
- **Gate:** `cargo check --features preview,stable` on any declaring crate fails naming the conflict; on `main`, `cargo check -p Waypoints --features stable` fails naming nightly, `--features nightly` passes, `--features development,stable` passes, no flavor at all passes, and `WAYPOINTS_BUILD=1 cargo check -p Waypoints` with no flavor fails naming the flavors it accepts.

### D3 (2026-10-29, decided — AUDIT): Each channel is its own build, and nightly is where questionable code goes (monolith D19)

- **Why:** the channels are alpha, beta, and production. A nightly may carry unfinished work; a preview is a candidate; a stable is what users keep. That only holds if each is compiled and tested as itself — a stable that is a relabelled preview is a preview, and a series that builds its own tree is whatever that tree happens to be.
- **Promotion is a human decision after soak.** It already is — `release-plan` is dispatch-only — and stays so. Nothing here automates promotion; the design assumes an app reaches preview and stable only after substantive time on nightly, which is also what will make a library hotfix tag on `main` safe to pin under `library-minting`: the non-breaking work it carries has already shipped to nightly users.
- **Libraries share the app's flavors so questionable work can be gated.** A storage-format experiment in `bedrock` lives under `cfg(feature = "nightly")`; it compiles into nightly builds, is absent from every series' stable-flavor compile of the same tag, and will be invisible to `library-minting`'s API floor, which measures under `stable`. Graduation is loosening the gate, which is a visible, reviewable diff.
- **Every release rebuilds and retests under its flavor.** The release workflows already build each channel under `--features <flavor>` and `release-stable` triggers on the bare tag a promotion mints, so a promotion is already a stable build rather than a preview artifact renamed; what changes is that the suite that gates a release runs under that flavor too (D5), so the combination that ships is the one that was tested, and that a generator test holds every channel's build step to its own flavor and every publish job to its own channel's artifacts.
- **Rejected:** identity-only flavors (D1's first draft); automating promotion on a soak timer (the decision is about readiness, which a timer cannot read).
- **Gate:** a nightly-gated test exists that the stable suite does not run; a promotion's artifacts come from a build under `stable`.

### D4 (2026-10-29, proposed): A flavor reaches every group crate by forwarding along the dependency graph

- **Why:** `src-tauri` depends directly on `cartograph`, `domain`, and `store` only, and a Cargo feature can forward (`dep/feature`) only to a crate's own dependencies. "`src-tauri` forwards all four to every group" therefore means the forwarding originates at `src-tauri` and propagates: every crate that declares a flavor forwards it to each workspace dependency that declares it, so `Waypoints/nightly` reaches `bedrock-derive` through `store → bedrock → bedrock-derive` without `src-tauri` taking a dependency it does not use. Optional dependencies forward weakly — `transload?/nightly` on `store`, `outpost-fabric?/nightly` and `outpost-hold?/nightly` on `outpost` — so the flavor is enabled only when the dependency is.
- **Why this matters beyond `main`:** a `cargo nextest run --workspace --features nightly` enables the feature on every workspace member that declares it directly, so forwarding is redundant there. It is not redundant for a release build, which `cargo tauri build` runs against `src-tauri` alone, nor on a series branch under `library-minting`, where the libraries are git dependencies rather than workspace members and the flavor can reach them only through the graph.
- **The edges, from the metadata:** `src-tauri → cartograph, domain, store`; `cartograph → domain, outpost, store`; `store → bedrock, domain, outpost-protocol, transload?`; `domain → bedrock`; `transload → bedrock, domain`; `bedrock → bedrock-core, bedrock-derive`; `outpost → outpost-fabric?, outpost-hold?, outpost-protocol`; `outpost-fabric → outpost-protocol`; `outpost-hold → bedrock, outpost-protocol`. `bedrock-core`, `bedrock-derive`, and `outpost-protocol` depend on no group crate and declare the flavors without forwarding.
- **Not named:** `crates/importer-sdk` and `plugins/importer-*`, which are in the working copy and not on `main`, belong to no group and gain no flavor here; the day the group file names them (`release-groups-guards`), they declare the four like every other member, and the forwarding is one edge per dependency.
- **Rejected:** direct dependencies from `src-tauri` on every group anchor (adds unused dependencies, and still would not reach `bedrock-derive` or `outpost-protocol`); forwarding from the workspace root (Cargo has no such mechanism).
- **Gate:** `cargo tree -p Waypoints --features <flavor> -e features` lists `feature "<flavor>"` under every group crate for each of the four flavors.

### D5 (2026-10-29, proposed — AUDIT): The suites take the tree's channel flavor from `test-plan`

- **Why:** the release suite must run under the flavor the build enables (D3), and the pull-request suite should compile and run the code the branch's channel will ship, or a broken nightly-gated test is first seen by the nightly release job and withdraws the nightly. Both suites are the same `jobs::test`; one mechanism serves both.
- **Shape:** `cargo xtask test-plan` reads the app manifest's version (`APP_MANIFEST`, already the one source), classifies it with `Version::channel`, and emits a second output, `flavor`, beside `filterset`. `steps::cargo_nextest` appends `--features "${FLAVOR}"` bound to that output, the way `-E "${FILTER_EXPR}"` is bound today. Cargo accepts the flag with `--workspace` when only some members declare the feature (Context), and after D1 every group crate does.
- **Why the manifest rather than the workflow's channel:** on a release workflow the two agree by the published requirement _The manifest version names the channel_ — the tag that triggered the workflow and the tree it checked out classify as one channel — and the build step's own guard (D2) refuses the build if they did not. Reading the manifest means the pull-request workflow, which has no channel of its own, gets the right flavor on `main` and on every series branch without a second mechanism. A generator test asserts that every nextest step in the release and pull-request workflows carries the binding, and an `xtask` unit test that a `0.3.0-nightly` manifest plans `nightly`, `0.3.0-pre.2` plans `preview`, and `0.3.0` plans `stable`.
- **The hooks stay flavorless.** `.config/hk.pkl`'s clippy and nextest steps keep compiling the ungated baseline; the pull-request suite is the flavored gate, and D2's scoping keeps the hooks green.
- **Rejected:** threading a `Channel` into `jobs::test` for the release suite and inventing a separate path for the pull-request suite (two mechanisms for one line); a fixed `--features nightly` on the pull-request suite (wrong on a series branch); leaving the pull-request suite flavorless (nightly-gated code would be compiled nowhere before the nightly release).
- **Gate:** the regenerated `pull-request.yaml` and `release-*.yaml` carry `--features "${FLAVOR}"` on every nextest step, bound to `steps.test-plan.outputs.flavor`; `just check-generated` is clean.

## Risks / Trade-offs

- [A local `just tauri::build desktop` on `main` is refused] → the recipe defaults the flavor to `stable`, which disagrees with `main`'s nightly manifest; D2 refuses it naming both. Rather than pick a better default, `desktop` stops being a build method at all (task 2.3): a release build names its platform and flavor, as CI already does, and `desktop` stays the dev server's alias for the host.
- [A development-flavored bundle is refused] → `just tauri::build <target> development` sets `WAYPOINTS_BUILD` with no shipped flavor, and D2 refuses it. The dev server is the development flavor's home; a bundle is a release build. Accepted.
- [A build-only dispatch against the wrong tree is refused] → dispatching `release-preview` or `release-stable` with an empty tag against `main` now fails at `build.rs` rather than producing a preview-flavored build of a nightly tree. That is the guard working; a build-only exercise of a channel's pipeline targets a ref of that channel.
- [A third copy of the channel reading] → `build.rs` joins `Version::channel` and `nix/channel.nix`. All three are the same three-way match on the first prerelease identifier; the `xtask` test on `Version::channel` is the reference, and the gate in D2 exercises `build.rs`'s copy on a nightly manifest.
- [Flavor features must exist everywhere before the guards do] → the manifests and the `compile_error!` guards land before the `build.rs` guard and before the suites take a flavor; until then no shipped flavor gates anything, so the order is safe.
- [`--features` on a workspace-wide nextest run] → verified against the pinned cargo; if a future cargo tightens the rule to "every selected package must declare it", the tooling members would need the four features too (empty), a mechanical fix.
- [The hooks compile the ungated baseline] → a nightly-gated test is first run by the pull-request suite rather than the pre-commit hook. Accepted; the hooks' nextest line can take the same flag later.
- [No crate gates anything yet] → the proof that the staircase works is one nightly-only test; the first real gate will be a library's, under `library-minting`'s rules for what the stable surface is.

## Migration Plan

1. **Manifests and guards** (D1, D2's `compile_error!`, D4): the four flavors in every group crate with the forwarding, and the two-flavor guard in every declaring crate. Landable with no change to any workflow; nothing gates, so every existing invocation still compiles.
2. **The `build.rs` guard** (D2): refuses the wrong flavor, two flavors, and — under `WAYPOINTS_BUILD` — none. CI's release builds already pass exactly one channel flavor; local `just tauri::build` callers on `main` must now name `nightly`.
3. **The suites** (D5, D3): `test-plan` emits the flavor, the nextest step takes it, the workflows are regenerated, and the generator tests hold every suite and every build to its flavor; the nightly-only test lands with them.

Rollback: each step is additive and reverts independently; reverting step 1 after step 3 requires reverting step 3 first, since the suites would name a feature no crate declares.
