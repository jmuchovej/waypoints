## Context

See proposal.md — Why. Verified 2026-11-17 against the tree `group-file-versions` left the same day, at the commit that recorded its strict validation; each paragraph below names where a fact lives and, where it matters, which change put it there.

**The group file as it stands.** `tooling/release-groups.toml` names five groups. Each carries `version`, `members`, `tag`, `breaking`, `floors`, `fixtures`, and `minted`; `waypoints` also carries `internals`, `owns = "remainder"`, `counts = "closure"`, `breaking = "trailer:Covenant: break"`, `features-always-increment-minor = true`, `channels`, and `flavors`, and the file closes with an `[enforce]` table of five keys. Its header comment explains `breaking = "header"` and `minted = [ "cut" ]`. `release-groups-guards` D1 and D6 declared every key but `version` so the file's shape would be settled once, parsed and schema-checked with nothing acting on them; `group-file-versions` added `version` and removed `anchor`. The parser in `tooling/xtask/src/release_groups.rs` is `GroupFile { bookkeeping, group, enforce }` and `Group` with every key above as a field, under `deny_unknown_fields`, with the enums `Breaking`, `Floor`, `Owns`, `Counts`, `Commits`, `SummaryType`, `VersionWrites`, `Fixtures`, and `SchemaRule`; `schema()` generates `tooling/schemas/release-groups.schema.json` from those types and `the_committed_schema_is_the_generated_one` holds the two equal.

**How a path is attributed.** `owned_paths` in `release_groups.rs` lists every `(group, directory)` a group owns: its `members`, `internals`, and `fixtures`, trailing slash trimmed. `owner_of(path)` answers none for a path under `tooling/` or a `[bookkeeping].paths` prefix, else the group `test::owning_package` finds — the owned directory that is the longest `{dir}/` prefix of the path (`tooling/xtask/src/planners/test.rs`) — else `remainder_group()`, the group carrying `owns = "remainder"`. `attribute` in `tooling/xtask/src/releases/history.rs` marks a commit bookkeeping when the ignore file lists it, the release bot authored it, or a reserved subject opens it; otherwise it collects each changed path's owner and, when any owner counted, adds every group `closure_groups()` names, which is the one carrying `counts = "closure"`. That is `library-minting` D2's "the app counts what it ships". On this tree the remainder covers `.github/`, `deploy/`, `docs/`, `nix/`, `openspec/`, `src/`, `website/`, and every root file — `Cargo.toml`, `Cargo.lock`, `pnpm-lock.yaml`, `flake.nix`, `justfile`, and the rest. `history.rs`'s module doc and `attribute`'s doc state the closure; its tests `a_library_change_counts_for_its_group_and_the_app`, `a_pull_request_lands_as_one_commit`, `a_summary_reads_one_header_per_group`, and `a_single_group_commit_keeps_its_free_form_scope` assert `waypoints` on library commits, and `planners/release.rs`'s test helper `library_commit` builds a commit counting for `[group, "waypoints"]`.

**Who tells the app from a library.** `GroupFile::app_group()` returns `remainder_group()` with a context naming `owns = "remainder"`, and `app_version()` reads through it; `planners/release.rs` reaches both through its own `app_group`, in `plan`, `cut_target`, `execute`, `open_series`, `remote_pins`, `rehearse`, `app_members`, and `summary_headers`. `semver_check::library_members` sets `is_app_group = groups.remainder_group() == Some(group)` and then leaves out the package named `workspace::APP`, which is `"Waypoints"`, the app's crate at `src-tauri` (`group-file-versions` D2); `src/bin/xtask/tasks/semver_check.rs` computes `is_app` the same way for the verdict. Outside Rust, `src-tauri/build.rs` skips the group where `group.get("owns").is_some()`, `nix/channel.nix` takes `builtins.head (builtins.filter (group: group ? owns) …)` for the app's version, and `nix/packages/waypoints/package.nix` filters the libraries as `!(group ? owns)`. `workspace::APP` names a crate, not a group: no constant names the group.

**What `version-integrity` reads.** `tooling/xtask/src/version_integrity.rs` computes the groups a pull request touches through `GroupFile::touched`, which maps each changed path through `owning_package` over `owned_paths` and drops the unowned — no remainder, no closure — so the summary rule today sees a pull request changing `website/` and `crates/bedrock/` as `bedrock` alone, while the walk counts the same commit for the app. `pin_violations` and `planners/release.rs::fixture_breaks` use `owner_of`, so a changed fixture resolves to its group by the `fixtures` directory, and a series change under an unowned path resolves to the remainder, which is never pinned. The published requirement _Landing commits are conventional, and summaries are complete_ (`release-groups-guards`) says "a pull request changing more than one group's own paths SHALL be a summary".

**Which keys are read.** `breaking` is read once, in `history::Commit::header_for`: `Breaking::Header` reads `!` on the group's own header, `Breaking::CovenantTrailer` re-expresses the trailer as `!` on the app's header and ignores `!`. Searching the tree outside `openspec/`, `minted`, `floors`, `features-always-increment-minor`, `channels`, and `flavors` appear only in the `Group` struct, the generated schema, the group file, and the test fixtures; the bumper hardcodes the app's rule as `minor_for_features = true` in `Version::cut` and a library's as `false` in `Version::next_library` (`tooling/xtask/src/releases/version.rs`); the API floor runs for every library group in `group_plan` and the fixture floor for the owning group and the app in `plan`, whatever `floors` says. `[enforce]`'s five keys are read by nothing: `Enforce` and its enums are constructed by the parser and never matched on; the `version_writes` the search finds in `version_integrity.rs` is a function of that name, not the field.

**What a cut computes with nothing counted.** `cut_target` collects `header_for(app)` over the cycle's commits, which is `None` for a commit that does not count for the app, and hands the headers to `Version::cut`, which calls `bumped(commits, true)`, which is `next_version::VersionUpdater::increment`. `VersionIncrement::from_commits_with_updater` (`next_version` 0.2.26) returns `None` when the iterator is empty, and `increment` then returns the version unchanged, so `cut` appends `pre.1` to the last stable release itself: from `0.1.0` the target is `0.1.0-pre.1`, which sorts below `0.1.0`; before any stable tag, from `0.0.0`, it is `0.0.0-pre.1` with `main` moving to `0.1.0-nightly`. With commits present but none conventional the same path bumps a patch. A group-scoped cut already refuses with nothing counted — `plan` bails `nothing to cut for `{name}`: no counted commit since `{tag}`` or `in its history` — as an inline `bail!`; the planner's other messages are Tera templates in `tooling/xtask/src/templates.toml` rendered by `templates::must`, and the dry run's per-group lines are `dry-run.group-minted` and `dry-run.group-unchanged` there.

**What the dry cut prints today.** Run on this tree against the remote, which holds one nightly tag and no stable or group tag, `cargo xtask release-plan cut --dry-run` prints `Cut: 0.1.0-pre.1 on v0.1.x (preview); tag v0.1.0-pre.1`, `main moves to 0.2.0-nightly`, the summary's headers `chore(bedrock): 0.1.1`, `chore(domain): 0.2.0`, `chore(outpost): 0.2.0`, `chore(transload): 0.1.1`, and `chore(waypoints): main now targets 0.2.0-nightly`, then one line per library: `bedrock` 35 commits, `domain` 45, `outpost` 49, `transload` 7, each "over the whole history, with no tag yet". The app's own count is not printed; under the closure it is every commit that counted for anything.

**What the docs say.** `docs/CONTRIBUTING.md`'s _Landing a pull request_ says "The changed paths decide the group, not the scope. `tooling/release-groups.toml` names the groups." and its regions table says `app` covers "the Tauri app + frontend"; neither it nor `nix/AGENTS.md` names `owns`, `closure`, or any key this change deletes. The group file's own header comment does, for `breaking` and `minted`.

**`deploy/`.** The directory holds the Station's Kubernetes manifests and a `justfile`. Two commits have touched it, both scoped `outpost/deploy`, the first being `feat(outpost)!: deployable Station — supervised process, image, and Kubernetes manifests (#146)`. Today it counts for the app through the remainder.

**What does not exist yet**, and this change proposes: a constant naming the app group, a `paths` key, a planner refusal for a cut with nothing counted for the app, and a group file without the unread keys.

## Goals / Non-Goals

**Goals:**

- Every reader that needs the app's group finds it by one name, stated once in Rust and once in each reader that cannot read Rust, and a file without that group refuses before anything is planned.
- The file says what each group owns, and a path it does not list belongs to no group; a person reading the file can answer "what moves the app's version" without knowing a remainder rule.
- A library commit counts for its library, an app commit for the app, and a summary for the groups it touches; nothing counts for the app by closure.
- A cut never computes an app target from nothing; it says what moved and how to mint it.
- The file carries no key without a reader.

**Non-Goals (design-level, beyond the proposal's):**

- No second kind of ownership. `paths` is the same prefix rule as `members`; it is not a glob, a pattern, or a file list.
- No `kind` key or any other key that says "this is the app". The name says it (D1).
- No change to the bookkeeping rule: `[bookkeeping].paths`, the ignore file, the reserved subjects, and the bot's authorship stay as `library-minting` D2 left them.
- No change to how the fixture floor reaches the app's cut; it reads the diff since the last stable and never went through the closure.

## Decisions

### D1 (2026-11-17): The app group is named `waypoints` in code; `owns` and `counts` go

- **Why:** `owns = "remainder"` exists to be found by `remainder_group`, and `counts = "closure"` to be found by `closure_groups`; neither says anything a reader could not know from the group's name. This is one repository with one app, so a general rule for finding "the app group" is a rule for a case that never occurs, and inferring the app from a key whose only job is to be found is dishonest about that. `group-file-versions` D2 made the same call for the app's crate, naming `workspace::APP` rather than keeping `anchor`.
- **Shape:** `release_groups::APP_GROUP = "waypoints"`, documented beside `workspace::APP = "Waypoints"`: one names the group, the other the crate. `load_unprojected` refuses a file with no `[group.waypoints]`, naming the group and the constant, before the enumeration rule runs; `app_group()` returns the constant and `app_version()` is `version_of(APP_GROUP)`; `planners/release.rs::app_group` and every call site read the constant. `Group.owns`, `Group.counts`, `Owns`, `Counts`, `remainder_group`, and `closure_groups` are deleted, and `deny_unknown_fields` refuses a file still carrying either key. `semver_check::library_members` and the `semver` task compute `is_app` as `group == APP_GROUP`. The three readers outside Rust state the name themselves: `src-tauri/build.rs` skips the group named `waypoints`, `nix/channel.nix` reads `groups.waypoints.version`, and the recipe's `group-versions` filters `name != "waypoints"`. Each fails loudly on a missing attribute, which is what `load` would have refused first.
- **Rejected:** keeping `owns` as the marker (the key being removed); a `kind = "app"` key (one more key whose only job is to be found); inferring the app from the tag template `v{version}` (true today, an accident of naming); inferring it from the group whose members include `workspace::APP`'s directory (couples the group file to `cargo metadata` for a fact the file can state, and `load_unprojected` would have to read the metadata before it can validate the file).
- **Gate:** `load` refuses a fixture without `[group.waypoints]` naming the group (scenario _A file without the app's group_); a fixture carrying `owns` or `counts` does not parse; `the_readable_members_are_the_library_targets` still omits `src-tauri` and measures `crates/cartograph`; `nix eval` of `channel.nix` on this tree answers `nightly` and `v0.1.x` as before and fails on a fixture file without `waypoints`; a development build's `--version` prints the four library groups and not the app (scenario _The app is told from a library by name_).

### D2 (2026-11-17): A group owns what the file lists, and nothing else

- **Why:** paths cannot misreport (`library-minting` D2), and the file already says what three kinds of path a group owns; the remainder was the one kind it did not say. Writing the fourth kind down makes `owner_of` a lookup with no fallback, and makes "what moves the app" a question the file answers.
- **Shape:** `Group.paths: Vec<String>`, default empty, documented as "directories the group owns beyond its crates and fixtures". `owned_paths` chains it after `fixtures`, trailing slash trimmed as the others are, so `owner_of`, `touched`, and `problems` read it with no further change; `owner_of`'s `None` arm replaces the remainder. The match stays `owning_package`'s: a path belongs to the owned directory that is its longest `{dir}/` prefix, so a listed directory is a prefix, never a glob, and a file name listed there would match nothing. `problems` holds a listed path to what it holds `fixtures` to — it exists, it is not under `tooling/`, and it is named by one group and nested in no other owned path — which the existing `named` map and overlap check already do once `paths` feeds `owned_paths`. `waypoints` lists `paths = [ "src/" ]`: the Nuxt frontend is the app, and CONTRIBUTING's regions table already says `app` covers it. Everything else the remainder covered — `.github/`, `docs/`, `nix/`, `openspec/`, `website/`, the root files — is listed by no group and counts for none; `deploy/` is the one directory with a plausible owner, and the Open Questions put it to John with `outpost` proposed. `docs/CONTRIBUTING.md` gains one sentence under _Landing a pull request_: a path the file lists for no group counts for no release.
- **What changes downstream:** the nightly planner's "did anything land" reads `product_subjects`, the commits counting for any group, so a day of commits under unlisted paths publishes no nightly; a `chore(deps)` bump touching only `Cargo.lock` and the root manifest counts for nothing until a commit touches an app path. The `version-integrity` summary rule, which already dropped unowned paths, now sees `src/` as the app's: a pull request changing `src/` and `crates/bedrock/` lands as a `summary`, and one changing `website/` and `crates/bedrock/` is still `bedrock` alone. The summary rule and the walk now agree about every path.
- **Rejected:** globs (nothing needs one, and `owning_package` is the rule the test planner and the walk already share); a remainder under another name; listing files (the match is a directory prefix); folding `fixtures` into `paths` (`fixtures` is read by the floor and by the append-only exemption as a thing of its own).
- **Gate:** tests on `fixture::Repo`: a commit under `src/` counts for `waypoints` alone, one under `website/` or `docs/` counts for no group and `product_commits` is empty for it, one under `crates/bedrock-core/` counts for `bedrock` alone (scenarios _Frontend change_, _Unlisted path_, _Library-only change_); `problems` refuses a listed path that does not exist, one under `tooling/`, and one nested in a member (scenarios _Listed path that does not exist_, _Listed path under tooling_, _Overlapping listed path_); `a_path_resolves_to_the_group_owning_it` grows `src/` and keeps `docs/CONTRIBUTING.md` unowned; `version-integrity` on a fixture pull request touching `src/app/a.vue` and `crates/bedrock/src/lib.rs` demands a summary, and on one touching `website/a.md` and `crates/bedrock/src/lib.rs` does not.

### D3 (2026-11-17): The closure goes; a library commit counts for its library alone

- **Why:** the closure made every library commit an app commit so that a `fix(bedrock)` would read as a user-facing fix. But the app's version is a statement about the app's own change, and the app adopting a library's change is a commit on the app's paths — a `cartograph` or `src-tauri` edit that takes the new API — which counts on its own. Where nothing in the app changed, nothing in the app's version should. A series takes a newer library by a pin move `patch` lands, which bumps the app's patch for exactly that reason (`library-minting` D1), and `main` keeps building the libraries from source, so a nightly ships whatever landed; the group versions a build embeds (`src-tauri/src/group_versions.rs`, `library-minting` D6) already say which library commit a nightly carried. Nothing the closure recorded is lost; it is recorded where it belongs.
- **Shape:** `attribute` drops the `counted.extend(closure_groups())` step; `Commit.groups` is exactly the owners of the commit's paths. `history.rs`'s module doc and `attribute`'s doc stop describing the closure. The tests that asserted `waypoints` on library commits assert its absence: `a_library_change_counts_for_its_group_alone`, `a_summary_reads_one_header_per_group` (the app's header is `None`, so `cut` over it is the empty case D4 refuses), `a_single_group_commit_keeps_its_free_form_scope`, and `a_pull_request_lands_as_one_commit` where the summary touches `src-tauri/`, which still counts for the app by its own path. `planners/release.rs`'s `library_commit` helper builds a commit counting for the library alone, and `an_undeclared_api_break_raises_a_cut_to_breaking` and its neighbors read the same.
- **The fixture floor is unchanged.** `plan` passes every changed fixture since the last stable to `cut_target`, which refuses the app's cut without `--major`; `fixture_breaks` attributes each fixture to its owner for that group's floor. Neither went through the closure, so a changed `bedrock` fixture still floors the app.
- **Rejected:** `main` pins library tags so nightlies build versioned editions — every library change would then reach the app on `main` only after a group cut and a pin move, slowing every library-plus-app change and needing `[patch]` overrides to develop them together; a partial closure (the app counts fixes but not features — a rule nobody could state from the file); counting the app by scope (`library-minting` D2 rejected it for the same reason it rejects it here: scopes are optional and unchecked).
- **Gate:** the four `history.rs` tests above hold under the new assertions; a `fixture::Repo` summary touching `crates/bedrock/` and `crates/outpost/` counts for those two and not `waypoints` (scenario _Summary across two libraries_); `cargo xtask release-plan cut --dry-run` on a scratch repository whose cycle holds one `feat(bedrock)` and one `feat(app)` commit plans `bedrock` from one commit and the app from one; the fixture-floor tests in `planners/release.rs` still floor the app on a changed `bedrock` fixture.

### D4 (2026-11-17): A cut with nothing counted for the app refuses

- **Why:** without the closure a cycle can hold library work and no app work. `Version::cut` over no headers appends `pre.1` to the last stable release itself (Context), so the planner would open `v0.1.x` for `0.1.0-pre.1` after `0.1.0` has shipped — a target below the release it follows — or before any stable, `0.0.0-pre.1`. A release of nothing is not a release, and the planner already knows how to say so for a library.
- **Shape:** in `plan`, after the group plans and before `cut_target`, the cut refuses when no commit in the cycle counts for `APP_GROUP`, and it refuses before reading `--major`: a major is a floor on counted work, not a substitute for it. The message is `refusal.app-unmoved` in `templates.toml`, rendered by `templates::must` in the `--group` refusal's style: `nothing to cut for `waypoints`: no counted commit since `v0.1.0`` — or `in its history` before the first stable — followed, where any library plans to mint, by the groups that moved and `release-plan cut --group <name>` as the way to mint one alone, and where none moved, by `; no library moved either`. A group-scoped cut is untouched: it never reads the app.
- **Rejected:** cutting the computed target anyway (below the last stable, and `index::classify` would record a preview of a shipped version); falling through to group-scoped cuts for every moved library (a cut should do what was asked and refuse what it cannot); a patch-level app bump with nothing counted (a release with no change in it); letting `--major` bypass the refusal (a product decision still needs something to release).
- **Gate:** tests over `cut_target`'s inputs and `plan`'s refusal: a cycle of `library_commit`s alone refuses naming `v0.1.0`, `bedrock`, and `--group` (scenario _Library-only cycle_); the same before any stable tag names `in its history` (scenario _Before the first stable_); the same with `--major` still refuses; one `app_commit` beside them plans as before; `cut --group bedrock` on the same cycle mints (scenario _A group-scoped cut still mints_); the message renders from `templates.toml` and `every_message_the_planner_writes_is_conventional_and_skipped` is unaffected, since a refusal writes nothing.

### D5 (2026-11-17): Policy follows from the kind, so the unread keys go

- **Why:** `release-groups-guards` declared `minted`, `floors`, `features-always-increment-minor`, `channels`, `flavors`, `breaking`, and `[enforce]` so that `channel-flavors` and `library-minting` could give them meaning. Both landed and gave the meaning to the kind of group instead: the app's feature bumps the minor and a library's the patch (`Version::cut` and `next_library`), the API floor measures every library and the fixture floor every owner and the app (`group_plan`, `plan`), the app breaks on the trailer and a library on `!` (`header_for`), every transition mints the app and only a cut mints a library (`execute`), and the checks `[enforce]` names are the five clauses `version_integrity::violations` runs unconditionally. A key nothing reads drifts into meaning something — the argument that removed `anchor` — and a key read only to learn what the group's name already says is a second spelling of the name.
- **Shape:** `Group` becomes `{ version, members, internals, tag, fixtures, paths }` and `GroupFile` becomes `{ bookkeeping, group }`; `Breaking`, `Floor`, `Enforce`, `Commits`, `SummaryType`, `VersionWrites`, `Fixtures`, and `SchemaRule` are deleted with the `Channel`, `Flavor`, and `Transition` imports they needed. `header_for` takes the rule from `group == APP_GROUP`: the app reads the highest body header or the subject with the trailer re-expressed as `!`, a library reads its scoped body header or the subject as written. The planner's own `Floor` (`Major`, `Minor`, `Patch`) is the `--floor` flag and stays. The schema is regenerated with `cargo xtask release-groups schema`; `the_committed_schema_is_the_generated_one` holds it. The group file drops every deleted key and its header comment says what the file now says: every crate outside `tooling/` is named once, `version` is the group's and projected by the bot, `paths` lists what a group owns beyond its crates and fixtures, and a path no group lists counts for none. Every fixture — `release_groups.rs`, `version_integrity.rs`, `releases/index.rs`'s `GROUPS`, `planners/release.rs`'s `SERIES_GROUPS`, `tests/version_write.rs`'s `group_file`, `tests/planners_refuse.rs` — drops the same keys, so a fixture still carrying one fails to parse the way `a_misspelled_key_does_not_parse` shows.
- **Rejected:** keeping the keys as documentation of policy (documentation that `deny_unknown_fields` enforces and nothing honors is a schema for a program that does not exist); a `kind` key the policies key off (D1); keeping `breaking` because it is read (it is read to answer "is this the app", which D1 answers by name).
- **Gate:** a fixture carrying any of the nine keys or `[enforce]` fails to parse naming the key (scenario _A retired key does not parse_); `the_app_ignores_the_bang_and_reads_the_trailer`, `a_summary_reads_one_header_per_group`, and `a_library_right_shifts_before_one` hold under the derived rule; `the_committed_schema_is_the_generated_one` and `tombi lint tooling/release-groups.toml` pass; `nix eval --expr 'builtins.fromTOML (builtins.readFile ./tooling/release-groups.toml)'` reads five groups; `cargo xtask version-integrity` on the tree reports agreement, since the file edit moves no `version`.

### D6 (2026-11-17): The first dry cut is re-read

- **Why:** the first cut measures the whole first-parent history, and today's dry run measures the app over every commit that counted for anything. After D2 and D3 the app is measured over `src-tauri/`, `crates/cartograph/`, `crates/store/`, `covenant/fixtures/waypoints/`, and `src/`. From `0.0.0` any `feat` on those paths still yields `0.1.0-pre.1`, so the target may read the same while the commits behind it do not; a `fix`-only app history would yield `0.0.1-pre.1`, and no counted commit would refuse under D4. Which of these the history justifies is for a reader, not this document.
- **Shape:** after the change lands, `cargo xtask release-plan cut --dry-run` is run on `main` and John reads the app's target, `main`'s next version, and each library's counted commits against `git log --first-parent`. The `version` values in the file are not touched by this change or by that reading; John intends to lower them separately so the first manual cuts land versions that can be committed to `main`.
- **Gate:** the dry run prints an app target and per-group lines, or the D4 refusal, and `git status` is clean afterwards; John signs off on the reading in tasks.md group 7.

## Risks / Trade-offs

- [A day of docs, website, or Nix commits publishes no nightly] → intended: those paths are not the app, and the nightly planner's "product work" now means a listed path (D2). The index and the group versions a build embeds still say what each nightly carried.
- [A dependency bump touching only the root manifest and lockfile counts for nothing] → flagged in Open Questions rather than decided; listing the root files under the app would recreate a remainder-shaped rule for two files. A bump that changes behavior reaches the app's version through the commit that adopts it, or is cut deliberately.
- [`src/` and a library in one pull request now needs a `summary`] → CONTRIBUTING already says a change across groups lands as one; the check names both groups. Before this change the same pull request moved the app by closure without saying so.
- [Three readers outside Rust hardcode the group's name] → `load` refuses a file without `[group.waypoints]` before any planner runs, and `the_group_file_describes_this_workspace` holds the name on this tree; the Nix readers fail on a missing attribute at evaluation, which `nix eval` of `channel.nix` in D1's gate covers. Renaming the group is a four-site edit and nothing hides it.
- [Deleting `breaking` changes behavior] → it does not: the rule it selected is the one `group == APP_GROUP` selects, and `header_for`'s tests hold unchanged (D5).
- [This change's REMOVED names a requirement that is in `library-minting`'s open delta, not the main spec] → `library-minting` is implemented and archives first, after which the REMOVED applies; if this change archived first the archive would find nothing to remove and say so, and `library-minting`'s delta would then need its requirement dropped before it archives. The Migration Plan states the order.
- [The first dry cut prints the same app target as today] → possible, since any `feat` on an app path from `0.0.0` yields `0.1.0-pre.1`; what D6 reads is whether the paths justify it, not whether the number changed.
- [`paths` overlaps a member's directory] → `problems`' overlap check refuses it as it refuses a nested fixture (D2).

## Migration Plan

1. **The name and the keys** (D1, D5): the constant, `load`'s refusal, the deleted keys and enums, the derived `breaking` rule, the three readers outside Rust, the schema regenerated, every fixture and the file edited. One pull request by a person; the file edit moves no `version`, so `version-integrity` reports agreement.
2. **Ownership and the closure** (D2, D3): `paths`, `owner_of` without a fallback, `attribute` without the closure, the tests, the CONTRIBUTING sentence, and `deploy/` wherever John places it. Lands with step 1 or after it.
3. **The refusal** (D4): `plan` and the template.
